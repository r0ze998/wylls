# 参考サイトの分析・比較・検証メモ

作成日: 2026-10-31　対象: 真 −SHIN− Claude版（`shin-aircare-claude/`）

## 1. 参考サイトの確認方法と、確認できなかった部分

ヘッドレス Chromium（Playwright）で、PC 1440×900 と iPhone 13 相当（390×844、2x）の 2 条件で実際に表示し、
ファーストビューと全ページのスクリーンショットを取得、見出し構造・使用フォント・配色・文字サイズを抽出しました。
対象: Procoat トップ／エアコンクリーニング、BEPPO トップ／エアコンクリーニング、比較対象（ChatGPT版）。

**確認できなかった・限定的だった部分（見たことにしていません）**

- 縦書きの見出し（Procoat トップの「見えない汚れまでプロの技術で徹底洗浄」、ChatGPT版ヒーローの縦書きコピー）は、
  検証環境に縦書き用グリフを持つ日本語フォントがなく、文字が重なって描画されました。意図した見た目は推測です。
- ホバー時の挙動、動画（Procoat の「動画・実績で見る」）、LINE 連携、ページ遷移後の各下層ページは確認していません。
- Procoat の「実績紹介」カードの一部はサムネイルがロゴ画像でした（遅延読み込みか、実際にロゴなのかは未確認）。
- BEPPO の右下のクーポンポップアップは閉じずに撮影しています。
- 実機のスマホ（Safari / Android Chrome）では確認していません。

## 2. 参考サイトから読み取ったこと

### Procoat（大阪・堺、B2C 中心）
- **良い点**: ファーストビューで大きな縦書きコピー＋作業中の写真＋「3つの理由」バッジで、何の会社か即座に伝わる。
  サービス紹介ページの冒頭に「他社で断られた」「ニオイが戻る」など **顧客の言葉で困りごとを列挙** しており、入りが上手い。
  料金表は税込・注意書き付きで明快。問い合わせは電話・フォーム・LINE の三本立てで、ページ下部に大きく再掲。
- **自案に取り込んだ点**: 「困りごとから入る」構成（01 セクション）。作業の流れを担当者が説明できる形で示すこと。
- **取り込まなかった点**: 青＋白＋黄色のキャンペーン色、マスコット、受賞バッジ、価格訴求。法人向けには軽く見える。

### BEPPO（名古屋、B2C 中心）
- **良い点**: 「ORGANIC HOUSE CLEANING」の英字見出しと茶・緑の落ち着いた配色で、オーガニックという個性が一貫している。
  エアコンページの **7ステップの作業手順を写真付きで** 見せており、作業当日のイメージが湧く。FAQ が実務的（駐車場、外出可否）。
- **自案に取り込んだ点**: 作業手順を具体的な行為（養生・分解・洗浄・組立・報告）で示す。FAQ は「当日どうなるか」に答える。
- **取り込まなかった点**: 価格の打ち消し線表示、クーポン、ビフォーアフター写真（素材がないため）、情報密度の高いサイドバー。

### 両者に共通して法人向けに不足していたこと
- 法人担当者が社内で使える資料（見積もりに何が必要か、稟議用の説明）がない。
- 「営業への影響」「複数拠点」「請求書払い」など法人特有の関心への回答が薄い。
→ Claude版では 05「見積もりに必要な情報」（チェックリスト＋コピー／印刷）と FAQ でここを厚くしました。

**総評**: ChatGPT版は「空気の心地よさ」を写真と柔らかい色で伝える B2C 寄りの上質さ、Claude版は「法人担当者の仕事を助ける」情報設計と硬質なトーンに振った案です。
同じ見た目に寄せていないため、どちらの方向性が「真 −SHIN−」のブランドとして正しいかを判断材料にしてください。
写真素材が用意できる前提なら Claude版の骨格に実写を入れる案、素材が当面ない前提なら ChatGPT版の生成写真の使い方も参考になります。

## 4. 実装前に比較したオープンソースの実装例

GitHub 連携は今回のリポジトリに限定されているため、Web 検索経由で GitHub 上の実装を確認しました。

- **多段フォーム**: [LucaIsMyName/stepper.js](https://github.com/LucaIsMyName/stepper.js)（TypeScript、<7KB、各ステップを DOM に残し opacity で切替、HTML5 検証を利用）、
  [mallow12/multi-step-form-project](https://github.com/mallow12/multi-step-form-project)（Frontend Mentor 課題、要約ステップあり）。
  → 依存を増やさず、確認画面は「別ビューを表示して値を読み直す」だけで足りるため **自前実装**。stepper.js の「要素を DOM に残す」考え方は、
  確認画面でも `form` を `hidden` にして値を保持する設計に反映。
- **メール送信**: [dwyl/learn-to-send-email-via-google-script-html-no-server](https://github.com/dwyl/learn-to-send-email-via-google-script-html-no-server)
  （Google Apps Script で受信、送信後に同ページで thank-you 表示。宛先を data 属性に置くと第三者に書き換えられる注意あり）、
  Cloudflare Pages の Formspree チュートリアル。
  → 宛先はクライアントに置かず、`site-config.js` の `endpoint` へ JSON POST し、サーバー側でメール送信する構成に。
- **モバイルメニューのフォーカス管理**: [uswds/uswds issue #3527](https://github.com/uswds/uswds/issues/3527)（ドロワー表示中に背景が inert でないと VoiceOver で背景に到達できる）、
  [ithaka/focus-trap](https://github.com/ithaka/focus-trap)。
  → ライブラリは使わず、メニュー表示中は `main` と `footer` に `inert` を付与し、Escape で閉じて元の要素へフォーカスを戻す実装に。

## 6. ドキュメントとコードの食い違い（見つけたもの）

- **検証環境の案内 vs 実際の挙動**: 環境の説明には「`require('playwright')` はどのディレクトリからでも動く」とありましたが、
  ES Modules の `import ... from 'playwright'` は `node_modules` のないディレクトリでは解決できず失敗しました。
  CommonJS の `require` は `NODE_PATH` 経由で動くため、スクリプトは `.cjs` に統一しました。
- **自分の検証スクリプト vs フォーム実装**: 初版の検証スクリプトは必須項目を 4 件と想定していましたが、実装は 5 件
  （会社名・担当者名・メール・相談内容・同意）です。コードに合わせてスクリプトを修正しました。
- **比較対象（ChatGPT版）の掲載内容**: 会社情報に「美装工事・ハウスクリーニング／ダクト清掃」とありますが、
  今回提供された情報は「事業：エアコンクリーニング」のみです。Claude版では未提供の事業は書いていません（どちらが正しいかは要確認）。
- 提供資料そのものには、コードと矛盾する記述はありませんでした。
