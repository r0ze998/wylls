# ⑨の隔離統合と世代番号の安全策（2026-11-05）

## 受領した原本

- Library の添付 `wylls-09-capacity-9b26f0a9.base-4cd901de.bundle` は 94,404 バイト。SHA-256 は `92233c29051339338586ef9989bb2cca676766c12c9f72f1a9ef4c021926088a` で申告値と一致した。
- bundle の前提は `4cd901de9f8e0d6c0b2016851d30595c4a70aa46`。復元 HEAD は `9b26f0a9e493b3f4fba6254c6ececfc8cbcd106a`、tree は `8c2d9c0ce0960fae23414ae99928773bab2b4ced` で申告値と一致した。原本の復元ツリーは別ディレクトリに保持する。

## この候補の範囲

既存の④・⑱・⑲の隔離候補に、⑨の独立した能力貸出カーネルと文書を追加した。預かりは `MockCustody`、施設の所有者側は未適用の 0001 パッチを模擬する。オンチェーン命令、口座、検証器、⑩の実預かり、④の実 Run との接続は含まない。0001 パッチは `git apply --check` を通るが、Holding の生産率と ABI byte 700 に触れるため、この候補には適用していない。0002 は命令案の文書である。

## 見つかった世代番号の問題と修正

元のカーネルは施設の `u8` 世代が 256 回の占領で一周したあと、旧貸出枠を退役させれば同じ `FacilityId` を再利用できた。この場合、古い喪失履歴を新しい貸出枠の喪失と誤認し、古い署名済み操作や冪等キーも新しい貸出枠に重なり得る。`end_of()` を逆順で探すだけでは、遅れて処理する旧貸出枠の喪失時刻を誤る。

この隔離候補は、現在の世代番号と同じ終了履歴がある施設について、新規貸出と旧貸出枠の生存操作を `GenerationReused` で拒否する。旧貸出枠の喪失確定、物の受取、退役は維持する。安全側の一時策なので、その施設は世代が一周した後、新しい貸出を再開できない。恒久策には再利用しない施設 incarnation を④・⑧の共通 ID と⑩の預かりキーに通す必要がある。

## 他担当との接続

- ④: `UseFacility` は模擬の `FacilityRef{place, recipe}`。⑨の能力予約・材料所有権・精算とまだ結んでいない。
- ⑧: 地図拡張の仮命令タグ `0xC1` と⑨の命令案 `0xC1` は衝突する。どちらもここでは採用せず、共有 ABI の番号割当を保留する。
- ⑩: 最新の本体・core 差分は手元に未受領。`MockCustody` を実際の所有者別預かりと読み替えない。

## 検証の境界

原本のカーネルは 37 件通過。この隔離候補では世代番号の回帰試験を修正し、同じ 37 件を再実行した。コードの共通部分への接続、SBF、LiteSVM、実チェーン送信は未検証。
