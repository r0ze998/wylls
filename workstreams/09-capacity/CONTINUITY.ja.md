# ⑨ 継続世界への対応（2026-10-31 の方針訂正）

方針：世界は期間で終わらない。戦期は世界の寿命とは別。⑨の担当は「加工と能力予約が戦期をまたいでも進み、二重生産・予約消失を起こさない」こと。

⑨は World・Period の正本も、移行処理も作りません。期間の区切りはコア（④）と継続世界の横断設計（⑧→④）のものです。⑨のカーネルには開始・終了・期間の概念がもともと無く、今回も足していません。試験の境界は、固定した試験用の時刻です。

## 1. 残っていたシーズン依存

### ⑨ 自身のカーネル（今回直した）

| 依存 | 何が起きたか | どこ |
|---|---|---|
| 貸出枠の表が固定長で、記録が減らない | 予約 16 件・許可 8 件を使い切ると、その施設は永久に `TooMany`。長く続く世界では必ず詰まる | `ledger.rs` の `MAX_JOBS`・`MAX_GRANTS` |
| 預かりの冪等キーが ID のハッシュ | ハッシュの衝突、または世代（`u8`）が一周して同じ ID になったとき、別の予約の操作が「済み」と誤判定されうる（投入が実際には動かずに帳簿だけ増える） | 旧 `JobId::tag()` |
| 番号の再利用を拒まない | 消した記録と同じ番号の再送が、新しい記録として通りうる | `Reserve`・`Grant` |
| 世代番号が一周したときの扱いが無い | 256 回占領されると、古い世代の未精算の記録と新しい世代の記録が同じ鍵になる | `Ledger.pools` の鍵 `FacilityId` |
| 試験用の入れ物の名前が `World` | 「⑨ 独自の World の正本」と読める | `ledger.rs` |

### コアと周辺（⑨からは直さない。④ への要求 §4）

| 依存 | 中身 | どこ |
|---|---|---|
| **R1 終了後の命令拒否** | プレイヤーの命令はすべて `bell(now) ≥ end_bell` で `WrongStatus`（`PlayerStart::finish`）、状態も Running のみ。0002 で提案した利用者の操作（予約・投入・取消・受取）と所有者の操作をこの経路に載せると、境界をまたぐ加工の成果物が受け取れなくなる。試験で再現した（§3） | `frontier-abi/src/prologue.rs` `PlayerStart::finish`、`player_prologue` |
| **R2 口座の住所がシーズンの鍵から作られる** | `AddrCtx::of` は `with_seed(season, seed)`。Holding・Citizen・Vault はシーズンごとの口座。0002 の CapacityPool／CapacityJob も同じ作りで提案していた | `frontier-abi/src/addr.rs` `AddrCtx::of`、`v2/addr.rs` `vault` |
| **R3 終了に伴う口座閉鎖** | 終了後は誰でも Holding・Citizen を閉じられる（`season_end_close`、tombstone）。施設の Holding（貸した工房の数、倉）も、利用者の Vault も消える | `permutation-frontier/src/proc/citizen.rs` `close_holding`・`close_citizen` |
| **R4 世代が `u8` で、最後の占領しか残らない** | `Holding.GEN` は u8。`CAPTURED_BELL`・`PREV_GEN` は最後の占領だけを持つので、喪失の記録（0002 の RecordFacilityLoss）より前に 2 回占領されると、前の世代の終わりの時刻が分からない | `frontier-abi/src/v2/layout/player.rs` `holding` |
| **R5 解放の規則が季節の長さに結びつく** | FRONTIER_7 は「7日の季節が終わるまで解放しない」（R-14）。継続世界では、休眠した施設の解放（＝⑨の施設喪失）の時刻の決め方を決め直す必要がある | `permutation-rules/src/frontier/holding.rs` `LifecycleParams` |
| R6 上限の根拠が 28 日 | 「rate × 28 days stays below 10¹²」という注記。ただし計算は i128 で、値は上限で止まるので桁あふれはしない（約 970 年の精算を試験した） | `holding.rs` `MAX_PRODUCTION_PER_HOUR` の注記 |
| R7 検証器はシーズンの記録を最初から再生する | 戦期をまたぐ加工を検証するには、区切りでの状態の引継ぎ（checkpoint）が要る。⑨の機能はまだ検証器に載っていない | `frontier-node/crates/verify` |

keeper・herald・RPC 索引・UI・AI は、⑨の機能がまだ載っていないため、⑨としての依存はありません（各担当の調査に任せます。未調査）。

## 2. 変更した挙動（カーネル）

1. **記録を閉じる操作を足した。** `Retire`（終わって全部を渡し終えた予約）、`RetireGrant`（取り消されたか期限が来て、予約が残っていない許可）、`RetirePool`（失われた世代で、予約が残っていない貸出枠）。誰でも送れる。閉じた予約の出力は許可の `spent` に残り、出力上限の計算は変わらない。
2. **番号は増えるだけ。** 許可の番号は貸出枠ごと、予約の番号は許可ごとに増える一方。閉じた記録や古い番号への操作は `Retired`（28）で、預かりには届かない。
3. **予約ごとの uid。** 一度も再利用しない番号を予約に振り、預かりの冪等キーの範囲にした（ハッシュをやめた）。閉じた予約のキーは `Custody::forget` で捨てる。カーネルが先に `Retired` で止めるので安全。
4. **世代の一周。** 失われた世代の記録が残る鍵に `OpenPool` が来たら `GenerationReused`（29）。利用者が受け取り、記録が閉じれば同じ番号を使える。
5. **操作の種類 `Op::class()`。** 所有者・利用者・誰でも、の 3 つ。④ がコアの命令の種類に写すときの入力。どれも「戦期の境界で拒否される」前提を持たない。
6. **許可の期限と世界の寿命は別。** 許可は必ず有限（`from < until`）で、自動延長しない。期限が来たら閉じて、必要なら新しい許可を出す。世界が続くことを理由に許可を永久化しない（⑤の方針と同じ）。
7. 試験用の入れ物を `World` から `Harness` に改名した。開始・終了・期間を持たない。
8. エラー `NotRetirable`（30）を足した。

## 3. 試験で確認したこと（`kernel/tests/continuity.rs` 8 件、ほか）

| 試験 | 確かめたこと |
|---|---|
| 境界をまたぐ加工 | 境界の前に予約し、材料は運搬中に境界を越え、境界の後に投入・加工・受取・記録の閉鎖。所有者（B）・数量（兵器 20、鉱石 40・木材 20 の消費）・精算の回数（2 回）・預かりの保存則が、境界が無い場合と一致 |
| 境界の前・境界・境界の後での再起動 | 保存・復元を挟んだ実行の最終状態が、挟まない実行と完全に一致。全操作を後から再送しても、移動も生産も起きない（`AlreadyApplied` か `Retired`） |
| 今のコアの終了規則を当てた場合（R1 の再現） | 投入と受取が拒否され、材料は B の隊商に残り、兵器は作られない。カーネル自身はこの規則に依存しない |
| 許可の期限 ≠ 世界の終わり | 許可が期限で閉じても、貸出枠と貸した工房（Holding の lent）はそのまま。新しい許可で次の予約が通る。閉じた番号の再発行は `Retired` |
| 閉鎖と予算・古い鍵 | 加工中・未受取の予約は閉じられない。閉じた後も出力は上限に数える。閉じた予約への 5 種の操作がすべて `Retired`。預かりのキーが消える |
| 世代の一周 | 256 回の占領で世代番号が一周。古い記録が残る間は `GenerationReused`、受取と閉鎖の後に新しい貸出枠が開ける |
| 大きな時刻 | 西暦 3000 年ごろの予約・加工・受取が正確。所有者の Holding は約 970 年分の貸し出しを精算しても値が上限内 |
| **長期運用（境界の通過とは別の検証）** | 1 施設・2 利用者で 20,000 件の予約を約 27 年（10,013 日）、許可は 90 日ごとに 226 回発行し直す。状態の大きさは 1,097 バイトで一定、預かりのキーと置き場の数も有界、生産 = 引出し |
| ランダムな競合（既存） | 閉鎖を混ぜた 300 通りで、毎手の不変条件（閉じた予約の出力を `spent` で数える）を維持 |

戦期の区切りそのもの（何を集計し、いつ区切るか）は試験していません。⑨には区切りが無いので、「区切りがあっても挙動が変わらない」ことだけを確かめました。

## 4. 移行と仕様判断が残る点（④・⑧・⑩へ）

| # | 相手 | 内容 |
|---|---|---|
| R1 | ④ | 能力の命令（所有者・利用者の操作）は、戦期の境界で拒否しない経路に載せる。少なくとも `Cancel`・`Claim`（物を返す・渡す操作）は、どの状態でも通す |
| R2 | ④⑧ | CapacityPool・CapacityJob の住所は、シーズンの鍵ではなく、世界が続く間変わらない鍵から作る。どの鍵にするかは ④ の共通方針に従う（⑨は決めない）。0002 を「シーズンの鍵から」と書いていた箇所は直した |
| R3 | ④⑩ | 戦期の境界で Holding・Vault・CapacityJob を閉じない。旧シーズンの口座を閉じる場合は、未受取の成果物と未返却の材料を ⑩ の預かりへ移してから |
| R4 | ④ | 世代を u8 のまま使うなら、喪失の記録（RecordFacilityLoss）を世代ごとの終わりの時刻とともに残す。または世代を広げる。カーネルは `GenerationReused` で守るが、コアの他の世代比較（隊商・Vault）も同じ問題を持つ |
| R5 | ④⑧ | 休眠した施設の解放時刻の決め方（季節の長さに依存しない規則） |
| R6 | ④ | `MAX_PRODUCTION_PER_HOUR` の注記の根拠（28 日）を継続世界の前提に書き直す（計算は安全） |
| R7 | ④⑯ | 検証器の区切りでの状態の引継ぎ。旧版の証拠を新版の証拠として読み替えない |
| C1 | ⑩ | `Custody::forget(scope)` を口に足した。⑩ の台帳でも、閉じた予約のキーを捨てられるようにする（または予約の口座と一緒に閉じる）。期間の切替を理由に預かりを没収・返却不能にしない |
| P1 | 仕様 | 材料の無い予約が開始まで枠を押さえる問題は、継続世界では長期化しうる（予約の開始時刻に上限が無い）。上限を設けるかは未決定（料金は入れない） |
| P2 | 仕様 | 失われた世代の記録が受取待ちのまま残ると、その施設の番号は一周するまで再利用できない。受取の期限を設けるかは未決定（期限＝没収になるので、⑩ の方針と合わせて決める） |

旧シーズンの互換性：カーネルは旧シーズンの記録を読みも書き換えもしません。既存のコアの口座（パッチ 0001 の `LENT_WORKSHOPS` は旧版で常に 0）にも影響しません。
