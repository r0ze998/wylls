## 2. 照合した項目と、接続での扱い

| 項目 | ⑨ | ⑩ | 接続 |
|---|---|---|---|
| 資源の種類 | 入力は鉱石と木材、出力は兵器（`Horses` の欄、4） | 区画で扱えるのは鉱石だけ（`ENABLED_RESOURCES = 1 << Ore`） | 区画から取るのは**鉱石だけ**。木材は利用者自身の物を ⑨ の通常の投入で入れる。兵器は ⑨ の出力の置き場に残る（⑩ に兵器の入口は無い）。⑩ は木材・兵器の区画を開けない（試験で確認） |
| 数量の単位 | milli。加工は時間とともに milli で進む | 保存は milli、移動と消費は**整数単位（×1,000）だけ** | 区画から取る量は整数単位（`units: u32`）。⑩ の消費は**投入のときに一度だけ**。⑨ の精算は自分のホッパーから使うので ⑩ を呼ばない（端数で拒否されることも、二度消費することもない） |
| 注文 ID | 予約 `(grant, job_seq)`、投入 `(job, deposit_id)` | 利用注文 `(slot, id)`。id は注文を出したときの区画の `NONCE` | 接続の記録 `(job, deposit_id) → (区画, slot, 注文 id, 量, bell)` |
| 再送防止 | 自然キー。同じ中身の再送は無変化、違う中身は `Conflict` | `set_order` は `NONCE` で守る。**`consume` 自体は冪等ではない**（呼ぶたびに注文の残りが減る） | 再送は接続の記録で答え、⑩ を呼ばない。同じ ID で中身が違えば `Conflict`。オンチェーンでは、予約の口座の投入表が同じトランザクションの中でこの鍵になる |
| 原子性 | 失敗した操作は何も変えない | 拒否は口座を一切変えない | ⑩ が消費を受けた後で ⑨ が投入を拒否したら（開始済み・投入表が満杯・ID の重複など）、両方を元に戻す |

### 加工中と完了後の状態の対応

| ⑨ の予約 | ⑩ の区画・注文 | 物の所在 |
|---|---|---|
| 予約済み・投入前 | 利用注文が `QTY_LEFT` を予約（`HELD` は変わらない） | 区画（所有者 M） |
| 区画から投入（開始前） | `HELD −= q`、`CONSUMED += q`、注文の `QTY_LEFT −= q` | ⑨ のホッパー（予約の置き場。動かせるのはカーネルだけ） |
| 加工中 | 変わらない | ホッパーから消費され、出力の置き場に兵器 |
| 完了・取消・施設の喪失 | 変わらない（⑩ には区画へ戻す入口が無い） | 余った鉱石はホッパー、兵器は出力の置き場。**引き渡しは保留**（§4 D1, D2） |
| 注文の期限切れ・取消（投入の後） | 以後の投入だけが拒否される | 投入済みの分は影響なし |
| ⑩ の倉の押収（投入の前） | 区画は凍結（`Forfeited`）、投入は拒否 | ⑨ は何も変わらない |
| ⑩ の倉の押収（投入の後） | ⑩ の没収は `HELD` だけを対象にする | 投入済みの分は ⑨ 側にあり、⑨ の規則に従う |

## 3. 契約試験（2026-11-05 時点の記録。現在の試験は §6.2）

2026-11-06 から、この表の 12 件も ⑨ の預かりに ⑩ の `LotCustody` を使って動く（§5）。`tests/lots.rs` の 6 件は §5 に。

| 試験 | 確かめたこと |
|---|---|
| 区画の鉱石で加工、整数単位で一度 | 40 単位を投入すると ⑩ の `CONSUMED` は 40,000、`HELD` は 60,000、注文の残りは 20,000。半端な時刻に 5 回精算しても ⑩ は動かず、兵器 20 ができる |
| **注文の再送** | 同じ投入を開始前・開始後・再起動後に再送しても `AlreadyApplied` で、区画のバイト列は不変。同じ ID で量が違えば `Conflict`。自分の木材で使った ID を区画の投入に再利用すると拒否され、⑩ は消費しない |
| **加工途中の再起動** | 精算の 3 時点それぞれで保存・復元（⑨ は Borsh、⑩ の区画は ⑩ 自身の 576 B の口座形式）しても、最終状態が再起動なしと完全に一致する |
| **容量不足** | 枠が埋まっていて予約は `CapacityExceeded`。存在しない予約への区画からの投入は拒否され、区画は不変 |
| **失敗時に材料を二重消費しない** | 開始後の投入（⑩ は受けるが ⑨ が拒否）と、9 件目の投入（⑨ の投入表が満杯）が丸ごと戻る。その後の正しい投入は自分の量だけ消費する |
| ⑩ の拒否で ⑨ は変わらない | 注文の残りを超える量、注文の期限切れ、違う注文 id、受け手でない者、倉の押収。どれも ⑨ のホッパーと区画が不変 |
| 用途の違い | 別の用途の注文では、工房の用途を拒否する |
| 鉱石だけ | ⑩ は木材・兵器の区画を開けない |
| 引き渡しの保留 | 区画の鉱石で作った兵器は、既定（`Hold`）では受け取れず出力の置き場に残る。自分の材料だけの予約は通常どおり受け取れる |
| 加工途中の取消 | 余った鉱石は ⑨ のホッパーに残る。⑩ には戻らないが、二度数えることも失うこともない |
| 施設の占領 | ⑨ の仮の喪失規則（占領者が施設の物を取る）がそのまま動く。⑩ の区画は触れない |
| ランダム | 200 通り × 60 手（区画からの投入 945 件、再送 1,766 件、再起動を含む）。毎手、⑩ の `CONSUMED` ＝ 接続が取った量の合計、区画の保存則、⑨ の預かりの保存則、通過用の置き場が空、を検査 |

不変条件は `Bridge::check` にまとめています。

## 5. ⑩ の adapter-09 との接続（2026-11-06）

⑩ は統合候補に、⑨ の `Custody` trait を ⑩ の区画で実装したアダプター `workstreams/10-custody/adapter-09`（`LotCustody`、commit `52a43745`、tree `f5784e40…`）を置き、⑨ への要求 R1–R6 と食い違い F1–F5 を書いた（⑩ の `08-adapter-09.ja.md`）。⑨ はこれを受けて次をした。

### 5.1 ⑨ の模擬を外した範囲

- `bridge10` の ⑨ 側の預かりを、⑨ の模擬（`MockCustody`）から **⑩ の `LotCustody`** に替えた。予約のホッパー・出力の置き場、隊商・Holding の置き場、利用者自身の区画は、⑩ の区画カーネルと口座バイト（576 B）で動く。
- 利用者**自身の区画**の鉱石は ⑩ の経路で動く：⑨ の通常の `Deposit`（`from = Vault(v)`）で区画から出し、区画が返却用の容量を予約する。余りは `ClaimSplit` で整数単位が区画へ戻り、予約はちょうど一度終わる（⑩ の `Returned` 通知と一致）。
- **他人の区画**の鉱石（利用注文）は、これまでどおり bridge の経路（⑩ の `consume`）。⑩ のアダプターに利用注文の口がまだ無いので（⑩ の R6）、利用注文の区画は bridge 側に別に持っている。**二つの区画の表を一つにするのは ⑩ の作業**（§5.4）。
- ⑨ の試験の大部分（kernel/tests）は今も ⑨ の模擬で動く。⑩ の実装は bridge10 の試験と、⑩ 自身の adapter 試験（このブランチの kernel に対して実行）で通している。

### 5.3 加工結果の記録を ⑩ と揃えた

- 予約ごとに **⑩ と同じ言葉の口座**（`Job::accounts()`：材料 2 つと成果物、`IN_TOTAL = HELD + OUT_TOTAL + CONSUMED + FORFEITED`）を持つ。返却（`returned`）と喪失による移転（`forfeited_*`）を予約に記録するようにした。
- 予約の記録を閉じるとき（`Retire`）に **`Event::Receipt`**（その口座）を出す。
- 試験：ランダム 300 通りの毎手で口座が釣り合い、ホッパー・出力の残高と一致する（kernel）。⑩ の `Consumed`・`Produced`・`Reserved` 通知の合計が受領書と一致する（bridge `the_receipt_agrees_with_10s_notes`）。

### 6.2 揃えた会計（試験 `tests/contract10.rs` 10 件、`tests/accounting.rs` 11 件）
