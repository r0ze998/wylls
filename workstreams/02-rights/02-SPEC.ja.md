# ② 最小仕様と脅威モデル：工房在庫の交換権（StockSwap）

> **未採用（統合側の判断待ち）。** StockSwap は、施設がすでに作った武具を、同じ州の中で**隊商を使わずに**交換する案で、既存の物流・距離・襲撃の危険を変える。設計 20 の「使用権の札」が指す**「工房の加工能力を貸す権利」とは別の候補**であり、その代わりではない。①④⑥はこれを決定版として前提にしないこと（`HANDOFF.ja.md` §0）。

**状態：** 採用待ちの提案。**この交換を最初の権利として採用するかは、まだ判断されていない。** 共有仕様として既成事実にしない。数字は例。

## 1. この権利は何か、何ではないか

**工房在庫の交換権**とは、次の権利です。

> 発行者の工房の村（施設）が**すでに作って倉に持っている武具**を、利用者が、**自分の鉱石と木材と引き換えに**、工房と同じ比（武具1 = 鉱石2 + 木材1）で受け取れる。範囲は、合計 N 個まで・M 回まで・期限 T まで。

| | この権利 | 違うもの（この権利ではない） |
|---|---|---|
| 何が動くか | 施設の倉の**既存の**武具と、利用者の材料 | **加工の実行**。プログラムに「工房を1回動かす」命令はない。工房は、自分の村の材料を連続で変換し続ける。この権利は、その連続生産を**一切変えない** |
| 容量 | 施設の倉にある分だけ | **将来の生産能力の予約**。「1日3回分の工房の時間」を押さえる仕組みはない |
| 在庫がないとき | 予約は `Insufficient` で失敗する。**待ち行列も待機状態もない。** Grant はそのまま残り、期限まで何度でも試せる。工房が作れば、後で成功する | 「在庫ができたら自動で実行する」は④（複数段階の実行）の側で作る |
| 期限が来たら | 新しい予約・実行はできない。開いている予約は、誰でも解放できる（両側が戻る）。予約がなければ、何も動かない | — |

名前は、コード・ABI・文書・テストで「StockSwap／交換」にそろえた。命令は ReserveSwap・ExecuteSwap・ReleaseSwap、種類は `KIND_STOCK_SWAP`。前回の「WorkshopUse／利用」という名前は、加工の実行と誤解されるので廃止した。

## 2. 定義

| 項目 | 定義（v1） |
|---|---|
| 対象施設 | 発行者の村（Holding）1つ。工房が1つ以上あること。**鍵・世代（`GEN`）・所有者**で固定する |
| 発行者 | 施設の所有者の Citizen。発行は**財布の署名だけ**（セッションは `WalletRequired`） |
| 利用者 | 別の Citizen 1人。国は問わない。**国籍だけでは、他人の施設も資源も使えない** |
| 入力の所有者と所在 | 利用者。利用者の村（受取口 = station）にある。受取口は**施設と同じ州**にあること |
| 出力の所有者と受取先 | 利用者。受取口の倉に入る |
| 回数 | `max_swaps`：実行した交換の数の上限 |
| 数量 | `max_units`：実行した武具の合計の上限。1回は 1〜10,000 |
| 期限 | `expires_ts`：発行から最大30日 |
| 予約 | ReserveSwap(units, seq)：両側を Grant の預かりへ。全部か、何もしないか。同時に開ける予約は1つ |
| 実行 | ExecuteSwap(seq)：預かりを相手側へ。確定し、返らない |
| 再送の防止 | `seq` は、Grant の実行済みの交換の数。作り直した再送（新しい blockhash なので、ランタイムは重複として落とさない）は `SeqMismatch` になる |
| 解放・取消 | ReleaseSwap（利用者。期限切れか世代切れの後は誰でも）、RevokeGrant（発行者） |
| 施設の世代 | 施設か受取口の世代・所有者・生死が発行時と違えば、使えない（`StaleHolding`）。占領の決着前は待つ（`CapturePending`） |

## 3. 資源はどこにあり、誰のもので、何に使えるか

| 段階 | 受取口の鉱石・木材（利用者の分） | 施設の武具（発行者の分） | 置き場所 | 連続生産・通常操作・他の予約に使えるか |
|---|---|---|---|---|
| 予約の前 | 受取口の倉 | 施設の倉 | 各村の倉 | 使える（それぞれの所有者のもの） |
| **予約中** | Grant の `OPEN_ORE`・`OPEN_WOOD` | Grant の `OPEN_ARMS` | **どの村の倉にもない**。Grant アカウントの数値 | **使えない。** 連続生産の入力にも出力にもならない。所有者の訓練・建設、別の Grant の予約、占領の対象にもならない（`escrow_is_outside_every_store_during_a_reservation`、`parallel_reservations_cannot_take_the_same_stock_twice`） |
| 実行後 | 施設の倉（発行者のもの。施設の工房の材料になる） | 受取口の倉（利用者のもの） | 各村の倉 | 使える。以後は普通の倉の中身として、占領などの規則に従う |
| 解放・取消の後 | 受取口の倉へ戻る | 施設の倉へ戻る | 元の村 | 使える |
| **戻し先が消えた**（解放済み・閉鎖済み） | Grant に残る | Grant に残る | Grant の数値 | **誰も使えない（凍結）。** 焼却も、別の場所への入金もしない。Grant は閉じられない（`StillLive`）。賃料も戻らない |

**預かりの法的な位置：** 予約中の資源は、どちらの側も「元の所有者に戻る約束つきで、Grant が預かっているもの」です。所有権の移転は実行のときに起こります。

## 4. 資源の保存と、損失が起こる条件

**保存（テストで確認）：** 予約・実行・解放・取消のどれでも、施設＋受取口＋預かりの合計は、資源ごとに変わりません（連続生産の分を除く）。並行した予約が同じ在庫を二度取ることはありません。片側が足りなければ、何も動きません。

**現在の規則での損失・凍結の条件（改善案とは分けて書く）：**

| 条件 | 現在の規則での結果 | 損失か |
|---|---|---|
| 戻し先の倉が上限まで満杯 | 上限を超えて入る（`Accrual::add` は上限を超えられる。settle は上限を超えた値を下げない）。その資源の、その村での追加の生産は、上限を下回るまで止まる（既存の規則） | **戻す量は失われない**（`a_return_into_a_full_store_is_kept_above_the_cap`）。追加の生産の機会は失われる（既存の規則による） |
| 戻し先の村が消えた（ReleaseDormant：所有者が10日間何もしない最初の村は、季節中でも閉じる。CloseHolding：季節の終了から72時間後） | その側は Grant に残る（凍結） | 資源は消えないが、**取り出す規則がない**。採否は未決定（`04-PROPOSALS.ja.md` §3） |
| 季節の終了 | 終了後も解放はできる（季節の状態を問わない）。村が閉じるまで（72時間）に解放しなければ、凍結 | 季節の資源は、季節とともに意味を失う |
| 実行済みの資源 | 普通の倉の中身として、襲撃・占領の規則に従う | 既存の規則のとおり |

**改善案（未採用）：** 凍結した側を、利用者や発行者の別の村、または倉（Vault）へ戻す規則。季節の終了前に自動で解放する仕組み。凍結を検知して表示する herald の feed。

## 5. ①④⑥が想定する施設利用との比較

設計文書（提案を含む）の想定：20（段階2）、21（段階3の決まり）、22（段階4のテンプレート）、26（最初の30分）、`DEVELOPMENT-HANDOFF`（国の共同作戦）。

| 想定 | 出典 | この権利で一致すること | 不足していること |
|---|---|---|---|
| 「この施設を、1日○回まで**動かせる**。材料は使う側が出し、できた物は使う側の倉に入る」（使用権の札） | 20 §2 | 材料は利用者、できた物は利用者の倉。回数・数量・期限の上限 | **加工の実行ではない**（既存在庫との交換）。**1日あたり**の回数ではなく合計。工房の時間や容量の確保がない |
| 引き換えの預かり（札を鉄で買う）、工房の又貸し・転売 | 20 §2、§4 | — | 権利の売買・譲渡はできない（grantee は固定）。代金の授受もない |
| 「鉄が届いたら工房を動かす」決まり、毎日の自動の送り（④） | 21 | 予約と実行の2段階。`seq` で再送しても安全。予約中の資源は他に使われない | 届いたことを条件にした実行は、チェーンにない（④が作る）。在庫がなければ失敗するので、④は再試行と期限を扱う必要がある |
| 「B の工房の使用権（**夜の分**）」を束ねて「夜間の前線補給」として公開。テンプレート「工房の貸し出し」（⑥） | 22 | 発行の条件（量・回数・期限）は、テンプレートの引数にできる | **時間帯**の権利がない。公開・再利用・転売がない。複数の利用者への一括発行がない |
| 運営の AI 住民が、最初から工房の貸し出しを動かす | 26 | AI 住民は自分の財布で発行できる | 財布を持つのは運営（⑤）。AI 住民のセッションでは発行できない（財布だけ） |
| 国の戦略が協力の目的を生み、各人の施設利用権を組み合わせる（北方拠点の共同作戦）（①） | HANDOFF | 国籍と無関係に、所有者の許可で使える。国が所有者に代わって発行することはできない（意図どおり） | 出力は施設と同じ州に留まる。前線へは隊商が要る。国単位の権利、複数施設の束ね、前線への届けはない |

**この交換を最初の権利にする場合の判断材料：**
- 長所：rules カーネルを変えない。Sybil で生産が増えない。予約と実行は④の部品になる。
- 短所：
  - 「動かす権利」という設計の言葉と意味が違う。
  - 同じ州の中で、隊商を使わない資源の交換経路が増える（`06-EVENTS.ja.md` §5）。
  - 時間帯・1日あたり・転売は、別の種類か拡張が要る。

## 6. 不変条件

1. **鍵：** 発行者の財布は発行だけに使う。利用者の操作は利用者自身の鍵でする。発行者の鍵やセッションでは、利用できない。
2. **範囲：** 実行した武具 ≤ `max_units`、実行した回数 ≤ `max_swaps`。予約と実行は、Active で期限前のときだけ。
3. **固定：** 施設と受取口は、記録した鍵・世代・所有者・生死と一致すること。占領ロックも確認する。
4. **保存：** §4 のとおり。戻し先が消えた場合は凍結で、消滅しない。
5. **原子性：** 全部か、何もしないか。テストでは、テスト側のロールバックで再現した。SBF での確認は未実行。
6. **偽造：** 権利アカウントは、このプログラムが所有し、大きさ・magic・季節 id が合い、自分の欄から再計算したアドレスにあるものだけを受け入れる。
7. **所有者の活動ではない：** 施設の `LAST_OWNER_ACTION` は更新しない。
8. **再送：** 実行済みの交換を、`seq` で区別する。同じ予約は二度実行できない。
