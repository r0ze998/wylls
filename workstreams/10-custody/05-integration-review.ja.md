## 3. 宛先容量の予約：守られる範囲と限界

### 3.1 何を予約し、何が守るか（コードを読んだ・確認した）

- 予約は二段：(a) 区画の `QUOTA` を倉の `CAP` に対して約束（`STORES + CUSTODY_QUOTA ≤ CAP`）、(b) 区画の中で、出発時に到着予定の量を予約（`HELD + 到着予定 ≤ QUOTA`）。
- (a) は**倉の一般在庫に書き込むすべての経路が `CAP − CUSTODY_QUOTA` を守る**ときだけ保証になる。差分のプログラムで一般在庫に書くのは3か所だけ（確認した）：SendCaravan の引き落とし、SettleCaravan の加算（上限 `CAP − CUSTODY_QUOTA` に改定）、custody の書き戻し（没収は区画の quota の範囲、預け入れの引き落とし）。倉を閉じるのは CloseVault だけで、区画があれば拒否。**新しい書き込み経路（例：⑨の成果物を倉に入れる）ができると保証が崩れる**ので、ソースを走査して書き込み箇所がこの3つであることを確かめる試験（`vault_stock_writers_are_the_listed_ones`）を足した。これは「書き方が同じ」箇所しか見つけないので、仕組みとして閉じるには ④が一般在庫への加算を一つの関数（上限つき）に集めるのがよい。
- 保証しないもの：**配達そのもの**。宛先の押収（`DestinationGone`）、襲撃（`Raided`）、焼失（`Burned`）では物は届かず、損失として記録する。容量は「届くなら入る」の保証で、「届く」の保証ではない。

### 3.2 競合の確認（確認した：モデル）

`tests/capacity.rs`（6 件）：

| 競合 | 結果 |
|---|---|
| 保管品の到着と、保管者自身の通常の隊商の到着（両方の順序） | 区画には全量、保管者の一般在庫は `CAP − quota` で止まる（超えた分は既存の上限処理で保管者自身の積荷が失われ、`credited < cargo` に表れる） |
| 輸送中に宛先の倉を閉じる・区画を閉じる・quota を到着予定未満に下げる・同じ容量を別の区画に約束する | すべて拒否（到着予定までは下げられる） |
| 出発の再送 | `Stale`、世界は変わらない（予約は一度だけ） |
| 届いた／焼かれた／奪われた／宛先が押収された | 各経路で予約がちょうど一度だけ解放される。二度目の精算・照合は拒否 |
| 襲撃が開いたまま | 結果が決まるまで予約は残り（「不明」）、DefaultRaid 相当で解決すると解放 |
| 混在の後の排出（drain） | 隊商も予約も残らず、所有者ごとの保存則が成り立つ |

`World::check` に2つの不変条件を足し、全試験の各段階で確かめている：**倉の `STORES + CUSTODY_QUOTA ≤ CAP`**、**生きている予約はそれぞれちょうど一つの隊商に対応し**（まだ保管品、奪われて照合待ち、または奪われた後に閉じた）、**二つの区画が同じ隊商を予約しない**。乱択試験（300 種 × 400 手）は最後に毎回排出し、予約の残りがないことを確かめる。変異試験に「通常の精算が quota を無視」「精算が予約を解放しない」「照合が予約を解放しない」を足し、いずれも検出（計 11 件）。

### 3.3 到着不能について（コードを読んだ）

S1 の隊商は出発時に道と宛先を検査し、途中で呼び戻し・行き先変更ができない。途中で終わらせるのは襲撃（襲撃者の決定、または DefaultRaid。道がなければ `RAID_BURN_AFTER_BELLS` 後に焼く）だけで、宛先の消失は精算時に損失になる。したがって予約が永久に残るのは「Province の鐘が解決されない」「keeper が動かない」場合で、これは通常の隊商と同じ前提（keeper の当番）に依存する。シーズン終了後も精算・照合は動く。

## 4. ⑨の Custody 契約との照合、押収の扱いの分け方

### 4.1 ⑨の契約は手元にない

この作業機から見える remote に⑨のブランチ・文書はない（2026-10-30 に `git fetch` で確認）。以下は依頼文に書かれた⑨の範囲（材料・加工中・成果物・返却物、木材と兵器）との照合で、⑨の契約文と突き合わせたものではない。

### 4.2 段階ごとの所有権（⑩が今保証すること）

| 段階 | ⑩が提供するもの | 所有者 | 足りないもの（⑨・④の決定） |
|---|---|---|---|
| 材料（預けた物） | 区画の HELD、利用注文（量・期限・目的・受け手）による予約 | 預けた人（A） | — |
| 加工中 | **なし**。ConsumeLot（または⑨の命令内の `custody::consume`）で材料は区画から出て消える | 記録上は「消費済み」。加工中の物の持ち主を表す状態はない | 数鐘かかる加工なら、加工中の物を表す記録（誰のものか、押収・失敗時にどうなるか）を⑨が定義する必要がある |
| 成果物 | **なし** | 未定 | ⑨の決定。段階2の文書（[20](../../docs/design/redesign/20-stage2-play.ja.md) §2「使用権の札：材料は使う側が出し、できた物は使う側の倉に入る」）は**提案のまま（§5 だけが採用）**で、しかも「材料は使う側」の場合。A の材料で B が加工したときの成果物の持ち主はどの決定にもない |
| 返却物（余った材料、成果物を A に返す） | 所有者自身の DepositLot だけ | — | **他人（B）が A の区画へ入れる入口がない**。DepositLot は所有者の署名と所有者の場所の一般在庫を要求する。⑨が「成果物を A の区画に返す」なら、注文の範囲で受け手が A の区画へ入れる新しい入口（`IN_TOTAL` に加える、保存則つき）が要る |

### 4.3 資源（木材・兵器）

- 現状のカーネルは `ENABLED_RESOURCES = 1 << Ore` だけ。**⑨の木材と兵器を使うデモへは接続済みではない。**
- 兵器は資源配列の `Horses` の欄にある（`permutation_rules::frontier::arms::ARMS = Resource::Horses`）。倉の `STORES`・区画の資源番号は8欄なので、木材（1）と兵器（4）を許すのは**マスクの変更だけで、口座の形は変わらない**。ただしマスクは ruleset の表に入るので `RULESET_HASH_V4` が変わる。名前の上で「Horses の欄の区画＝兵器」になる点は画面・ABI 文書で明記が要る。
- 一つの区画は一つの資源。⑨が材料2種（木材＋鉱石など）を一度に使うなら、2つの区画と2つの利用注文を一つの命令で消費する（どちらかが足りなければ全体が失敗、トランザクションの原子性）。

### 4.4 押収の扱い：参照した決定の範囲と、⑩の適用判断を分ける

| | 内容 | 状態 |
|---|---|---|
| 採用済みの決定（2026-10-23、[20](../../docs/design/redesign/20-stage2-play.ja.md) §5 の1行目） | 「倉が奪われたら、その倉の**持ち分の札と受け取りの札**は無効。中身は奪った側のもの」。対象は**段階2の札**（共有の倉の持ち分、倉の持ち主が出す受け取りの約束）。段階2は未実装 | 採用済み（ただし札が対象） |
| J2・S1 §3.6 | 奪った隊商は襲撃者のもの、押収した倉の中身は押収者のもの（倉の持ち主の一般在庫として） | 採用済み・実装済み |
| **⑩の区画への適用** | 区画（一人の所有者の物を他人の倉で保管する新しい区分）にも、押収で同じ結果（区画は没収、中身は押収者）を当てはめた | **⑩の判断（提案）。決定ではない** |

⑩がこう判断した理由：区画だけ押収に残ると、倉の持ち主自身の物より他人に預けた物の方が安全になり、「安全な倉庫」の例外になる。別案（押収後も区画を所有者のものとして凍結し、押収者は引き出せない／所有者が期限内に運び出せる、など）は所有者の判断に回す（[03](03-rules-and-conflicts.ja.md) §5）。

### 4.5 利用者向けの説明（二つを分ける）

1. **保管者は区画に手を出せない（仕組み）**：あなたが他人の倉に預けた物は、倉の持ち主の在庫とは別の帳簿にあり、倉の持ち主は売る・使う・送る・別の人に貸すことができません。あなたが許可した人だけが、許可した量・期限・行き先・目的の範囲で運ぶ・使うことができます。倉の持ち主は、預かり品があるうちは倉を閉じられません。
2. **戦闘では持ち主が変わる（ゲームの規則）**：倉が敵に奪われる（押収）と、預けた物もその倉の中身として奪った人のものになります。運んでいる途中に隊商が襲われ「奪う」を選ばれると、積荷は襲った人のもの、「焼く」を選ばれると失われます。行き先の倉が途中で奪われると、届かずに失われます。いずれも記録に残ります。預け先を選ぶことは、その倉の守りを信用することです。（2 の押収の扱いは現在⑩の提案で、決定待ち）
