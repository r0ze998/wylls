# 08 ④との送信記録の保持契約（2026-11-05、提案。④の採否待ち）

⑬の住民は、送信ごとに手順から決まる冪等キー（`<住民>:t<ターン>:<n>`、約束の返送は `<住民>:return:<依頼>`）を使い、二重送信の防止を実行側（④）のキーの記録に頼っている。この文書は、住民が④に求めることと、住民の側が守ることを定める。試験は `test/retention.test.mjs` と `test/uncertain.test.mjs`。

## 1. ④に求めること

| 項目 | 内容 |
|---|---|
| R1 保持期間 | キーの結果（受理・着地・失敗・取消、署名）を、**結果が確定してから少なくとも 1 ゲーム日（144 ターン）**、`status(key)` で同じように答え、同じキーと同じ本文の `submit` には記録済みの結果を返す（再実行しない） |
| R2 宣言 | 実行ポートは保持期間を `retentionBells` で宣言する。宣言がない、または 144 未満のポートは、住民が最初の手番で拒否する（`assertPort`） |
| R3 忘れたキー | 保持期間を過ぎて忘れたキーで `submit` が来たら、**実行せず** `KeyExpired` で拒否する。忘れたキーを新しい行動として実行してはならない |
| R4 未確定 | 結果が分からないときは `fate: 'unknown'` を返す（④の executor の `unknown`）。住民はこれを再送の理由にしない |
| R5 記録なし | `status(key)` が `null` を返すのは「このキーを受理した記録がない」ときだけにする。一時的に答えられないときは例外を投げるか `unknown` を返す |

## 2. 住民の側が守ること（実装済み）

| 項目 | 内容 |
|---|---|
| S1 キーを作り直さない | 一度終えた行動のキーを作り直さない。約束の返送は、掲示板が「返済済み」とするか一覧から消えるまで返送済みの目印を消さない（以前は1ゲーム日で消え、返送義務が作り直されていた） |
| S2 新しいキーを使わない | 応答が失われた送信は、元のキーのまま照会し続ける（統合候補 f637c7a）。`#a2` などの新しいキーは、④が**失敗を確定**した場合にだけ使う |
| S3 同じキーでの再送 | ポートが「記録なし」と3回答えた失われた送信だけを、**同じキー**で再送する。保持期間内（最後の送信から `retentionBells` 未満）に限り、最大 `maxRetries` 回。④の `unknown` は再送しない |
| S4 行動回数 | 1キーにつき1回、受理（または受理されたかもしれない曖昧な応答）を初めて見たときに数える。行が作られる前から記録されていた送信は数えない |
| S5 未確定のまま | 1ゲーム日確定しない行は `unresolved` として残し、`owed()` で報告し、同じ行動を選ばない。後から確定すれば決着する。照会は 1, 2, 4 … ターン（最大 36）と間を空ける |

## 3. 回帰試験で確認したこと（模擬世界、2026-11-05）

- 保持期間の最小値（144）で鍵を忘れ、忘れたキーを**再実行してしまう**最悪の実行ポートに対して：襲われた返送は4日間で1回だけ支払われる。再起動をはさんでも1回。行動回数は送った日の1回だけ。
  - 修正前（`41e212cb`）は同じ試験で2回支払った（期待1、実際2）。
- 支払いが届いた返送は、掲示板が決着させた時点で目印が消え、以後作り直されない。
- 宣言が143以下、または宣言なしのポートは、何も送る前に拒否される。
- 失われた送信は同じキーで再送され、1回だけ着地し、行動回数も1回。④の `unknown` は再送されず、確定した時点で着地として決着する。
- 1ゲーム日以上確定しない行は `unresolved` になり、再起動後も残り、後から確定する。
- 保持期間を過ぎた失われた送信は再送されず、`unresolved` になる。
- 以上5件の未確定の試験は、変更前（`19c971ce`）ではすべて失敗する。

## 4. 未決（④の判断）

- R1 の 1 ゲーム日で足りるか（住民の停止・障害がそれより長い運用では、住民は保持期間外の再送をしないため `unresolved` が残る）。
- R3 の `KeyExpired` と R5 の `null` の意味分けは、④の現行 executor（ws04 `a967f5f1` の `intent/sent/unknown/rejected`）にそのまま対応するか未確認。
- `unresolved` の最終処理（運営が着地・失敗を決める手順）は④または運営の担当。
