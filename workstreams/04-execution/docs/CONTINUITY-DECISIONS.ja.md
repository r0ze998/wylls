# 継続世界の実装方法：判断のための資料（④、2026-10-31）

**決定済み**：世界は継続し、シーズン終了で世界・所有・輸送・進行をリセットしない。

**この資料で扱う未決事項**：その実装方法（共通方針）と、program の変更案 P-C1〜P-C4。どれも採用されていない。ここに書いた変更は、どれも当てていない。

根拠の行番号は、統合ブランチ（基準 `4cd901de`）のコードで④が確認したもの。⑯⑰の報告で④が再確認した点は、その旨を書いた。

## 1. 共通方針の案

④が統合担当として一本化したい規則。program と各担当の実装の両方を縛る。

### 1.1 世界の識別子

| 案 | 内容 | 既存データ | 評価 |
|---|---|---|---|
| **W1（推奨）** | 今動いている Season の口座を「世界の口座」として固定し、二度と新しく作らない。名前の `season_id` は世界の id として残す | 住所が一つも変わらない。移し替えは不要 | 変更が最も小さい。名前に Season が残るのは、移行上の理由である |
| W2 | 新しい World の口座を作り、全口座をその下へ移す | 全口座の移し替え、署名、rent、索引の作り直しが要る。移す途中の取引の扱いが難しい | 利点に比べて危険が大きい |
| W3 | シーズンを続けて作り、中身を次へ持ち越す | 毎回、全口座の住所が変わる | 「リセットしない」という決定に反する |

**採らない場合**：識別子が決まらないまま、各担当が別々に World／Period の正本を作り始めてしまう（⑪⑮は既に `epoch` を前提に写し替えを設計している）。

### 1.2 世界の状態

- 継続モードの世界には「終わる」状態を持たせない（実装は P-C1）。
- 旧版の Season（Ended／Closed）は、旧版の証拠として読む。書き換えず、新版の証拠に読み替えない。

### 1.3 戦期

- 世界とは別の口座、または外からの入力にする（P-C4）。
- player の操作は戦期を見ない。
- 周期・集計・配分は決めない。

### 1.4 時刻・番号・保存量

- bell は u32 で、600 秒なら約 81,000 年ある。足りる。
- 番号（seq など）は世界の中で単調に増やし、戻さない。
- 記録の保存は、増え続けてもよい履歴（log、索引）と、閉じる口座（rent が戻る）に分ける（P-C3）。

### 1.5 版と証拠

- program version と ruleset hash は、registry（`contracts/registry.txt`）に一本化する。
- 規則の版の切り替えは、戦期の切り替えと結び付けない（⑪の要件）。
- 旧版の記録は、旧版の規則で再検証する。

### 1.6 実行経路と認可

- AUTH-ROUTES の推奨（送り手ごとの capability、session key の署名は gateway に一本化し、Citizen ごとに一列で処理する）。
- 有効期限と予算の上限は、世界が続いても永久化しない（⑤の方針）。

### 1.7 off-chain の識別子

- relay・keeper・herald・UI の鍵、invite、署名文の season id は、W1 の世界の id として固定する。
- 戦期の番号は別の欄にする。

**推奨**：1.1 は W1。1.2〜1.7 も上のとおり採用する。

**採らない場合の支障**：
- 担当ごとに識別子・時計・番号の前提がずれる。
- ⑮は bell が期ごとに 0 に戻る前提で、④は戻らない前提である。結果として、照合が成り立たない。

## 2. P-C1：継続モードの印（世界を終わらせない）

**内容**
- Season の予約領域（F8）に、1 バイトの `WORLD_MODE` を置く（0 は旧版、1 は継続）。
- authority だけが使える一方向の命令（例：`SetContinuing`）で 0 から 1 にする。1 から 0 には戻せない。Running で、かつ `bell < end_bell` の間だけ受け付ける。
- 継続モードでは、次をやめる：
  - player の処理の前提にある `bell < end_bell` の検査（F2）
  - EndSeason（拒否する）
  - bell の解決・beacon・anchor の `end_bell` による打ち切り
  - 進軍の到着の上限
  - 包囲の完成の上限
  - reveal の終了による判定
- `end_bell` は継続モードでは読まない。F3 の上限は旧版の作成のために残す。

**必要な理由**：F2・F3・F4。`end_bell` を大きくする方法は F3 で取れない。世界を続けるには、program の挙動を変えるしかない。

**変更対象**

| 区分 | 場所 |
|---|---|
| ABI | `frontier-abi`：layout（新しい欄）、tags（新しい命令の番号。registry で採番）、`prologue.rs:1066-1068` |
| program | `proc/season.rs`（`end_season`、新しい命令）、`clash.rs:442-448`（`in_season`）、`beacon.rs:192,240`、`host.rs:652-657`、`conquest.rs:785-793,1006-1012,1617,1711`、`reveal.rs:761` |
| off-chain | stack・keeper の EndSeason の自動送信（`stack/src/up.rs:1643-1667`）、keeper の `end_bell` による打ち切り（`beacon.rs:188-193`、`play.rs`、`reveal_accept.rs`）、herald の `ended`、agents・bots の `end_bell`、UI の「終了」、verifier の V20 |

**既存データと未完了の取引への影響**

| 対象 | 影響 |
|---|---|
| 旧版のシーズン（印 0） | 挙動は変わらない |
| Running のシーズンを `end_bell` より前に 1 にした場合 | 口座・住所・所有はそのまま。移動中の隊商と進軍は、bell が解決され続けるので普通に精算される（F4 の詰まりが起きない）。予約・加工・預かりもそのまま進む |
| 既に Ended のシーズン | 戻せない。`end_bell` 以降の bell は未解決のまま、終了から 72 時間後には誰でも口座を閉じられる。「蘇らせる」かは別の判断で、④は勧めない（旧版として扱い、受取権を P-C3・P-C4 で守る） |
| 賞金の pool | 印を 1 にしたシーズンの pool は、永久に Ended にならない。入金に出口が無いまま（D2）になる → P-C4 の (a) が要る |

**推奨**：採用する。四つのうち最初に必要な、最小の核である。

**採らない場合の支障**
- 世界は最長 28 日で止まる。
- 終了をまたいだ隊商は、物資を積んだまま永久に道に残る。
- 続けるには新しい Season を作るしかなく、それは F1 によりリセットになる。決定済みの方向と両立しない。

## 3. P-C2：継続モードでは参加を締め切らない

**内容**
- 継続モードでは `join_close_bell` の検査（F5）をやめる。
- join gate（x402・invite）による参加の制御は残す。参加費・参加証（NFT）は別に決める。
- keeper の fold（`keeper/src/fold.rs:64-72`。今は締め切りまで動く）と、relay の利用枠（今は genesis から 7 日間だけ多い）を、参加した日から数える。

**必要な理由**：F5。シーズンの 75% の時点（preset では 3,024／4,032 bell）で、新しい人が入れなくなる。

**変更対象**：`proc/citizen.rs:321-349`、`keeper/src/fold.rs`、`agents/src/profile.rs`、`permutation-gateway/src/frontier/quota.mjs`、UI の文言（「入植受付は終了しました」）。

**既存データと未完了の取引への影響**
- 既存の Citizen への影響は無い。
- JoinShard の人数の欄は増え続ける（u32）。shard の数は作成時に固定なので、容量の確認が要る（未確認）。
- 有料の参加（Pay＋Join）は、P-C4 の (a) を決めるまで、入金が出口の無い金庫に入り続ける。**参加費を取るかどうかは P-C2 と切り離す**（毎戦期の買い直しや参加費を前提にしない）。

**推奨**：P-C1 と同時に採用する。ただし、有料の参加を開くのは P-C4 の (a) の後にする。

**採らない場合の支障**：継続する世界に、後から誰も入れない。

## 4. P-C3：口座の後始末を、終了ではなく経過と完了で行う

**内容**（二段階）
1. **守り（先に入れる）**
   - 継続モードでは、「終了から 72 時間後なら誰でも閉じられる」経路（F6）を使わない。
   - Citizen は本人の wallet だけが閉じられる。次のどれかが残っている間は閉じられない：Holding、移動中の輸送、預かり、未受取の賞金の Entry。
   - D3 への対処として、次のどちらかを決める：
     - (i) 受取の資格（国）を、確定の時点で pool 側に記録し、Claim が Citizen を読まないようにする（prize program の変更）
     - (ii) 未受取の Entry がある間は CloseCitizen を拒否する（program をまたぐ検査が要る）
   - ④は (i) を勧める。
2. **回収（後から入れる）**
   - 次のものを、対象の bell の解決・精算・請求の期限の後に、猶予を置いて閉じられるようにする：進軍の記録（精算・畳み込みの後）、AnchorArchive・RingSeed・DefenceClaim（対象の bell をすべて解決し、請求の期限が過ぎた後）。
   - Holding は今の休眠の解放（`release_after_secs`）を使う。ただし今の値は季の長さに合わせてあるので（⑯の報告）、値を見直す。

**必要な理由**
- F6 のままでは、継続する世界でこれらの口座と rent が際限なく増える。AnchorArchive は region ごと・半日ごとに 1 口座で、16 region なら 1 日 32 口座、1 年で約 11,700 口座になる。
- 去った人の rent が戻らない。
- D3：受取権が後始末で消える。

**変更対象**：`proc/conquest.rs:1750`（CloseMarch）、`season.rs`（CloseSeason の part 8〜10 を個別の close にする）、`citizen.rs`（CloseCitizen・CloseHolding の条件）、`permutation-prize/src/lib.rs`（(i) を選ぶ場合）、keeper の close の役割、verifier（閉じた口座の代わりに記録を読む）。

**既存データと未完了の取引への影響**
- 旧版のシーズンは、今の規則のまま。ただし D3 の危険が残るので、旧版の pool の受取が済むまで、後始末を送らない運用が要る（program を変えなくてもできる）。
- 継続モードでは、close の条件に「まだ読む処理が残っていない」ことを口座ごとに入れる。精算の前の輸送、請求の期限内のもの、未受取の Entry がこれに当たる。条件を誤ると、精算や請求に要る口座を消してしまう。そのため、各 close に試験を付ける。
- 閉じた口座の中身は、log と索引に残る。過去の履歴を書き換えることにはならない。

**推奨**：第一段（守り）を P-C1 と同時に採る。第二段（回収）は、長期運用の前に入れる。

**採らない場合の支障**
- 口座と rent が増え続ける。
- 去った人の預け金が戻らない。
- 旧版でも受取権が消えうる（D3）。

## 5. P-C4：戦期を世界から分ける

**内容**
- **(a) 既存の pool の出口（急ぐ）**：継続モードにしたシーズンの pool が、永久に Ended を待たないようにする。例：authority の命令で refund モードの確定を許し、Entry だけで受け取れるようにする。案は複数あり、配分は未決のまま。
- **(b) 戦期の口座（器だけ）**：世界の口座の下に `WarPeriod{index, start_bell, end_bell, params_hash, status}` を置く。player の操作は読まない。集計と賞金だけが読む。中身（周期・集計・配分）は決めない。
- **(c) 集計の凍結（設計が要る）**：今の Tally は「`end_bell` の後はどの bell も解決されない」という凍結に頼っている（`permutation-prize/src/lib.rs` のモジュール文書）。世界が続くと、戦期の終わりの後も州の持ち主は変わる。境界の時点の写し（Province に戦期の境界の持ち主を記録する、など）が要る。

**必要な理由**：F7（D2・D3）。賞金と集計が「世界の終了」に結び付いたままでは、継続する世界で戦期を区切れず、預かった参加費も出せない。

**変更対象**：`frontier-abi`（layout・tags）、program（戦期の命令、Province の写しの欄）、`permutation-prize`（pool の seed を戦期ごとにする、Tally・Finalize の条件、(a) の出口）、herald（`final.json` を戦期ごとにする）、UI（戦期の集計と世界の継続を分けて表示する）、⑮の評価器（外からの入力を、この口座から読む形にする）。

**既存データと未完了の取引への影響**
- 既存の pool（シーズン単位）は旧経路として残す。今の受取（受取額の一致を④の試験で確認済み）は変えない。
- 継続モードにしたシーズンの pool は、(a) が無ければ入金が閉じ込められる。
- (b)(c) は新しい口座を足すだけで、既存の口座を書き換えない。

**推奨**
- (a) は、継続モードに切り替えるシーズンに有料の入金がある場合、P-C1 と同時に必要。入金が無いシーズンから切り替えるなら不要。
- (b)(c) は今は採用しない。戦期の規則が決まってから設計する。それまで戦期は、⑮のように外からの入力として扱う（表示と評価だけで、オンチェーンの配分はしない）。

**採らない場合の支障**
- 継続する世界では、オンチェーンの賞金を一切配れない。
- 継続モードのシーズンの入金は出られない。
- 戦期の集計は off-chain の評価だけになる。

## 6. 順序、検証、承認が要ること

| 段 | 内容 | 必要な承認・環境 |
|---|---|---|
| 1 | 共通方針 W1 と 1.2〜1.7 を決める | 方針の判断 |
