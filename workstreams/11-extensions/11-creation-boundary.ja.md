**照合の対象。** ⑥の公開済みブランチ `preserve/ws06-creation-517796dc`（commit `517796dce6dec5c1496775d73ad84a0cb8befa09`）。⑥の補遺（ADDENDUM-20261030）はこの commit に入っておらず、GitHub 上で読めなかった。補遺が commit の文書より優先する点（回数制限の層、StockSwap）は、この対応表の範囲（識別・署名・状態・引数）には関わらない。

## 3. 対応しない部分（近い意味に寄せず、名指しで拒否）

| ⑥ | 理由 |
|---|---|
| `steps[].effect`（`caravan.send`、工房の手順など既存の命令） | ⑪の効果の語彙（effect set 1）に命令を呼ぶ op がない |
| `limits.runsPerDay`（1 日に受理された開始の数） | ⑪の Grant の `calls_left` は累計で、日ごとではない |
| `validUntilDay`（作者の期限） | ⑪の Grant の `expires_ts` は利用者の期限 |
| 場所・札・成果の型の `params`（vault、workshop、grant:*、result:*） | ⑪の引数は整数だけ |
| 公開状態 | ⑪の実行状態とは別系列（⑥の回答どおり） |
| 内容ハッシュ（正準 JSON）と `manifest_id`（正準 byte 列） | 別の識別。相互参照は⑥側の新しい契約案で、決めていない |

**⑪ → ⑥:** ⑪の op（`Pay`、`Refund`、`Burn`、状態の欄）はすべて新しい世界効果（⑥の区分 D、`EFFECT_UNKNOWN`）なので、`eleven_to_creation` は全体を拒否する。

⑥の公開済みの 4 定義（`front-supply`、`mine-delivery`、`front-supply-river`、`plain-caravan`）はどれも手順が既存の命令なので、⑪は**識別と引数の範囲を読めるが、実行はできない**（`k08`）。

## 4. 契約試験（`creation-bridge/tests/contract.rs`、10 件）

試験の期待値は⑥自身のコードで作った（`creation-bridge/vectors/gen.mjs` が⑥の `src/` を import して出力。⑥の鍵は⑥のリポジトリにある公開のデモ用シード）。

| 試験 | 確かめること |
|---|---|
| `k01` | 期待値が⑥ `517796dc` のものであること、署名の領域名 |
| `k02` | 正準形とハッシュが⑥と一致（⑥の 4 定義、キーの順＝UTF-16 単位、文字列のエスケープ、`-0`・`1e2`・安全な整数の上限、深さ 32）。⑥が拒否する数（1.5、2^53、1e300）は⑪も拒否 |
| `k03` | 公開の封筒が通る。中身・ハッシュ・作者・署名の 1 byte のどれを変えても通らない。公開の署名は状態変更の領域では通らない |
| `k04` | ⑥の登録簿の書き出しを読み、⑥の状態（取下げ・掲載）をそのまま得る |

| `k07` | 状態変更の署名（⑥が書き出しとは別に渡した場合）が、署名された順番・状態でだけ通る |

| `k09` | 物の名前とコアの枠・単位（`arms` ＝ `ARMS` の枠、×1,000、範囲外・負・小数・知らない資源は拒否） |

## 5. ⑥に伝えたい観察（⑥への依頼ではない）

1. **状態変更の署名が書き出しに残らない。** `Registry.toJSON()` の `statusLog` は `{status, day, seq}` だけで署名を持たない。第三者は「停止された」ことは読めても「作者が署名した」ことを確かめられない（⑪は署名が別に渡されれば確かめられる: `verify_status_change`）。
2. **公開項目と状態変更の項目の形が違う。** 公開は `{status: "listed", day, version}`（`seq` なし）、状態変更は `{status, day, seq}`。⑪はこの形の違いを前提に検査している。⑥が形を変える場合は契約試験を作り直す。
3. **重複キー。** `JSON.parse` も serde_json も後勝ちなので、両者のハッシュは一致する。ただし正準形を作る前の JSON の文字列としては別物になりうる。
