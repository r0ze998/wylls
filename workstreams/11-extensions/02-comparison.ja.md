# 02 三案の比較と推奨

**読み方。** 「事実（実行）」はこの作業機で動かした結果、「事実（コード）」は基準 commit `4cd901de` か一次資料のコードを読んだ結果、「計算値」は一次資料の式で計算しただけの値、「未測定」は確かめていない値。Solana の数値の出典は [10-research](10-research.ja.md) §0（Agave v3.1.9 のソース）。

## 1. 三案

| | A 既存命令の合成（基準） | **B 宣言型の効果（推奨）** | C 外部プログラム接続 |
|---|---|---|---|

## 2. 比較

| 観点 | A 合成 | B 宣言型 | C 外部接続 |
|---|---|---|---|
| **作れる機能** | 74 命令の組合せ・自動化・委任（session の範囲内）。③ `t12`（委任送付） | 利用者ごとの新しい状態機械: 時間で解ける預かり、回数・称号、条件つき返却、消費（[03](03-prototype.ja.md) の「見張りの誓い」） | 任意の計算・ループ・自前の状態・利用者間の市場（自分の口座の中で） |
| **作れない機能** | コアにない状態・規則すべて。③ `t11`：迂回できない | 利用者をまたぐ作用（v1 の op は呼出し者自身の Holding と状態だけ）、資源の発行、ループ、他の口座（Province など）の読取、乱数 | コア資源・コア状態への直接の書込（権限降格が要る。下記）。コアへの書戻しは再入禁止で不可 |
| **新しい状態遷移** | **なし**（部分集合） | **あり**（コアの解釈器の範囲内） | あり（ただしコア資源に効く部分は結局コア側の規則＝B が要る） |
| **Solana の制約** | CPI は 5 段まで（トップ＋4）、13 命令は `top_level_only`、読取／書込の宣言の衝突で同一取引に入らない組がある（③ [03](https://github.com/r0ze998/wylls/blob/2f8ec700/workstreams/03-composability/03-composition.ja.md)）、CPI 先の ProgramData も読込量に数えられる（③ drill、約 1.74 MB） | CPI なし→再入・深さの問題なし。**取引 1,232 B** なので 1,024 B の manifest は 1 取引に載らない（分割書込が要る。下記 §4） | 再入禁止（A→B→A は `ReentrancyNotAllowed`）、深さ 5（SIMD-0268 は mainnet 未有効）、hook の CU と ProgramData の読込量は呼出し側の取引の予算に入る |
| **費用** | courier 経由で SendCaravan +6,214 CU（署名）／+11,318 CU（委任）（③ 実測、LiteSVM）。外部プログラムの配置 rent は作者負担 | manifest 口座 1,024 B 上限で rent 免除 8,463,360 lamports（計算値、作者負担）。利用者ごとの状態 240 B で 2,561,280 lamports（計算値、利用者負担）。**解釈の CU は未測定**（SBF ビルド不可、[00](00-context.ja.md) §4） | hook の CU は呼出しごとに利用者の取引の予算から出る。上限は作者次第（未測定） |
| **検証** | 再生検証器はトップレベルの Frontier 命令しか集めない（③ patches/0002）。CPI の作用は判定されない | 同じ純関数（`exec::run_entry`）を検証器が再実行。SBF VM は不要。未知の語彙は UNVERIFIABLE（事実（実行）：`v03`） | 検証器が第三者の `.so` そのものを SBF VM で再実行する必要がある。`.so` が手に入らなければ UNVERIFIABLE |
| **更新・停止権限** | 外部プログラムの upgrade authority が意味を黙って変えられる（authority を None にすれば不変、[10](10-research.ja.md) §0）。**コアはその外部プログラムを止められない**（CPI 呼出し元の許可表がない） | 内容の SHA-256 が識別子。更新＝新 id、利用者の許可は旧 id に固定（`r04`）。作者・運営が停止／取消、利用者は出口で預かりを戻せる（`r06`） | 外部プログラムの upgrade authority が残る。コアが ProgramData の `slot` を記録して照合すれば「変わったら拒否」はできる（未実装・案）。止めるにはコア側の許可表が要る |
| **コア資源の発行・消費** | コアの規則そのもの | `Pay`/`Burn` は `Holding::pay`、`Refund` は預かり分だけ `Holding::credit`。発行の op はない（`r09`、`f03`） | コアが要求ごとに規則を当てる必要がある（＝B の効果の語彙を外部向けに開くことになる） |
| **任意コード** | 作者のコードは作者の口座の中だけで動く | **実行しない** | コアの取引の中で第三者のコードが動く |
| **共有コアへの変更** | なし（検証器の修正は要る） | 命令 5 個、口座 3 種、解釈器（[patches/0002](patches/0002-core-extension-instructions.md)） | hook の呼出し点と権限降格、許可表、`.so` の版固定 |

## 3. 推奨: B（宣言型の効果）

理由:

1. **本当に新しい状態遷移を足せる唯一の案で、作者のコードを実行しない。** A は③が示したとおり部分集合にとどまる。C は新しい状態を持てるが、コア資源に効かせる段階で「コアが許す効果の語彙」が要り、結局 B の語彙を外部に開くことになる。
2. **検証の約束（README「A verifier can replay a season's transaction log」）を保てる。** 検証器が同じ純関数を再実行するだけで、第三者の `.so` と SBF VM を持つ必要がない。
3. **版の固定が識別子そのもの。** 先例（BOLT・MUD・Dojo）はいずれも authority が差し替える方式で、内容ハッシュで固定する先例は見つからなかった（[10](10-research.ja.md)）。B なら仕組みとして「作者の更新で利用者の意味が黙って変わらない」。
4. **Solana の制約のほとんどを避けられる。** CPI を使わないので深さ・再入・CPI 先の読込量の問題がない。

B の代償（採用前に判断が要る、[06](06-adoption.ja.md)）:

- **語彙の外のことは作れない。** 作者は「コアが用意した op」の組合せしか書けない。語彙を増やす（effect_set 2）たびにコアのアップグレードと検証器の更新が要る。新しい effect_set を知らない旧検証器は UNVERIFIABLE を返す（`v03`）。
- **解釈器はコアの一部になる。** 解釈器のバグはコアのバグ。コアのアップグレード権限者が解釈器の意味を変えられる（effect_set の番号で区別するが、同じ番号の中身を変えないことは運用の約束）。
- **利用者をまたぐ機能（交換・共同作業）は v1 にない。** 1 人の状態と Holding だけを扱う。2 人以上を扱うには、相手の同意（Grant）を同じ取引で確かめる op が要る（effect_set 2 の候補、未設計）。

## 4. Solana 上で B を置くときの制約（コードを読んだ結果と計算、未実行）

| 項目 | 内容 |
|---|---|
| 取引の大きさ | 1,232 B（`PACKET_DATA_SIZE`）。署名 65 B、ヘッダ 3 B、口座 6 個（Frontier・compute budget・署名者・Season・登録口座・System）192 B、blockhash 32 B、compute budget の前置き約 40 B、命令の枠約 10 B を引くと、1 取引で書ける manifest は約 890 B まで（計算値）。上限 1,024 B のままなら、BPF loader の Buffer と同じく **分割書込（Write(offset, bytes)）→ 確定（Publish）** の 2 段にする。例の「見張りの誓い」は 438 B（事実（実行）：`examples/sizes.rs`）なので 1 取引に載る |
| 口座の増加 | 1 命令の realloc は 10 KiB まで。manifest・状態とも固定長で作成時に確保するので該当しない |
| CU | Holding の決済（`Holding::settle`）が支配的と見込む。SendCaravan 全体で 27,809 CU（③ 実測）。解釈器の 32 op × 定数時間の上乗せは**未測定** |
| 時刻 | `Clock::unix_timestamp` をコアが `now_ts` として渡す。それ以外の外部入力はない |
| 版 | Season の `PROGRAM_VERSION` と `RULESET_HASH` を manifest の `core` と照合（`r05`）。不一致は `CoreVersion` |
