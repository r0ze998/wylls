# 4. D：新しい種類の世界効果をどう扱うか

**決定（2026-10-30、あなたの判断）：** 新しい世界効果は、当面コア側だけが追加する。「上限つきの効果の雛形」（下の選択肢2）は将来の検討案として残し、今回は実装を広げない。任意コードの実行は本番に入れない。

**この試作がしていないこと：** 任意コードの実行、利用者が新しい効果を登録する仕組み、雛形の実装。検証器は表にない効果をすべて拒否する（`EFFECT_UNKNOWN`／`EFFECT_FORBIDDEN`）。

## 1. 区別

| | 何が増えるか | 世界に新しい作用が生まれるか | この試作 |
|---|---|---|---|
| A 定義を写す | 定義の写し | いいえ。写しても札・物・署名・記録は増えない | 動く（`fork.mjs`） |
| B 施設に接続する | 利用者自身の札による接続 | いいえ。施設の持ち主が出した札の範囲で、既存の命令を使う | 動く（実行前の確認まで。実行は模擬） |
| C 成果を使う | 配達で届いた物の束（消費する権利）の消費。記録は出どころの証明で、消費されない | いいえ。物はすでに倉にある | 動く（台帳・束・実行は模擬） |
| D 新しい世界効果 | 新しい命令・規則 | **はい** | 分類と比較だけ。追加はしない |

**A だけで B〜D ができたとは言わない。** 写しは定義の文章と構造の写しで、写した人は元の作者の札も倉も使えない（`test/required.test.mjs` 10、`test/abcd.test.mjs`）。

## 2. 分類：既存命令の合成でできるもの／コアの拡張が要るもの

基準は「S1（main）か S2（未統合ブランチ）の命令の並びで書けるか」。S3（決まりの自動実行）は決定済みだが未実装なので「拡張が要る」に入れる。

| 作りたい仕組み（設計文書の例） | 分類 | 使う命令・足りないもの |
|---|---|---|
| 定期配送（手で毎回出す） | 合成（S1） | `caravan.send` |
| 工房の貸し出し・他人の工房で作る | 合成（S2） | 発行は `IssueTickets`、受け渡しは `OpenEscrow`/`AcceptEscrow`（定義の外の準備）、実行は `workshop.run` |
| 軍需組合（持ち分で分配） | 合成（S2） | `OpenShares`・`WithdrawShares`・`workshop.run`・`caravan.send` |
| 先渡し・新参への投資 | 合成（S2） | 受け取りの札（`IssueTickets` kind 2）、`receipt.withdraw` |
| 鉱山の便の成果を工房で使う（C） | 合成（S1+S2） | `caravan.send` の記録 → `workshop.run`（この試作の例） |
| 保険（二つの組合の札を持つ） | 合成（S2）。ただし「片方が襲われたら自動で他方から」は拡張 | 札を持つのは合成、切り替えは S3 |
| 毎日6時・在庫が下回ったら・届いたら自動 | **拡張**（S3 決定済み・未実装） | 決まりの判定と実行（`trigger.schedule`） |
| 仕組みの持ち主の札・手数料の自動受け取り | **拡張**（S4） | 新しい札の種類（`owner.ticket`、`fee.collect`） |
| 出しっぱなしの申し出（市場・関所） | **拡張**（決定済み・S2 の預かりは1対1） | `escrow.standing` |
| 新しい変換（例：食料→携行食） | **拡張**（規則の数値と指紋が変わる） | `recipe.custom` |
| 荷車を通さずに物を動かす | **禁止**（16 §2「運ぶには時間がかかり、襲われうる」） | `goods.teleport` |
| 物を無から増やす | **禁止**（16 §2「無から増えない」） | `goods.mint` |
| 軍の自動進軍・攻撃 | **禁止**（21 §5、99 の塔の線引き） | `march.auto` |
| 隠れた情報（移動中の軍）を合図にする | **禁止**（21 §2） | `signal.hidden` |
| 任意コードの実行 | **禁止**（この課題の制約） | `code.run` |

この表は `src/catalog.mjs` の `EFFECTS`（合成に使える）と `NOT_COMPOSABLE`（拡張・禁止）に対応し、`test/abcd.test.mjs` が全項目を検査する。

## 3. 拡張の入れ方の比較（許可対象・上限・互換性・更新権限）

| | 1. コアだけが足す（今の進め方） | 2. 型つきの効果の雛形（上限つき） | 3. 利用者のコード（サンドボックス） |
|---|---|---|---|
| 中身 | 新しい命令を ABI・program・検証器・herald・web に足し、コアの新しい版として出す（MAINTENANCE「Adding a conquest instruction」、S2 の L9。当時は新しいシーズンで出す前提だったが、2026-10-31 にシーズン制を廃止。動いている世界への入れ方は④の移行が決める。docs/10） | 運営が「変換」「条件つき送り」など少数の雛形を命令として持ち、利用者はその **数値の範囲内の組み合わせ** を登録する（例：材料と製品の組を、価値の換算表で増えない範囲に限る） | 利用者が WASM などのコードを登録し、命令の中で実行する |
| 許可対象（誰が足せるか） | 運営（あなたの判断） | 誰でも登録できるが、雛形の型と範囲は運営が決める。登録は国の投票で承認する案もある | 誰でも |
| 上限 | 命令ごとの CU 予算・取引の大きさを ABI で固定（`budgets.rs`） | 雛形ごとに CU・入出力の数・換算表の範囲を固定。検証器の再計算も雛形ごとに書ける | コードの計算量を計量で縛る必要。チェーンの CU 上限（1.4M/取引）の中で、検証器が同じ計算をやり直せることが必要 |
| 互換性 | 規則の指紋が変わる（J5・L9）。世界は作り直さず、④の移行で入れる。意味の変わった効果を使う採用済みの計画は、利用者が確認し直すまで保留（docs/10 §2） | 雛形そのものはコアの版で入れる。登録された組み合わせはデータなので、コアの版を変えずに増やせる | コードの版ごとに検証器の判定が変わる。改ざん検出（tamper）の作り方が定まらない |
| 更新権限 | 運営。決定ログに記録 | 雛形：運営。登録された組み合わせ：登録者（版は⑥の規則で固定、既存の札の条件は変えない） | 登録者。既存利用者を壊さないための版の固定が必須 |
| 守れるもの | 世界のルール（16 §2）をすべて守れる | 「無から増えない」を換算表で、「運ぶには時間がかかる」を荷車の雛形で守れる | 守れることを機械で示しにくい |
| 費用 | 命令1つごとに、検証器・herald・web まで（17 の「検証ツールの手間」） | 雛形1つごとに同じ手間。登録ごとの手間はない | 一度は大きい。安全の確認は終わらない |
| 扱い（2026-10-30） | **採用：当面はこれだけ** | **将来の検討案**（実装しない） | **本番には入れない** |

## 4. 残っていること

- 選択肢2（型つきの雛形）は将来の検討案。検討するなら、段階3の決まりの設計と合わせ、雛形の候補は「変換」「条件つき送り」「出しっぱなしの申し出」の3つから始める案。
- 拡張の要望を、住人が一覧に「提案」として出せるようにするか（実行はできない、要望の記録だけ）。この試作では作っていない。
