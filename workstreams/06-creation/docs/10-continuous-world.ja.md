# 10. 継続する世界での⑥（シーズン制の廃止を受けて）

**前提（2026-10-31 の方針訂正）：** Wylls の世界は、期間の切替で終わったりリセットされたりしません。戦争や競争を区切る「戦期」は世界の寿命とは別で、区切り方・集計・賞金は未決定です。⑥は戦期を定義せず、World／Period の正本も移行処理も作りません。それらは④（共有コア・移行）と⑧（継続世界の横断設計）の担当です。この文書は⑥の範囲だけを扱います。

この版の位置づけは、**稼働中の実装を捨てずに作る移行の候補** です。commit `517796dc` と補遺 `ADDENDUM-20261030.ja.md` の引き渡し単位はそのまま残し、この変更はその上に積みます。本番の移行を実行する許可ではありません。

## 1. 残っていたシーズン依存

⑥の模擬そのものには、シーズンの開始・終了、終了後の命令拒否、口座の閉鎖はありません。定義・版・公開状態・採用・利用履歴は、もともと期間で区切られていません。依存が残っていたのは次の箇所です。

| 箇所 | 依存の中身 | 区分 |
|---|---|---|
| 実行の依頼の使い捨て番号（`AdoptionBook.useNonce`） | 使った番号を、計画ごとに **世界の寿命の間ずっと** 保存していた。シーズンで世界が作り直される前提なら上限があったが、続く世界では増え続ける | ⑥で修正 |
| 採用済みの計画の固定 | 定義の版と内容ハッシュには固定していたが、**効果の意味（コアの規則の版）** には固定していなかった。コアの変更は「新しいシーズン」で入る前提で、同じ世界の中で規則が変わると、確認済みの計画が気づかずに新しい意味で動いた | ⑥で修正 |
| 完了記録（証拠） | どの規則の版で起きた出来事かを持っていなかった。規則が変わった後に、古い記録を新しい意味で読むおそれがあった | ⑥で修正 |
| 文書の「新しい世界効果は新しいシーズンで出す」（README・docs/04・docs/08・handoff/03・`catalog.mjs` の注記） | コアの拡張を、世界の作り直しと同じものとして書いていた | ⑥で訂正（コアの新しい版を、④の移行で動いている世界に入れる） |
| 計画が名指す場所・札の識別子 | ⑥の計画は `vault:B-home`・`lot:B-1` のような論理的な名前を使っている。一方、コアのアドレスはすべてシーズンの PDA から導かれる（`frontier-abi/src/addr.rs`：`addr = sha256(season_pda ‖ seed ‖ program_id)`）。⑥のアダプタがアドレスを計画に入れると、シーズンの識別子に縛られる | ⑥は論理的な名前だけを署名の対象にする。名前からアドレスへの対応は④の移行が決める（推測で実装しない） |
| コアの「日」の幅 | ⑥は日を安全な整数（2^53 未満）で数え、2^32 を越えても動く（テストで確認）。コアは日・鐘を u32 でアドレスの種に入れている | ④⑧へ確認の依頼（⑥では変えない） |

1日の回数（`runsPerDay`）の区切りは、引き続き模擬の整数の「日」です。区切りを UTC の日にするか、ゲームのターン・戦期にするかは未決定のままで、⑥は戦期を採用していません（docs/05 §4）。

## 2. 変更した挙動

1. **実行の依頼に日付を入れ、受け付ける期間を決めた。**
   - 依頼の形式は `wylls.creation.run/1`。署名の対象に、依頼を出した日（`day`）が入る。
   - 受け付けるのは、その日と翌日だけ（`RUN_REQUEST_DAYS = 2`）。先の日付は `future`、古いものは `stale` として拒否する。
   - 使い捨て番号は、受け付けうる期間の分だけを持ち、それより古いものは捨てる。計画ごとに持つ量は「2日 × 1日の回数」以下で、世界がどれだけ続いても増えない。
   - 旧形式（`run/0`、日付なし）の依頼は `old-format` で拒否する。依頼は義務ではないので、利用者が新しく署名し直せばよい。旧形式の番号は、保存されていても次の受付のときに捨てる。
2. **計画を、効果の意味の版にも固定した。**
   - コアの効果に意味の版（`rev`）を持たせた。
   - 計画の形式は `wylls.creation.plan/1` で、確認した時点の、使う効果ごとの版（`effects`）が署名の対象に入る。
   - 動いている世界で効果の意味が変わる（模擬では `world.effectRevs`）と、その効果を使う計画は `EFFECT_REVISED` で **保留** になる。実行前の確認でも、実行の受付でも、各手順でも同じ。
     - 保留であって、終了ではない。採用は有効のままで、受付の前に止まるので回数にも数えない。
     - 利用者が新しい版で計画を確認し、更新として採用すれば動く（自動では移さない。docs/05 と同じ）。
   - 意味の変わっていない効果だけを使う計画は、そのまま動き続ける。
3. **旧形式の計画を読む。**
   - `plan/0`（`517796dc` まで、`effects` なし）の計画は、署名も中身もそのまま有効として読む。
   - 確認したときの版は「rev 1」とみなし、そうみなしたことを `legacy: true` として結果に出す。
   - **これは移行上の仮定です。** `517796dc` の効果の表がそのまま rev 1 になったので成り立つ。④がコアの版の対応表を出したら、それに合わせる。
4. **完了記録に、効果の名前と、その時点の意味の版を入れた。**
   - 古い記録（版なし）を書き換えたり、新しい版の証拠として読み替えたりはしない。

公開状態（listed / suspended / withdrawn）、作者の公開停止が新しい採用だけを止めること、版の固定、通知だけの更新、停止の権限の分け方は、変えていません（2026-10-30 の決定、補遺 §3）。

## 3. 試験で確認したこと（`test/continuity.test.mjs`、模擬の世界）

| 試験 | 確かめたこと |
|---|---|
| 日の境界と再起動 | 全部の帳簿（登録簿・台帳・採用・世界）を JSON に保存して読み直すと、中身が完全に一致する。境界の前に署名した依頼は、境界の後に1回だけ動く。使った依頼は、再起動の後も再送として拒否される。2日を過ぎた依頼は日付で拒否される。日ごとの回数の記録（開始・成功・失敗）はどちらの日の分も残る。荷車の手数料は、配達の記録の数 × 50,000 lamports と一致する。在庫の増減と、押さえの不変条件も合う |
| 束の持ち越し | 境界の前に届いて押さえられた物は、再起動と境界の後も押さえられたまま残る。1回だけ消費でき、2回目は `spent` になる。配達の記録は正しいまま |
| コアの変更 | 工房の効果の意味が変わると、それを使う計画は保留になる（回数に数えない、採用は有効）。荷車だけの計画は動く。旧形式の計画は rev 1 として動き、変わった効果では `legacy: true` が出る。利用者が更新を確認すると新しい版で動く。古い記録の版は 1 のまま |
| 依頼の期間 | 先の日付・古い日付の依頼は拒否され、回数に数えない。日付のない依頼は作れない |
| 長い運用 | 400日、毎日2回（途中で再起動を1回）。使い捨て番号の数は最大で 2日 × 2回 以下。日ごとの回数は400日分すべて残る。記録は800件すべて残る。手数料の合計が合う。日が 2^32 を越えても動く |

境界を越えられることと、長く続けても状態が扱えることは、別々の試験にしています。

この章の試験はすべて ⑥の模擬の中のものです。チェーン・④の実行サービス・本物の移行での確認ではありません。

## 4. 移行や仕様の判断が残る点

1. **（④）コアの版と、⑥の効果の版の対応。** 本番で「効果の意味が変わった」をどう表すか（規則の指紋・program の版・命令ごとの版）。⑥の `rev` はその受け口にすぎない。
2. **（④）論理的な名前とアドレスの対応。** 継続世界の口座・識別子の方針（シーズンの PDA に縛られた口座をどう移すか）が決まるまで、⑥のアダプタは論理的な名前だけを使う。
3. **（④⑧）日の幅。** コアの日・鐘が u32 のままで、長く続く世界に十分か。
4. **（あなた）1日の回数の区切り。** UTC の日、ゲームのターン、戦期のどれにするか。戦期を採用するかどうか自体が未決定。
5. **（④）依頼を受け付ける期間（2日）を本番で使うか。** 本番では、実行を認可する場所で同じ上限を持つ必要がある。
6. **（あなた・④）旧形式の計画を rev 1 として読む仮定を認めるか。** 認めない場合、旧形式の計画は、利用者が確認し直すまで保留になる。
7. **（④）記録・回数の履歴が増え続けること。** 履歴は消さない方針なので、置き場所（索引・保存の分け方）は④が決める。⑥が上限を設けたのは、強制に使う状態（使い捨て番号）だけ。
