# 5. 更新したとき、既存の利用者をどう扱うか（判断案）

**採用済みの前提：** 22 の4章「持ち主が条件を変える → 変えた条件は、新しく出す札にだけ効く。すでに出した札は、期限まで元の条件のまま」（2026-10-23）。⑥の定義は札ではないが、同じ考え方を定義の版に当てはめる。

**正本：** `src/upgrade.mjs`（上げ方の判定と、既存の計画への申し出）、`src/registry.mjs`（版の書き換え禁止と上げ方の検査）。テストは `test/upgrade.test.mjs` と `test/required.test.mjs` 5。

## 1. 案（試作で実装済み）

1. **版は書き換えられない。** 同じ名前・同じ版は一度だけ公開できる（`VERSION_EXISTS`）。新しい版は前の最新より大きい（`VERSION_NOT_NEWER`）。
2. **利用者の計画は、版とハッシュに固定する。** 作者が新しい版を出しても、準備済みの計画は元の版のまま動く。作者が後から中身を変えて利用者に押し付けることはできない。
3. **変更の大きさに見合う版の上げ方を、公開時に機械で強制する**（`VERSION_BUMP_TOO_SMALL`）。

   | 上げ方 | 変更 | 既存の利用者への扱い |
   |---|---|---|
   | patch | 機械の部分が同じ（題名・説明・主張・期限を延ばす） | そのまま移ってよい（`follow`） |
   | minor | 追加だけ（既定値つきの入力、新しい出力）。既存の入力・依存・手順・上限・合図・出力は同じ | 申し出る。移るのは実行前の確認をやり直してから（`offer`） |
   | major | それ以外（手順・依存・上限・合図が変わった、入力が消えた、期限ができた・早まった） | 移らない。今の計画は元の版のまま。移るなら準備し直す（`stay`） |

4. **停止と取り下げは作者の署名でだけできる**（`NOT_AUTHOR`）。署名は状態の履歴の番号に結びつくので、古い署名を出し直して後の変更を取り消すことはできない。停止・取り下げされた定義は、一覧から消え、新しい準備も、既存の計画の実行前の確認も通らない（`ENTRY_NOT_LISTED`）。その定義の成果を使う（C）定義も止まる（`DEPENDENCY_SUSPENDED`/`WITHDRAWN`）。記録（版・ハッシュ・状態の履歴）は残る。状態は版ごとではなく名前ごとなので、作者が新しい版を公開するとその名前は「一覧に出ている」に戻り、古い版に固定した計画も再び確認を通る（試作の扱い。版ごとの停止が要るなら拡張する）。
5. **写しは止められない。** 停止された定義も、公開された記録として写せる。写した人は自分の責任で、自分の定義として出し直す（写しは元の作者の札も記録も持たない）。

## 2. 理由

- 計画を版とハッシュに固定するのは、22 の4章の「後から不利な条件を押し付けられない」を、定義にも当てはめるため。
- 上げ方を機械で強制するのは、作者の自己申告（「小さな直し」）で、利用者の計画の中身が変わるのを防ぐため。
- 停止で既存の計画も止めるのは、作者が危険（例：経路が敵地を通るようになった）に気づいて止めたとき、その判断を利用者の画面に確実に届けるため。定義は利用者自身の操作の組み合わせなので、利用者は写して続けることもできる。

## 3. 判断してほしいこと（あなたへ）

1. **停止の効き方。** 案は「既存の計画も止める」。代わりに「新しい準備だけ止め、既存の計画には警告だけ」もありうる。止めると、作者が利用者の計画を止める力を持つ。止めないと、作者の警告が届かない場合がある。
2. **patch の自動追従。** 案は「機械の部分が同じなら移ってよい」。作者の説明（`note`）だけが変わる場合も、利用者の確認なしに紙が変わることになる。説明の変更も利用者の確認を要するか。
3. **期限を延ばすのを patch とすること。** 延長は利用者に不利でないので patch とした。
4. **国が持つ仕組み（C4）。** 持ち主の札を国の倉で持つ場合、版の公開と停止を国の投票で決めるなら、作者の鍵の代わりに投票の記録を「作者の署名」として扱う拡張が要る（この試作にはない）。
