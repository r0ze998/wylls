# 7. 記録と権利、確認と実行：何をローカルで防げて、何を防げないか

**束の扱い（2026-10-30）：** 束を新しいコア仕様として採用することは **保留**。試作の束は比較のための模擬で、まず「依存する配送の完了を証拠として確認し、実行時に現在の倉の在庫を原子的に検査・消費する」案と比べる（§4）。配送由来の資源を排他的に確保する必要がある場合だけ、予約・escrow 等の追加のコア機能を検討する。

## 1. 完了記録（証明）と、消費する権利（束）を分けた（試作の模擬）

| | 完了記録（evidence） | 使う物の束（batch） |
|---|---|---|
| 何か | ある実行のある手順が終わった、という過去の出来事の証明。結果・場所・物・受け取り手・作った定義（版とハッシュ）・計画・実行番号を持つ | 配達で届いた物を、受け取り手のために倉の中で押さえた「1回だけ消費できる権利」 |
| どこにあるか | 台帳（`src/ledger.mjs`。④ の Receipt の代わりの模擬） | 世界（`world.batches` と、倉の `held`）。証明の id を指す |
| 使うと減るか | **減らない。** 何度でも引用できる。消費されたという状態を持たない | **一度だけ。** 消費すると `spent`、持ち主が解放すると `released` |
| 物を生むか | **生まない。** 記録を書けば倉に物が増える、という経路はない | 物は配達の時点で倉に入っている。束はそのうち押さえた分を指すだけ |
| 誰が作るか | 実行（`execute.mjs`）。模擬なので、台帳を持つ者は誰でも `record` を呼べる（だから記録だけで物が動く経路を作らない） | 実行だけ（公開された出力の配達が倉に届いたとき） |
| 計画との関係 | C の依存の検査で引く（作り手・版・出力・結果・確定・受け取り手） | 計画には固定しない。**実行の依頼ごとに**名指しする |

成り立たせている不変条件（`checkHoldInvariant`、`test/resources.test.mjs` で多数の交互実行の後に検査）：
- どの倉でも、資源ごとに `0 ≤ held ≤ stores`。
- `held` は、その倉の開いている束の残りの合計に等しい。
- 普通の手順が取れるのは `stores − held`（自由在庫）だけ。束の物は、その束を名指しした消費でしか動かない。

### 確かめたこと（`test/resources.test.mjs`・`test/required.test.mjs` 8）
- 台帳に偽の「届いた」記録を書いても、束はできず、倉に物は増えない。実行も `BATCH_INVALID unknown` で止まる。
- 本物の配達の記録を、束の代わりに名指ししても使えない（記録は権利ではない）。
- 束の倉が奪われると（世代が変わると）束は無効。記録は過去の事実として有効なまま。
- 束で押さえた物は、同じ持ち主の普通の送りでも取れない（自由在庫 0 で `STOCK_SHORT`）。持ち主が解放すれば取れる。
- 一つの束を二つの採用済み計画が名指しし、同時に実行すると、消費できるのはちょうど一方だけ（他方は実行時に `spent`）。倉の物は一度分だけ減る。
- 同じ計画の同じ日の二回の実行も、記録の id は別になる（実行番号を記録に入れた。以前は同じ内容になり id が衝突していた）。

## 2. 確認（preflight）と実行を分けた

- **確認**は、そのときのスナップショットでの助言です。何も許可せず、何も押さえません。採用の条件として使うだけです。
- **実行**（`execute.mjs`）は確認の結果を受け取りません。受け取るのは、署名された計画と、利用者が署名した実行の依頼だけです。そして手順ごとに、その時点の世界で次を検査し直します。
  - 採用の状態（置き換え・停止）、依頼の署名・宛先・使い捨て番号、今日の回数
  - 固定した定義が一覧の記録と一致するか（ハッシュ）、世界の規則にその効果があるか
  - 札（持ち手・取り消し・世代・期限・束ごとと工房全体の残り回数）、場所（持ち主・生存・州・共有でないか）
  - 自由在庫、束、残高、容量
- 各手順の「検査→変更」は、途中に `await` を挟まない一つの同期ブロックです。手順と手順の間で別の実行が割り込んでも（テストでは `Promise.all` で交互に走らせる）、同じ札の回数・物・残高・束を二重に使えません。
- 失敗した手順で実行は止まり、それまでの手順の結果は残ります（「失敗は止まるだけ」、設計16 §2）。止まった手順は「failed」の記録になり、成功の記録は作られません。

### 確かめたこと（`test/runtime.test.mjs`・`test/policy.test.mjs`）
実行の途中で利用者が計画を止めた・置き換えた場合も、次の手順で止まります（`review2`）。一つの依頼で同じ束を二度名指ししても、二重には消費できません（`review2`）。確認と採用が通った後に、次が起きた場合、実行はその手順で止まります：取り消し、期限切れ、施設の奪取・閉鎖、札の譲渡、他の利用者による工房の回数の消費、残高の減少、材料の流出、届け先の満杯、作業倉の奪取。採用していない計画、署名後に書き換えた計画、一覧の写しの書き換え、依頼なし・他人の依頼・使い回しの依頼も止まります。

## 3. ローカルで防げていること／②④やチェーンの原子的な検査・更新がなければ防げないこと

| 守りたいこと | この試作（ローカル・模擬） | 本番で必要なもの | 担当 |
|---|---|---|---|
| 記録だけで物が生まれない | 防げている。物は実行の配達でしか増えず、束は実行しか作らない | 記録を書けるのは実行（Run）だけ、物の移動はプログラムの命令だけ、という本番の構造 | ④・チェーン |
| 同じ物の二重消費 | 防げている（一つのプロセスの中で、手順ごとの同期ブロック） | 在庫の検査と減算を、同じ取引の中で原子的に行う（S1/S2 の命令は自分の範囲でそうなっている）。**束（配達の物の押さえ）を本番で使うなら**、その状態をチェーンの上に置く新しいコア機能が要る（S2 の預かりの `HELD` の一般化。今の S1/S2 に配達を押さえる仕組みはない）。束は採用保留（§4） | ④・チェーン（コア） |
| 同じ札の回数の二重使用 | 防げている（同上） | S2 の `UseRun` は束ごと・工房ごとの回数を同じ命令で検査・加算している（2d §3）。これをそのまま使う | ②（S2 の規則） |
| 確認の後の状態の変化 | 実行時に検査し直すので止まる | 実行の各命令が、その時点の口座で検査する（S1/S2 の命令は既にそうなっている）。⑥の確認の結果を、実行の条件にしない | ④ |
| 実行の依頼を利用者以外が出す・使い回す | 防げている（依頼の署名と使い捨て番号を、採用の記録で検査） | 依頼の署名をウォレット／セッション鍵の規則（他人あての送りはウォレット）と合わせる。使い捨て番号の記録をチェーンの上に置く | ④・チェーン |
| 公開停止が採用済みの計画を止めない | 実装済み（採用の記録がある計画は、状態を見ない） | 採用の記録が、作者や運営から書き換えられない場所にあること（今はローカルの記録） | ④ |
| 固定した版の中身が変わらない | ハッシュで検査（一覧の写しを書き換えても `HASH_MISMATCH`） | 一覧（定義の本体）を改ざんできない場所に置く、または実行時にハッシュから取り直す | 公開の置き場（未決定） |
| 台帳・世界・採用の記録そのものの改ざん | **防げない。** すべて同じプロセスのメモリとブラウザの localStorage にある | チェーンと検証器。⑥の試作はその代わりにならない | ②④・チェーン |
| 襲撃・経路・到着時刻 | **扱っていない。** 荷車は依頼した直後に着く（指定したときだけ襲われる） | S1 の荷車の命令（経路・州の枠・襲撃・精算） | 既存の S1 |
| 本当の署名の権限（ウォレットとセッション鍵の区別） | **扱っていない。** 署名は模擬の鍵。「ウォレットが要る」は知らせるだけ | S1 の署名の規則（他人あてはウォレット、§3.3） | 既存の S1・中継 |

**この表の左の「防げている」は、すべて模擬の世界の中の話です。** 本番で同じことを保証するには、右の欄のものが要ります。⑥の検証器・確認は、本番でも「始める前に分かる不足を見せる」役に留まり、権限の判定や資源の確保の代わりにはなりません。

## 4. 束（案A）と、証拠＋在庫の原子的な消費（案B）の比較

**状態：** 比較だけ。どちらも本番には入っていない。試作は案A を模擬している。案B は試作に入れていない（機能を広げないため）が、案A の束の検査を外し、自由在庫からだけ取る形にすれば、同じ実行の仕組みで表せる。

| | 案A：束（配達の物を押さえる） | 案B：証拠を確認し、実行時に倉の在庫を原子的に検査・消費 |
|---|---|---|
| 実行時に確かめること | 束が自分のもの・未消費・倉の世代が同じ・使う倉にある。束の証拠（記録）が期待する作り手・版・出力の、確定した、自分あての配達 | 依存する配送の完了の証拠（記録）が、期待する作り手・版・出力の、確定した、自分あての、使う倉への配達。そのうえで倉の **今の** 在庫が足りるか |
| 物を減らす所 | 束の残りと倉の在庫を同時に減らし、押さえを外す | 倉の在庫を減らす（原子的に検査して減らす） |
| 記録だけで物が生まれない | 保証される | 保証される（物は倉の在庫からしか取らない） |
| 同じ物を二重に消費しない | 保証される（束は一度だけ。押さえた物は他の手順も取れない） | **物の数としては保証される**（在庫を原子的に減らすので、在庫を超えては取れない） |
| 同じ証拠を二度使わない | 束が消費済みになるので、自然に一度だけ | **別に印が要る。** 証拠は消費されない設計なので、「この証拠はこの計画の実行で一度使った」を記録する（④の Receipt の消費の印、または ⑥の採用の記録）。印がなければ、一つの配送の証拠で何回でも実行を始められる（物は在庫の分だけ） |
| 「あの配送で届いた物そのもの」を使う | 保証される | **保証されない（弱くなる保証）。** 在庫は混ざるので、同じ倉の他の物（自分で運んだ物、他の配送の物）を使うかもしれない。配送の物が既に他の用途に使われていても、在庫が足りれば実行は通る。逆に、配送の物が届いていても、同じ倉の別の操作が先に在庫を使えば足りなくなる |
| 配送の後に倉が奪われた | 束が無効になる（世代） | 在庫は奪った側のものになる（S1 の規則）。証拠は残るが、在庫の検査で止まる |
| 必要なコアの変更 | **新しい**：配達の物の押さえ（予約・escrow の一般化）をチェーンの上に置く | 既存の範囲：在庫の原子的な検査と減算は S1/S2 の命令にある。加えて、証拠の「一度だけ使った」印（④） |
| 合う場面 | 配送の物を排他的に確保する必要がある（例：代金を払って買った物を、他の操作に使わせたくない） | 「届いたことを条件に始める」で足りる（例：材料が届いたら工房を動かす。どの鉱石かは問わない） |

**推奨（提案）：** 本番の最初は案B（新しいコア機能が要らない）。案B の弱くなる保証（配送の物そのものは確保しない）を、定義の紙と実行前の確認の知らせに明記する。配送由来の資源を排他的に確保する必要が出た場合だけ、案A に当たる予約・escrow の追加のコア機能を、②④と検討する。

**試作のテストとの関係：** `resources` と `required` 8 の束に関するテストは案A を確かめている。案B を採るなら、束の検査を「証拠の一度だけの印＋在庫」に置き換え、「配送の物そのもの」を前提にしたテスト（押さえた物を普通の手順が取れない、倉の奪取で束が無効）は、案B の弱い保証を示すテストに書き換える必要がある。
