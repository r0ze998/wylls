**確認時点（2026-10-30）：** ②③④の成果物は、基準 commit `4cd901de` にも remote の全ブランチ・PR にもありません。②④からは統合担当経由で **報告の要約** が届いています（② `dc3bd3d9…`、④ `bd415e74…`）。ただし、どちらの commit も origin から取得できず、成果物は未受領・未検証です。したがって、下の各資料の「相手の成果物との対応」は、すべて **資料待ち** です。接続済みのものはありません。⑥は接続先を推測で実装せず、模擬（モック）と、必要とする契約だけを置いています。

## ⑥から各担当への依頼（まとめ）

1. **②へ：** 加工能力の貸出（使用権）を契約に含める予定はあるか（報告では StockSwap は素材と武具の交換で、加工能力の貸出ではなく未採用）。既に出した使用権を発行者が取り消せるか。束ごと・工房ごとの回数の確認と加算を、実行の命令と同じ取引で行うこと（S2 の `UseRun` の形）を、接続の前提にしてよいか。session の予算を制限しないなら、⑥の1日の回数を④の受理で強制する前提でよいか。
2. **③へ：** 命令の型を表として公開し、⑥の効果の表をそこから生成できるか。⑥の「効果」は複数の命令の組（例：荷車＝送る＋精算）だが、③の型の単位とどう対応させるか。
3. **④へ：** 実行の認可（採用・依頼の署名・使い捨て番号・1日の回数）をどこで記録するか。記録の id の決め方。「確定・部分到着・到着量未検証」の状態の名前と遷移、⑥が確定だけを C の証拠として受け入れてよいか。証拠の「一度だけ使った」印の置き場。取消の3段階のどこで⑥の回数を扱うか。束（配達の物の押さえ）は⑥で採用保留とし、まず「証拠＋在庫の原子的な消費」（[docs/07](../docs/07-guarantees.ja.md) §4）で進めてよいか。
