## 1. 到着量：記録の cargo は下限

| 事実（ソース） | 意味 |
|---|---|
| 送る時に道の損耗を掛ける（`caravan.rs:773` `worn_cargo`） | 運ばれる量は計画の量以下 |
| 記録の cargo は `floor(milli / 1000)`（`caravan.rs` `cargo_log`） | 運ばれた量の**下限**。記録が 0 でも、実入荷 0 とは限らない |
| 村は運ばれた量の全部を加える（holding の `credit`） | 村の入荷は、記録の値以上で、資源ごとに 1 未満多いかもしれない |
| 倉庫は容量で黙って切る | 倉庫の入荷は記録から分からない |

③の変更：
- **local の port：** 到着量は `unverified` のまま。記録の cargo を `recorded.cargoLogged` に、精度（「整数、milli を切り捨て。下限で、0 を含む」）と一緒に残す。計画の量は「届いた量」としては出さない。
- **`ws04-mapped`：** 村宛ての `verified`（④の RuleDerived）は、量を `{atLeast: 記録の値, below: 記録の値 + 1, unit: 'whole', precision}` で出す。記録が 0 の資源は「0 以上 1 未満」。計画の量は使わない（前の版の誤り。損耗があると多く言っていた）。
- **KnownZero：** 襲撃（taken／burned）と LOST は、**この要求自身のものと証明された caravan に、同じ番号の記録（`CARAVAN_RAIDED`、または settle の LOST）がある時だけ**。そうでなければ `Unverifiable`。

## 2. 自分の要求であることの証明（番号だけでは決めない）

番号（owner_tag, seq）が同じ記録は、別の経路の送信でもありうる。③は次の証拠でだけ「この要求の caravan」とする。

| 証拠 | 条件 |
|---|---|
| `CARAVAN_SENT` の記録 | herald の行の `sig`（記録を含む取引の署名）が**この要求の署名**と一致し、中身（宛先の場所、積荷）が計画と合う。積荷は計画以下で、損耗が 0 なら同じであること |
| この要求の署名の着地 | relay の `/f/tx`（この要求の署名を名指す）が landed |

| 場面 | ③の扱い |
|---|---|
| 同じ番号の `CARAVAN_SENT` が別の署名 | `hold: SeqUsedByAnotherSend`。この要求の結果はそれで決めない。settle の記録が来ても完了にしない。予約は解かない |
| 自分の署名だが中身が違う | `hold: Inconsistent`。道中にしない。以後の settle・襲撃の記録も数えない |
| 自分の署名が分からない（答えが失われた） | `hold: Indeterminate`。番号の記録は数えない。同じ requestId の再送で、⑤の記録から署名が返れば、それまでに見た記録を見直す（記録は操作に残しておく） |
| 自分の署名が失敗として着地 | **finalized の時だけ**決める（何も動かなかった。手数料は払った）。それより前（confirmed 等）や commitment が分からない時（0007 の無い relay）は保留 |
| relay の `expired` | 決めない（不在の証明ではない）。予約は数えたまま |
| 時間が過ぎても証拠が無い | `hold: Indeterminate`。**caravan の通し番号による NotSent はやめた**（番号は別の経路でも進む。番号が進まないことは、ゲームの効果が無かったことの証明にはなっても、手数料が無かったことや、自分の要求の結果の証明にはならない） |
| 自分の署名の不在が証明された（0007 の `absence.proven`） | `failed: NotLanded`。予約を解く。費用は `released` |

**ゲームの効果が無かった証明と、手数料が発生しなかった証明は別：**
- 失敗として着地した取引は、効果は無いが手数料が掛かる（`charged`、または 0007 の commitment が finalized でなければ `unconfirmed`）。
- `released` は、自分の署名の不在が証明された時だけ。

## 3. 0007 の限界（そのまま残す）

relay は送る前の slot を記録していないので、今の 0007 では `absence.proven` は true にならない（0007 の試験で確かめている）。足すなら、④⑤と次の順序を揃える（**提案。実装していない**）。

1. 署名する前に、finalized の slot を読む（⑤の `fate.mjs` `slotFloorOf`。⑤の gateway の `#build` は既に読んでいる）。
2. その slot、署名、`lastValidBlockHeight` を、**送る前に**永続化する（今の relay の `ctx.sent` はメモリだけで、再起動で消える）。⑤の ledger（行動の記録）か、④の run store のどちらに置くかは、④の判断。
3. 送る。
4. 再起動した時：記録に slot の無い署名は、いつまでも「証明できない」（`unknown`）として扱う。予約は解かない。記録がある署名だけ、`fateOf` で判断する。
