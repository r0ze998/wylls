# ④への選択肢：③④⑤で、認可と送信をどう共有するか（2026-10-30。判断は④。**どの方式もまだ採用しない**）

**⑤はどれも実装していません。** ⑤だけで共有の認証を作り直しません。下は、④が統合を判断するための選択肢と、それぞれに必要な変更と保証の違いです。

**前提（コードと③の実物で確認済み）：**
- Citizen の session 鍵は**1枠**です（`frontier-abi` の `SESSION`／`SESSION_EXPIRY`）。session 鍵を増やせるとは仮定しません。
- 代理1つに capability は**1つ**です（`AgentGateway.#authenticate` は `rec.capabilityHash` 1つと比べる）。③の接続の同意で回ると、前の token は使えなくなります（統合試験で確認）。
- 中継の `submit` は、capability のほかに、本人の署名（`{owner}`）と、中継の中の runner（`{runner: true}`）も受け付けます（既存）。
- `agent_view` は公開の読み取りで、capability を確かめません。

## 採らない物

| 案 | 採らない理由 |
|---|---|
| **再開のたびに token を回し、相手を無効にする** | 片方が動くと、もう片方が止まる。③の封印された token も、⑤の token も、本人の知らないうちに無効になる。本人の操作の優先（③が先）にも反する |
| session 鍵を増やす、代理ごとに session を分ける | session は Citizen に1枠。増やすには program の変更（④ P6 の範囲の外）が要り、今の前提にない |

## 選択肢

**読み方：** 各案が解くのは、表の「解くこと」の行に書いた事だけです。特に **B は capability の共存を解く案で、送信の順序や予算の競合までは解きません。** C・D は「すべての書き込みの経路が同じ管理を通る」ことが条件で、その条件は表の下に書きました。

| | A. 今のまま（どちらか一方） | B. 送り手ごとの capability | C. 送信の窓口を中継の中に一本化（runner として） | D. 送信の窓口を④の実行器に一本化 |
|---|---|---|---|---|
| 解くこと | — | **capability の共存だけ**（③と⑤が同時に token を持てる）。送信の順序・予算の取り合い・隊商の番号は解かない（今と同じく、中継の台帳・⑤の seq の印・鎖が守る範囲のまま） | 送信の窓口が、⑤の分は中継の中の1つになる。条件を満たせば、⑤の予約と中継の台帳が同じプロセスになる | 送信の窓口が④の1つになる。条件を満たせば、順序と番号を④が決める |
| 中身 | 本人が、③か⑤のどちらかに token を渡す。切り替える時に回す | 代理が capability を複数持つ。それぞれに `source`（`mcp`・`ai`）と名前を付け、別々に発行・取り消す | ⑤の自動運転を中継のプロセスの中で動かし、既存の `{runner: true}` で `submit` を呼ぶ。③は今の capability のまま | ③⑤とも④に要求（RunSpec など）を出し、④の実行器だけが中継へ送る |
| 共有コードの変更 | なし | `ledger.mjs`（capability の一覧）、`gateway.mjs` `#authenticate`（一致する物を探し、その `source` を要求に強制）、本人の命令（発行・取消を名前ごとに）、`agent-mcp.mjs`、③の同意の流れ（回さずに③用を発行） | `runner.mjs`（⑤の判断器を差し込む口）、中継の起動（⑤のモデル接続とその秘密情報が中継のプロセスに入る）、`meterInference` か⑤の費用の台帳のどちらを使うか | ④の Run が代理の1回の行動（Train など）も表せること（今は物流だけ）、③の MCP の送信を④経由に、④から中継への認証（④が capability を持つか、中継の中で動くか） |
| 同時に書き込めるか | **できない** | できる | できる | できる（④が順番を決める） |
| 片方を止める・取り消す | token を回すと、もう片方も止まる | 送り手ごとに取り消せる | ③は token、⑤は runner の停止。mode は今も共有 | ④の取消（3段階）で |
| 1つのプロセスの制限 | ⑤は自分のプロセスだけを守る | 同じ（⑤は複数プロセスを検出しない） | **⑤の予約と中継の台帳が同じプロセスに入る**（中継は状態ファイルのロックで1プロセス） | ④の run store（SQLite、lease と fencing）が守る |
| 順序（seq の印） | ⑤の境界がある | ⑤の境界がある。`source` で③と⑤を確実に分けられる | 同じ。中継の中なので、送る直前の確認を同期でできる | ④が `sole_owner_send` で守る。③⑤の印は不要になる |
| 鎖の上での権限 | session 鍵は session 可の命令すべてに効く（変わらない） | 同じ。capability は中継の中の制限で、鍵の権限を狭めない | 同じ | 同じ（④ P6 が無い限り） |
| 残る問題 | 本人が③を使う間、⑤は使えない | capability ごとの許可範囲（命令の群）を決めないと、送り手を分けても範囲は同じ | 運営のプロセスにモデルの秘密情報が入る。中継の停止で③⑤とも止まる | ④の範囲が物流から広がる。③の送信の経路が変わる |
| ⑤の側の変更 | 済み（`BadCapability` で止まる、新しい token の確認） | `source: 'ai'` の capability を使う（パッチ 0003 の考えと同じ） | 判断器と費用の台帳を、runner の口に合わせる | RunSpec を作る側になる。行動を直接送らない |

## C・D が成り立つ条件：すべての書き込みの経路が同じ管理を通ること

同じ Citizen に書き込める経路は、今、次の6つです。C・D の保証は、**このすべて**が窓口を通る時にだけ成り立ちます。1つでも窓口の外に残れば、その経路との順序・予算・番号の競合は、今と同じく残ります。

| 経路 | 今の通り道 | C で窓口を通るか | D で窓口を通るか |
|---|---|---|---|
| ③の MCP（本人の操作） | 中継の `submit`（capability） | 通る（③は capability のまま。⑤とは中継の台帳で同じ管理） | ③を④経由に変える必要がある |
| ⑤の自動運転 | 中継の `submit`（capability） | 通る（runner として） | ⑤が④に RunSpec を出す形に変える必要がある |
| ④の実行器 | （未接続） | 中継の `submit` を使うなら通る。**session 鍵を自分で持って RPC へ送るなら通らない** | 窓口そのもの |
| 本人のブラウザ（ウォレットの署名） | (a) 本人の署名で鎖へ、または中継の `POST /f/relay`。(b) agent wallet の本人の経路（`submit` に `{owner}`、source `browser`） | (a) は**通らない**（agent wallet の外）。(b) は通る（同じ中継の台帳） | (a) は**通らない**。(b) も④を経由しない |
| session 鍵（seed）を持つ者が RPC へ直接 | 中継の外 | **通らない**（鍵の権限は狭まらない。④ P6） | **通らない** |
| 別の中継のプロセス・別の運営 | 別の台帳 | **通らない** | **通らない** |

したがって、C・D でも、本人のブラウザの操作と、鍵を持つ者の直接の送信との競合は残ります。これを閉じるには、鎖の上の範囲（④ P6）か、本人がその間に操作しない運用が要ります。

## どの案でも役に立つ小さな変更（共有コード、④の判断）

- **capability を確かめる、読むだけの口 `agent_whoami`**：独立した変更候補 **0004**（`WHOAMI-PROPOSAL-4.ja.md`）。今の⑤は、暫定策の probe（`src/access-check.mjs`、隔離）で代用しています。probe は、検証した中継のツリーでだけ送り、冪等の記録を1件残し、1日の回数に上限があります（`ACCESS-CHECK.ja.md`）。
- **パッチ 0003**（MCP サーバーが `source` を名乗る）。B・C で、③と⑤の記録を確実に分けられる。

## ⑤の今の実装が、どの案でも守ること

- session 鍵も mode も変えない。token を回さない。
- `BadCapability` を受けたら止まる。再開は本人だけで、新しい token が、今の物か・この代理か・この所有者か・許可の範囲が足りるかを、モデルを呼ぶ前に確かめる。
- token の値を、記録・ログ・成果物に残さない（`[capability]` に置き換える）。
