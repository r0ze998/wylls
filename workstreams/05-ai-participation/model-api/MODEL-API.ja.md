## 2. provider 契約（`src/contract.mjs`）

### 1回の呼び出しの記録（分けて持つ物）

| 欄 | 中身 |
|---|---|
| `model.configured` | こちらが設定したモデル名 |
| `model.served` | 応答が名乗ったモデル名。**自己申告で、検証ではない** |
| `usage` | 課金される入力（キャッシュなし）、キャッシュ読み、キャッシュ書き（TTL 別）、出力、出力のうち推論分（参考） |

| `quote`（見積上限） | 呼ぶ前に確保する額。入力は「本文の UTF-8 バイト数 × いちばん高い入力単価」、出力は上限いっぱい |

| `unknown`（不明な費用） | 送った後に答えがない、またはサーバーの誤り。提供者が請求したかが分からない。確保したまま |
| `invoiced` | 提供者の請求・利用レポートとの照合。**未実装**（承認事項） |

|---|---|

## 3. ④との契約（④ `bd415e7` は未受領。⑤ 側に明示した mock：`src/run-cost.mjs`）

| 要件 | ⑤ の動き（mock で実装・テスト済み） | ④ への接続要件 |
|---|---|---|
| 推論前の予算確保 | 見積上限で確保する。確保できなければ呼ばない。1回・1日・総額の上限を確かめる | 確保・確定・解放・未確定を、呼び出しのキーで記録できること |
| 結果不明の保留 | 送った後に答えがない・5xx は「未確定」。コードでは解放も出金もできない。動かせるのは提供者の利用レポート（額）か、運営の判断（請求か返金）だけで、根拠のメモが必須 | 未確定を一覧でき、外部の答えで閉じられること |
| 再試行と重複課金 | 再試行のたびに、新しいキー・新しい確保・上限の確認をする。結果不明の後の再試行は、既定で**しない**。許した場合は「二重に請求されたかもしれない」と記録する（冪等キーがないため） | 試行ごとの記録と、試行のつながり |
| ゲーム操作分の予算 | ゲーム操作の USDC 価格を先に取り分ける（`setGameReserve`）。推論はその残りしか使えない | 1つの予算の中の、推論とゲームの区分 |
| 実行中に再起動 | 呼び出し中は未確定、呼ぶ前の確保は解放 | 同じ |
| 手動復帰 | 新しい呼び出しを止める（停止を事前確認で見る）。呼び出し中の推論は取り消せない（答えが返れば請求、返らなければ未確定）。送る前の確保は返る | ④の「新規要求の停止 → 署名済み要求の確認待ち → 成立済み効果の列挙」に、推論の行を加える |

4区分（予約・確定・未確定・解放）は `classes()` が返します。出金できるのは、利用可能分だけです。

**実際のお金との関係：** 本物のお金の記録は中継の台帳（`AgentLedger`）です。mock の数字を台帳に反映するには、パッチ 0001 の「見積りで確保して、実測で確定する」型（未適用）が要ります。⑤ はこの mock を台帳の代わりにしません。

## 4. 無駄な推論を減らす（`preflight`）

モデルを呼ぶ前に、費用のかからない情報で「呼んでも無駄」を落とします。

| 理由 | 何を見るか |
|---|---|
| `Stopped` | 本人が停止している |
| `NotDelegated` | 代理の鍵が今、Citizen の session でない（本人か別の持ち主が持っている）。⑤は委任し直さない |
| `DelegationUnread` | 中継が鎖の委任を読めなかった |
| `GrantInvalid` | 委任条件が切れた・取り消された・方針が変わった |
| `NothingAllowed` | 任された命令がない |
| `NothingOpen` | 答える依頼がない |
| `CallCapReached` | 本人の「1日に呼ぶ回数」を使い切った |
| `QuotaEmpty` | 今日の後払い取引の枠がない（決めても送れない） |
| `BudgetShort` | 利用可能額が「見積上限＋ゲーム操作の予算」に足りない |

既存の⑤の流れには、すでに「開いている依頼がない回はモデルを呼ばない」があります。この preflight は、それを予算・枠・委任まで広げたものです。

## 5. ③の本人操作と⑤の自動操作の調整案（③ `47b05ac6` は未受領。提案）

同じ Citizen と同じ予算を使うときの前提（コードで確認済み）：
- session は Citizen に1つです。
- 中継の代理の財布は、代理1つにつき台帳が1つです。
- 1日の後払い取引の枠は、Citizen 単位で共有です。

| 衝突 | 提案 |
|---|---|
| session の取り合い | **⑤は SetSession をしない**（ウォレット専用の命令で、代理には委任できない）。代理の鍵が session でなくなったら、⑤は止まって報告する（preflight の `NotDelegated`）。③が独自の session 鍵を使う設計なら、⑤と同時には成り立たないので、どちらに渡すかを本人が選ぶ。③が本人のウォレットで都度署名するなら、衝突しない |
| 同時に動く | 本人が③で操作している間は、⑤を止める。案A：③のクライアントが本人の署名で `mode manual` にする（今ある仕組み）。案B：中継に「本人が操作中」の短い期限付きの印を足し、⑤の preflight がそれを見る（共有コアの変更、提案のみ） |
| 予算と枠 | 両方が同じ台帳と同じ取引枠から引く。⑤は枠を使い切らない（例：本人のために枠の一定割合を残す。割合は未決） |
| 同じ蓄えの取り合い | ⑤は送る直前に見直す（既存の鮮度の確認）。中継の版の確認（`StalePolicy`・`StaleMode`）が、本人の方針変更を反映する |
| 記録 | 中継の台帳は、行動ごとに `source`（`browser`・`ai`・`mcp`）を記録している。本人の操作と⑤の操作を分けて見られる |

## 6. 最初の検証は、1つの実行プロセスに限る

- ⑤の実行層（確保・上限・再試行の判断）は、1つのプロセスの中で同期的に予約します。並行して動く呼び出しどうしでは二重に使われません（テストあり）。
- 中継の台帳も、1つの状態ファイルを1プロセスだけが持ちます（ロックファイル）。
- **この限定で安全になるのは、⑤の実行層を通る呼び出しだけです。** 次のものは、この限定では安全になりません。
  - 接続トークンを持つ別のクライアント（③の MCP を含む）
  - 代理の鍵（seed）で RPC へ直接送る取引
  - session 鍵の広い権限（Citizen のすべての村、session 可のすべての命令）
  - 2つ目の⑤プロセス
