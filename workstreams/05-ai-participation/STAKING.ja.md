# AI staking：agent を任せられる仕組み（要件2・3・5・6）

**状態：** ローカルの局所実装と検証。採用済みの仕様ではありません。担保の没収・利回り・新トークンは足していません。価格・手数料はすべて**試験値**で、本番の値として固定していません。

ここでの AI staking：ユーザーが自分の agent を参加させ、予算と行動範囲を決め、預けた残高から使った分を払う。推論費用とゲーム内の支出（建設・取引など）を**一つの予算**で管理し、同じ村を手動と自動で切り替える。

現状調査（要件1）は [STAKING-STATUS](STAKING-STATUS.ja.md)、他担当との境界は [STAKING-BOUNDARIES](STAKING-BOUNDARIES.ja.md) にあります。

## 1. モデルと予算を分ける

### モデル（`src/staking/providers.mjs`）

モデルは設定で選びます。Gemma は選択肢の一つで、決め打ちではありません。

| 提供者 | 中身 | 状態 |
|---|---|---|
| `local-openai` | loopback 上の OpenAI 互換サーバー（llama-server と任意の GGUF など）。外部への通信なし | 実装済み。fake のローカルサーバーで HTTP の経路まで確かめた |
| `scripted` | 台本の答え。モデルではない | 実装済み（テスト・デモ用） |
| `external` | 外部の API | **宣言だけ。** 通信しない、キーを読まない（環境変数の名前だけ書ける）。精算方法を本人が決めるまで使えない |

プリセット：`gemma-4-26b-local`（`start-pinned.sh` と同じ URL と別名）、`any-local`、`scripted`。

**設定したモデルと実際のモデルを分けて記録します。** 記録には次の3つが別々に残ります。
- 設定したモデル（こちらが頼んだ名前）
- サーバーが名乗る別名（`/v1/models`、答えの `model` 欄）
- 読み込んだファイル（`/props` の `model_path`。ファイル名だけ残し、ディレクトリは捨てる）

デモでは、別名が `gemma-4-26b-a4b-it` でファイルが Gemma 3 という食い違いを、そのまま記録しています（`logs/staking/staking.report.json`）。

### 予算の見え方と、実際の決済（`src/staking/pricing.mjs`）

本人に見えるのは一つの予算（テストUSDC）です。その裏の決済方法は、別の選択として扱います。

| 決済方法 | 状態 | 中身 |
|---|---|---|
| 台帳から1回いくらの固定額 | **実装済み（中継）** | 今の本人の決定（2026-10-17）。成否にかかわらず請求 |
| 台帳から実測の額 | **パッチ 0001 だけ（未適用）** | 見積りの上限を確保し、実測（≤ 見積り）で確定、残りを返す |
| 運営が立て替える | 未実装（整理だけ） | 運営が外部の請求を払い、本人の台帳に換算した額を請求する。要るもの：リクエストごとの利用ID、換算の出所と有効期限、精算の周期、換算差・端数を誰が負うかの本人の決定 |
| 本人自身のキー | 未実装（整理だけ） | 台帳は利用を記録するだけで、推論の請求は0。中継はその請求を確かめられない |

**外部APIの請求をUSDC残高から直接払えるとは仮定していません。** 台帳の請求は「本人の利用料」です。運営の実際の費用（手元のモデルの電気代、外部の請求）は、運営の記録（`operatorCosts`）に分けて残ります（DESIGN §6.5）。

価格表（`PriceBook`）の決まり：
- 状態は `TEST` か `PROPOSED` だけ（本番の値は作れない）。
- 費用は切り上げ、見積りを超えない。
- 外貨の換算には、出所を書いたレートが要る（なければ `NoRate`）。
- 中継の固定額と価格表が食い違えば、開始を断る（`PriceBookMismatch`）。

**⑤の実行層の限界：**
- 接続トークンを直接持つ者は、この層を通らずに `agent_act` を呼べます。この層は、モデルからは迂回できませんが、トークンの持ち主からは迂回できます。
- 予約は1つのプロセスの中で同期的に行うので、並行して動く実行どうしでは二重に使われません。ただし、複数のプロセスが同じ agent を動かす場合は守れません。
- どちらの限界も、中継で強制する（パッチ 0001）ことで解消します。

## 4. 必須の検証（要件5）

すべて `test/staking.test.mjs`（13件）。中継・台帳は本物、鎖とモデルは模擬です。

| 検証 | 結果 | 何で通ったか |
|---|---|---|
| 並行実行で予算を二重に使わない | 通過（5回くり返して安定） | 中継：台帳の同期的な確保。⑤：BudgetGuard の同期的な予約 |
| 再送・タイムアウト・再起動で二重請求・二重操作しない | 通過 | 返事が消えた後の再送は記録済みの結果（同じ requestId）。モデルのタイムアウトは1回分。中継の再起動中の呼び出しは「不明」になり、遅れた答えで1回だけ請求。⑤の再起動は記録から上限を数え直す |
| API課金済みでゲーム操作が失敗 | 通過 | モデルの 10,000 は確定のまま、ゲームの確保 15,000 は鎖の失敗で返る。追跡に「受理→返金→失敗」と出る。記憶は「失敗」 |
| 上限超過・権限外・失効を拒否 | 通過 | 1回の上限（ゲーム・モデル）、範囲外の行動、対象外の村、委任条件の期限、鎖上の委任の期限、残高不足 |
| 停止直後に新規操作が滑り込まない | 通過 | モデルが考えている間に停止 → その判断は送らない。考え中の料金は払う、と表示 |
| 受理と最終的な成功を混同しない | 通過 | 受理（送った）→着地→効果を別に扱う。隊商は「道を外れた」≠「着いた」（行き先の蓄えで閉じる）。隊商の判定は herald の形の fixture で確かめた（代理は隊商を送れない） |
| モデル障害の再試行で予算・回数を超えない | 通過 | 再試行も1回ずつ確保・請求・上限の対象。1日2回の上限なら、再試行5回を指定しても2回で止まる |

## 6. 残る技術的な不足

1. **中継での強制：** 1回の上限・カテゴリ別の上限・方針の期限・実測の請求は、パッチ 0001 を当てるまで、⑤の実行層だけにあります。
2. **資源の量・従う相手・依頼の期限**は、中継では強制できません。②の Grant が要ります。
3. **施設の利用**は、プログラムに命令がありません。
4. **実際に答えたモデルの記録：** 中継の runner の台帳は、別名を記録したままです（パッチ 0001 で `servedModel` を記録できるようにした。runner がそれを渡すのは別の変更が要る）。
5. **外部の提供者と、立て替えの精算**は、整理だけです。利用ID・換算の出所・精算の周期を本人が決めてから実装します。
6. **実モデル・本物の鎖・実ブラウザ**では、何も確かめていません。
7. **複数プロセス**で同じ agent を動かす場合、⑤の実行層の予約は守れません（中継の台帳も「1つの状態ファイルに1プロセス」：DESIGN §9）。
8. **session の枠は村に1つ**で、③の courier（外部プログラム）と代理の財布が取り合います（③の 04 §4）。
