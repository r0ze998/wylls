# ⑦ 表示契約：④・⑤ の状態と ① の協力入口

④（送信の取消と到着）、⑤（費用と手動復帰）、①（国の協力）の状態を、⑦ の画面がどう表示するかを決めた契約です。状態の中身と規則は各担当のもので、⑦ は決めていません。

**④・⑤・① の成果物はまだ受け取っていません。** そのため、この契約は報告の要約だけをもとにした⑦側の要求です。受け取った時点で、名前と遷移を突き合わせる必要があります（§4）。

実装は接続パッチ 0004 にあります。
- `permutation-server/web/frontier/hud/statusview.mjs`：④・⑤ の状態の表示
- `permutation-server/web/frontier/hud/coopentry.mjs`：① の協力入口

テストは `permutation-gateway/test/web-frontier-ws07-contracts.test.mjs`（8件、通常テスト）と、画面テスト `screens/ws07-s1.screen.mjs` の表示契約の項目です。

## 1. 共通の決まり

- 各表示は `{ok, key, symbol, text, details, tone, errors}` を返します。
- 状態は**記号と文**で伝えます。`tone` は CSS の class 名で、同じことを繰り返すだけです。色だけでは何も伝えません。強制カラー（白黒）でも記号と文が残ることを、画面テストで確かめました。
- 知らない状態や、欠けた欄があれば、「状態を受け取れていません」（記号 `?`）と表示し、`errors` に理由を並べます。**推測で埋めません。**
- 欄を省いた場合と、空であることがわかっている場合は、別の状態として扱います。
  - 例：取消の前に成立した分（`settled`）は、欄が無ければ `null`（まだ受け取っていない）、`[]` なら「成立した分はない」です。

## 2. ④：取消の3段階と到着量

### `cancelView({ stage, signedPending?, settled? })`

| stage | 記号 | 表示 | 欠けたとき |
|---|---|---|---|
| `stopNew` | ‖ | 新しい送信を止めました／署名済みの要求はまだ止まっていません。チェーンの確認を待ちます | — |
| `awaitSigned` | ⌛ | 署名済みの要求 N 件の確認を待っています／確認が済むまで、取消は終わっていません | `signedPending` が無ければ「件数は受け取っていません」 |
| `cancelled` | ■ | 取消が終わりました／取消の前に成立した分は戻りません：（④が渡す文の一覧） | `settled` が無ければ「まだ受け取っていません」。`[]` なら「ありません」 |
| それ以外 | ? | 状態を受け取れていません | `errors: ['stage: …']` |

### `arrivalView(x)`：隊商の到着（v5 で補正）

**経緯**
- v2 の3状態（`unverified`・`partial`・`full`）は v4 で廃止しました。倉庫宛てでは、決着の記録と実際に入った量が一致しないためです。
- v5 では次の2点を補正しました（パッチ 0011）。
  - 「全量」「一部」の比較の基準を、文に必ず出すようにしました。
  - 「入った量が分かるか」と「送付記録と比べられるか」を、別の判定にしました。

量は「資源の順に 8 つの整数」で渡します。単位は記録の単位で、`cargo_log` は内部の 1/1000 単位を整数に切り捨てています。

**v7（パッチ 0013）**：村に入った量は記録の数を**下限**として「n 以上」と言います（資源ごとに 1 未満多く入っていることがある）。すべて 0 なら「0 以上」で、「なし」とは言いません。全量・一部・入った量のみ、のどれも同じです。

| state | 記号 | 表示 | 判定 |
|---|---|---|---|
| `overdue`（`bell`） | … | 到着予定のターン N を過ぎました。まだ決着していません | 隊商 feed にまだ載っていて、予定ターンを過ぎた。**「着いた」とは言わない** |
| `settledUnverified`（`why`） | ? | 倉庫宛て（`vault`）は「到着しましたが、入った量は確認できません（最大 n）」（v7）。それ以外は「決着しました。入った量はまだ確かめられていません」 | 入った量：わからない。理由（`why`）は `vault`、`dstUnknown`、`rulesUnknown`、`outcomeUnknown` |
| `misdelivered`（`recorded?`、v7） | → | 別の場所に着きました（原因を確認中）／この隊商の到着としては、入った量を数えません | 送付記録の行き先と違う場所で決着し、奪取の記録を読んでいない。原因や相手を言わない（④ の `DestinationMismatch`） |
| `unread`（v7） | ? | 状態不明：道中の一覧から外れましたが、終わりの記録をまだ読んでいません | ページを開いているあいだに一覧から消え、決着も略奪もまだ読んでいない。メモリだけで、再読込のあとは出さない |
| `verifiedIntake`（`intake`、`compare`） | ○ | 村に入った量：（量）以上／比べない理由／単位 | 入った量：わかる（下限）。比較：できない（`compare` は `sentUnknown`、または奪った側の到着の `dstChanged`） |
| `verifiedPartial`（`basis: 'sentRecord'`、`sent`、`arrived`、`wornBps?`） | ◐ | **送付記録の数量に対して**一部が入りました：（量）／送付記録の数量：（量）／比べた基準／差の理由は決めない／単位 | 入った量：わかる。比較：できる（一部） |
| `verifiedFull`（`basis: 'sentRecord'`、`sent`、`arrived`、`wornBps?`） | ● | **送付記録の数量に対して**全量が入りました：（量）／比べた基準／単位 | 入った量：わかる。比較：できる（全量） |
| `lost` | ✕ | 積荷は失われました／行き先が無くなっていたため、どこにも入っていません（確定） | `outcome` 1 |

- 「全量」と「一部」は、`basis: 'sentRecord'` が無ければ表示しません（「状態を受け取れていません」になります）。
- 比べた基準の文は「比べた基準は送付記録の数量です。送付記録の数量は経路の減少を引いたあとの量で、最初に積んだ量と経路の損失は、この記録からは確定しません」です。
- 送付記録に経路の減少率（`worn_bps`）があれば、「送付記録には経路の減少率 X% が記されています」と、記録どおりに引くだけです。最初に積んだ量は逆算しません。

**「入った量がわかる」の条件（すべて）**
1. 決着の結果が「配送」（`outcome` 0）。
2. 宛先の種類が村（`dst` の種類 1）。
3. シーズンのプログラムの版が S1（`program_version` 4）。根拠は `Holding::credit` で、記録の積荷を上限なしでそのまま加えます。
4. 数量は記録の単位で言う。

**「送付記録と比べられる」の条件（上に加えて）**
5. 同じ隊商の `CARAVAN_SENT` を読めている。
6. その行き先（種類・州・場所・世代・マス）が、決着の行き先と完全に同じ。

**倉庫宛て**
- 倉庫は資源ごとに `min(have + c, max(cap, have))` で切り捨てますが、記録には元の積荷が載ります。
- その配送の実加算量の記録か、検証できる計算根拠（`REQUESTS.ja.md` ④-5）が無いあいだは、常に「決着・実入荷未検証」です。
- 倉庫の現在の残高や、残高の差からは決めません。

**元の送り主には到着を言わない場合**
- 焼かれた隊商：空のまま進み、`outcome` 0（配送）で記録されます。持ち主が無いので、到着の項目自体を作りません。
- 奪われた隊商：持ち主が奪った側に変わるので、元の送り主には到着を出しません。
- 奪った側の到着は、送付記録と行き先が違うので比べず、「入った量のみ確定」になります。
- どれも回帰テストで固定しています（`web-frontier-ws07-connect.test.mjs` の burned、taken）。

**④ の実契約との照合（未）**
- 受け口 `caravanArrival` に ④ が登録すると、道中の隊商の行は ④ の状態に置き換わります。
- 実物との契約テストが通るまで、画面テストの mock はテストの中でだけ登録します。本番の画面は、推測した ④ の状態を出しません。

## 3. ⑤：費用の4区分と手動復帰

### `costView({ phase, amounts? })`

| phase | 記号 | 表示 |
|---|---|---|
| `reserved` | ◇ | 予約：（額）／まだ支払っていません。使える量からは引いて見せます |
| `committed` | ◆ | 確定：（額）／支払いが確定しました |
| `unsettled` | ◇? | 未確定（額はまだ決まっていません）、または「未確定：最大（額）」／予約とも確定とも違います |
| `released` | ↺ | 予約の解放：（額）／予約が戻りました。使える量に戻して数えます |

「支払った」と言うのは `committed` のときだけです。

### `spendable(have, costs, { committedInHave })`

手持ちから費用を引いた、使える量を返します。
- 予約分と、未確定分の最大額を引きます。
- 未確定のものが1つでもあれば、`uncertain: true` を返します。
- 確定分を引くかどうかは、`committedInHave` の値で決まります。これは「確定した費用は、すでに手持ちから引かれているか」で、**⑤ が決めることです。** 渡されなければ誤りとして返します。

### `manualView({ signedPending? })`

| 入力 | 表示 |
|---|---|
| `signedPending: N`（N > 0） | 手動に戻しました／すでに署名した操作 N 件は止まらずに進みます |
| `signedPending: 0` | 署名済みで進行中の操作はありません |
| 欠けている | すでに署名した操作は止まりません（件数は受け取っていません） |

手動に戻しても、すでに署名した操作は止まりません。止まったように見せる表示（ボタンを灰色にするだけ、など）はしません。

## 4. ①：協力入口（最小の接続点）

- S1 の村カード（`screens/s1.mjs` の「交易と防備」）の、「国の議会」の下に枠を1つ置きました。
- ① が登録しなければ、枠は空で、画面は今までと同じです。
- 国どうしの協力や中央塔のルールは、⑦ では決めていません。

```js
import { registerCoopEntry } from './hud/coopentry.mjs';
const off = registerCoopEntry({
  id: 'nation-coop',
  title: () => L`…`,                         // ボタンの文（①が決める）
  state: FS => ({ available, why }),          // 押せるか、押せないならその理由（①が決める）
  open: FS => { … },                          // 押したときの動き（①が決める）
});
```

- 押せないときは、ボタンを無効にし、理由をその下に出します。理由がなければ「理由を受け取れていません」と出します。
- 押されると、画面は HUD の操作 `coop-open` から `open` を呼びます。呼ぶ前に `state` をもう一度確かめます。
- `state` が例外を投げたら、ボタンを無効にします。

## 5. 各担当から受け取る必要があるもの（未受領）

v3 で、より具体的な一覧を `REQUESTS.ja.md` に移しました。受け口（`registerStatusSource`）と、S1 のデータからつないだ到着量については `INTEGRATION.ja.md` §0b を見てください。以下は v2 のときの一覧です。

ファイル名は推測していません。どの内容が要るかを並べます。

**④ から**
1. 取消の状態の定義と遷移：新規停止 → 署名済み要求の確認待ち → 取消完了。状態名と、どの記録やアカウントの欄で判定するか。
2. 署名済みで未確認の要求を数える方法（`signedPending` の出どころ）。
3. 取消の前に成立した効果を表す方法（`settled` の中身と、プレイヤーに見せる文）。
4. 到着量を「確かめた」と言える根拠：どの記録か。未検証と部分到着が、何で分かれるか。
5. 上の挙動を固定している ④ のテスト。

**⑤ から**
1. 費用の4区分（予約・確定・未確定・解放）の定義と遷移、それを読む場所。
2. 確定した費用は、すでに手持ち（村の倉の値）から引かれているか（`committedInHave`）。
3. 未確定の費用に上限があるか（最大額を出せるか）。
4. 手動復帰の操作と、署名済みで進行中の操作を数える方法（`signedPending`）。
5. 上の挙動を固定している ⑤ のテスト。

**① から**
1. 協力入口を出す条件（`state` の規則）と、押したときに開くもの（画面か手続き）。
2. ボタンと理由の文（日本語と英語）。
3. 国どうしの協力と中央塔のルールの文書（⑦ が文言の検査に使う）。

## 6. 接続するときの手順

1. 受け取った状態名を、§2・§3 の名前と突き合わせます。違えば、各担当の側に変換用のアダプタ（小さな対応表）を置きます。⑦ の表示関数は変えずに済むようにしています。
2. アダプタのテストで、各状態が `ok: true` かつ `errors: []` になることを確かめます。
3. 画面に置く場所（④ の隊商カード、⑤ の費用欄など）は、各担当の画面に `renderStatus(view)` を足すだけです。⑦ の側で、他担当の画面を直接は変えていません。
