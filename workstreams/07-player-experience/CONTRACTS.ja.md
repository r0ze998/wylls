# ⑦ 表示契約：④・⑤ の状態と ① の協力入口

④（送信の取消と到着）、⑤（費用と手動復帰）、①（国の協力）の状態を、⑦ の画面がどう表示するかを決めた契約です。状態の中身と規則は各担当のもので、⑦ は決めていません。

**④・⑤・① の成果物はまだ受け取っていません。** そのため、この契約は報告の要約だけをもとにした⑦側の要求です。受け取った時点で、名前と遷移を突き合わせる必要があります（§4）。

実装は接続パッチ 0004 にあります。
- `permutation-server/web/frontier/hud/statusview.mjs`：④・⑤ の状態の表示
- `permutation-server/web/frontier/hud/coopentry.mjs`：① の協力入口

テストは `permutation-gateway/test/web-frontier-ws07-contracts.test.mjs`（8件、通常テスト）と、画面テスト `screens/ws07-s1.screen.mjs` の表示契約の項目です。

## 1. 共通の決まり

- 各表示は `{ok, key, symbol, text, details, tone, errors}` を返します。
- 状態は**記号と文**で伝えます。`tone` は CSS の class 名で、同じことを繰り返すだけです。色だけでは何も伝えません。強制カラー（白黒）でも記号と文が残ることを、画面テストで確かめました。
- 知らない状態や、欠けた欄があれば、「状態を受け取れていません」（記号 `?`）と表示し、`errors` に理由を並べます。**推測で埋めません。**
- 欄を省いた場合と、空であることがわかっている場合は、別の状態として扱います。
  - 例：取消の前に成立した分（`settled`）は、欄が無ければ `null`（まだ受け取っていない）、`[]` なら「成立した分はない」です。

## 2. ④：取消の3段階と到着量

### `cancelView({ stage, signedPending?, settled? })`

| stage | 記号 | 表示 | 欠けたとき |
|---|---|---|---|
| `stopNew` | ‖ | 新しい送信を止めました／署名済みの要求はまだ止まっていません。チェーンの確認を待ちます | — |
| `awaitSigned` | ⌛ | 署名済みの要求 N 件の確認を待っています／確認が済むまで、取消は終わっていません | `signedPending` が無ければ「件数は受け取っていません」 |
| `cancelled` | ■ | 取消が終わりました／取消の前に成立した分は戻りません：（④が渡す文の一覧） | `settled` が無ければ「まだ受け取っていません」。`[]` なら「ありません」 |
| それ以外 | ? | 状態を受け取れていません | `errors: ['stage: …']` |

### `arrivalView(x)`：隊商の到着（v5 で補正）

**経緯**
- v2 の3状態（`unverified`・`partial`・`full`）は v4 で廃止しました。倉庫宛てでは、決着の記録と実際に入った量が一致しないためです。
- v5 では次の2点を補正しました（パッチ 0011）。
  - 「全量」「一部」の比較の基準を、文に必ず出すようにしました。
  - 「入った量が分かるか」と「送付記録と比べられるか」を、別の判定にしました。

量は「資源の順に 8 つの整数」で渡します。単位は記録の単位で、`cargo_log` は内部の 1/1000 単位を整数に切り捨てています。

**v7（パッチ 0013）**：村に入った量は記録の数を**下限**として「n 以上」と言います（資源ごとに 1 未満多く入っていることがある）。ただし記録は `u32::MAX`（4,294,967,295）で飽和するので、その値に達した資源があるときは「1 未満」と言わず、「そこに達した資源は、記録よりどれだけ多く入ったかわかりません」と言います。下限であることは変わりません（2026-11-17）。すべて 0 なら「0 以上」で、「なし」とは言いません。全量・一部・入った量のみ、のどれも同じです。

| state | 記号 | 表示 | 判定 |
|---|---|---|---|
| `overdue`（`bell`） | … | 到着予定のターン N を過ぎました。まだ決着していません | 隊商 feed にまだ載っていて、予定ターンを過ぎた。**「着いた」とは言わない** |
| `settledUnverified`（`why`） | ? | 倉庫宛て（`vault`）は「到着しましたが、入った量は確認できません（記録の積荷：n）」（2026-11-17 訂正。v7 の「最大 n」は誤り：記録は 1 未満の切り捨てと上限での飽和なので、入った量の上限にならない。全 0 の記録も「記録の積荷：0」で、入った量 0 とは言わない）。それ以外は「決着しました。入った量はまだ確かめられていません」 | 入った量：わからない。理由（`why`）は `vault`、`dstUnknown`、`rulesUnknown`、`outcomeUnknown` |
| `misdelivered`（`recorded?`、v7） | → | 別の場所に着きました（原因を確認中）／この隊商の到着としては、入った量を数えません | 送付記録の行き先と違う場所で決着し、奪取の記録を読んでいない。原因や相手を言わない（④ の `DestinationMismatch`） |
| `unread`（v7） | ? | 状態不明：道中の一覧から外れましたが、終わりの記録をまだ読んでいません | ページを開いているあいだに一覧から消え、決着も略奪もまだ読んでいない。メモリだけで、再読込のあとは出さない |
| `verifiedIntake`（`intake`、`compare`） | ○ | 村に入った量：（量）以上／比べない理由／単位 | 入った量：わかる（下限）。比較：できない（`compare` は `sentUnknown`、または奪った側の到着の `dstChanged`） |
| `verifiedPartial`（`basis: 'sentRecord'`、`sent`、`arrived`、`wornBps?`） | ◐ | **送付記録の数量に対して**一部が入りました：（量）／送付記録の数量：（量）／比べた基準／差の理由は決めない／単位 | 入った量：わかる。比較：できる（一部） |
| `verifiedFull`（`basis: 'sentRecord'`、`sent`、`arrived`、`wornBps?`） | ● | **送付記録の数量に対して**全量が入りました：（量）／比べた基準／単位 | 入った量：わかる。比較：できる（全量） |
| `lost` | ✕ | 積荷は失われました（記録の積荷：n）／行き先が無くなっていたため、どこにも入っていません（確定） | `outcome` 1。記録の積荷は記録の数のまま示し、全 0 は「0」で「なし」とは言いません（1 未満の端数は記録に残らないため。2026-11-17） |

- 「全量」と「一部」は、`basis: 'sentRecord'` が無ければ表示しません（「状態を受け取れていません」になります）。
- 比べた基準の文は「比べた基準は送付記録の数量です。送付記録の数量は経路の減少を引いたあとの量で、最初に積んだ量と経路の損失は、この記録からは確定しません」です。
- 送付記録に経路の減少率（`worn_bps`）があれば、「送付記録には経路の減少率 X% が記されています」と、記録どおりに引くだけです。最初に積んだ量は逆算しません。

**「入った量がわかる」の条件（すべて）**
1. 決着の結果が「配送」（`outcome` 0）。
2. 宛先の種類が村（`dst` の種類 1）。
3. シーズンのプログラムの版が S1（`program_version` 4）。根拠は `Holding::credit` で、記録の積荷を上限なしでそのまま加えます。
4. 数量は記録の単位で言う。

**「送付記録と比べられる」の条件（上に加えて）**
5. 同じ隊商の `CARAVAN_SENT` を読めている。
6. その行き先（種類・州・場所・世代・マス）が、決着の行き先と完全に同じ。

**持ち主が確かめられない隊商の決着（帰ってきた人への要約、2026-11-17）**
- 送り主があなたで、いまの持ち主が記録から確かめられない隊商の決着は、記録の `outcome` で言い分けます。0 は「到着が記録されました」、1 は「積荷が失われたと記録されました」、それ以外は「決着が記録されました。結果を記録から読めないため、着いたとも失われたとも言いません」。1 やそれ以外を「到着」とは言いません（`hud/returnsum.mjs`・`hud/returnwords.mjs`）。
- あなたが持ち主の隊商でも、`outcome` が 0 でなければ「届いた」（`delivered`）としては扱いません。到着の表示は `arrivalSettled` の `outcomeUnknown` です。

**倉庫宛て**
- 倉庫は資源ごとに `min(have + c, max(cap, have))` で切り捨てますが、記録には元の積荷が載ります。
- 記録の積荷は `floor(milli / 1000)`、`u32::MAX` で飽和です（`permutation-frontier/src/proc/caravan.rs` `cargo_log`）。倉庫はミリ単位で加えてから切り捨てるので、記録の数は入った量の下限にも上限にもなりません。表示は記録の数をそのまま「記録の積荷」と言い、「最大」とは言いません（2026-11-17）。
- その配送の実加算量の記録か、検証できる計算根拠（`REQUESTS.ja.md` ④-5）が無いあいだは、常に「決着・実入荷未検証」です。
- 倉庫の現在の残高や、残高の差からは決めません。

**元の送り主には到着を言わない場合**
- 焼かれた隊商：空のまま進み、`outcome` 0（配送）で記録されます。持ち主が無いので、到着の項目自体を作りません。
- 奪われた隊商：持ち主が奪った側に変わるので、元の送り主には到着を出しません。
- 奪った側の到着は、送付記録と行き先が違うので比べず、「入った量のみ確定」になります。
- どれも回帰テストで固定しています（`web-frontier-ws07-connect.test.mjs` の burned、taken）。

**④ の実契約との照合（未）**
- 受け口 `caravanArrival` に ④ が登録すると、道中の隊商の行は ④ の状態に置き換わります。
- 実物との契約テストが通るまで、画面テストの mock はテストの中でだけ登録します。本番の画面は、推測した ④ の状態を出しません。

## 3. ⑤：費用の4区分と手動復帰

### `costView({ phase, amounts? })`

| phase | 記号 | 表示 |
|---|---|---|
| `reserved` | ◇ | 予約：（額）／まだ支払っていません。使える量からは引いて見せます |
| `committed` | ◆ | 確定：（額）／支払いが確定しました |
| `unsettled` | ◇? | 未確定（額はまだ決まっていません）、または「未確定：最大（額）」／予約とも確定とも違います |
| `released` | ↺ | 予約の解放：（額）／予約が戻りました。使える量に戻して数えます |

「支払った」と言うのは `committed` のときだけです。

### `spendable(have, costs, { committedInHave })`

手持ちから費用を引いた、使える量を返します。
- 予約分と、未確定分の最大額を引きます。
- 未確定のものが1つでもあれば、`uncertain: true` を返します。
- 確定分を引くかどうかは、`committedInHave` の値で決まります。これは「確定した費用は、すでに手持ちから引かれているか」で、**⑤ が決めることです。** 渡されなければ誤りとして返します。

### `manualView({ signedPending? })`

| 入力 | 表示 |
|---|---|
| `signedPending: N`（N > 0） | 手動に戻しました／すでに署名した操作 N 件は止まらずに進みます |
| `signedPending: 0` | 署名済みで進行中の操作はありません |
| 欠けている | すでに署名した操作は止まりません（件数は受け取っていません） |

手動に戻しても、すでに署名した操作は止まりません。止まったように見せる表示（ボタンを灰色にするだけ、など）はしません。

## 4. ①：協力入口（最小の接続点）

- S1 の村カード（`screens/s1.mjs` の「交易と防備」）の、「国の議会」の下に枠を1つ置きました。
- ① が登録しなければ、枠は空で、画面は今までと同じです。
- 国どうしの協力や中央塔のルールは、⑦ では決めていません。

```js
import { registerCoopEntry } from './hud/coopentry.mjs';
const off = registerCoopEntry({
  id: 'nation-coop',
  title: () => L`…`,                         // ボタンの文（①が決める）
  state: FS => ({ available, why }),          // 押せるか、押せないならその理由（①が決める）
  open: FS => { … },                          // 押したときの動き（①が決める）

```

- 押せないときは、ボタンを無効にし、理由をその下に出します。理由がなければ「理由を受け取れていません」と出します。
- 押されると、画面は HUD の操作 `coop-open` から `open` を呼びます。呼ぶ前に `state` をもう一度確かめます。
- `state` が例外を投げたら、ボタンを無効にします。

## 留守の要約：読めなかったこと・確認の位置の保存（2026-11-17、Lane C）

実際の導線：`app.mjs` の `awayPump` → `hud/awayread.mjs`（ページを読む）→ `hud/returnsum.mjs`（`summarize`・`confirm`・`loadMarks`）→ `hud/returnwords.mjs`（`headText`・`confirmText`・`confirmedText`）。

- **読めなかったことと、記録が無いことを分ける。** 範囲内に読めた記録が 0 件のとき、読み込みが最後まで終わっていれば「新しい記録はありません」と言います。失敗した・続きがある・欠けがあるときは「新しい記録があるかどうかは、まだわかりません」と言い、「読めた分だけを出しています」とも言いません。確認の案内も、この場合は「まだ記録を読めていないため、確認の位置は進めません」で、「新しく確認する記録はありません」とは言いません。
- **読めない記録は数えて伝える。** ページの中で中身を解読できなかった記録（`bad`）は推測せず、件数を「読めない記録が N 件ありました。その中身は推測しません」と伝えます。範囲内に読めた記録が無く、読めない記録だけがあるときは「新しい記録はありません」とは言わず「中身を読めた新しい記録はありません」と言い、確認の案内も「読めない記録のほかに、新しく確認する記録はありません」と言います。確認の位置の進め方は変えていません。
- **確認の位置（主）と、最後に使ったウォレットの記録（補助）の保存を分ける。** 確認の位置を書いて読み戻せたときだけ「確認済みにしました」と言います。補助の `ws07-return:last` だけ保存できなかったときも、確認の位置は進んでいるので失敗とは言わず、その旨を添えます（`lastSaved: false`）。画面では、そのときだけ要約の先頭の通知を閉じずに残し、その言葉に替えます（「確認した」はもう出しません）。別のタブが間に先へ進めていたら「すでに確認済みです」と言います。主が保存できなければ、これまでどおり「保存できませんでした。次に開いたときも同じ範囲が出ます」です。
- **確認の位置は世界に結び付ける。** 新しく保存する確認の位置と補助の記録には、固定した世界（クラスター・プログラム・シーズンの口座。シーズンの口座は `setPin` が導き、ヘラルドの記録と照合したもの）を記します。読み込みの範囲（scope）も同じ世界を含み、世界が固定されていないあいだは読み込みません（値を作りません）。遅れて届いた別の世界の読み込みは採らず、「確認した」は要約を読んだときの世界で、いまもその世界のときだけ保存します。違う世界の確認の位置は使いません（同じシーズン番号と同じウォレットでも、別の世界の位置から読むと、この世界の未読を飛ばすため）。世界を記していない以前の確認の位置は、これまでどおり読みます。保存先の鍵（`ws07-return:{シーズン}:{ウォレット}`）は変えていないので、別の世界で確認すると、前の世界の位置は置き換わります（その世界は、次は最初の見方から読み直し、未読を飛ばしません）。

## 地図の上の出来事（moments）は同じ世界の中だけで比べる（2026-11-17、Lane C）

実際の導線：`app.mjs` の `checkMoments`（毎秒）→ `people/moments.mjs` の `momentSnapshot`・`detectMoments` → 効果の bus → `fx/stage.mjs`。

- 前回の見え方と今回の見え方を比べるのは、固定した世界（クラスター・プログラム・シーズンの口座。`setPin` が導き、ヘラルドの記録と照合したもの）が同じときだけです。世界が固定されていない状態も一つの状態として扱い、値を作りません。
- 世界が変わったら、前回の見え方とあなたの村の一覧を捨てます。読み込み側は、読んだ世界を記録します：州の記録は `world` を持ち（`controller.mjs` の `loadEnvelope`。別の世界のために始めた読み込みの答えは何も書かずに捨て、`latestEnvelope` は同じ世界の記録どうしだけを番号で比べます）、あなたの村の一覧は `FS.holdingsWorld` を持ちます（`applyMeResult`。`refresh` は始めたときの世界のままのときだけ反映します）。配列や記録が入れ替わったことだけでは、この世界のために読んだ証拠にしません。
- あなたの村の一覧がこの世界のために読まれるまで（村があるとき）は見え方を取りません。その後は、この世界のために読んだ州だけを見ます。村の暮らしの記録（収穫・建設）は、読み込み側がこの世界のために読み直したと記録してから（`FS.lifeWorld`、`refreshChronicle`）見ます。そのとき最初に見えた暮らしは基準で、知らせではありません。その後の最初の変化からは、いつもどおり知らせます。キーが消えたことや、配列・記録が入れ替わったことは、出どころの証拠にしません。
- 世界の区別には、固定の**世代**も使います（`fchainio.setPin`：別の世界の固定に成功したときだけ一つ進み、同じ世界の読み直しや失敗では進みません）。A → B → A は三つの世代なので、最初の A で始めた読み込みの答えや記録は、B のあとに固定し直した A のものとして使いません。読み込みの範囲・読み込み側の記録（州の `world`、`FS.holdingsWorld`、`FS.lifeWorld`）・出来事の比較・報告・留守の要約の範囲は、この世代を含みます。端末に保存する留守の確認の位置は、読み込み直しても合うように世界そのもの（世代なし）を記します。
- そのため、別の世界の同じ座標の村・建物・軍勢を「村を失った」「村を取った」「建物ができた」とは言いません。新しい世界で最初に見えたものも出来事とは言いません（「最初の読み込みは知らせではない」のまま）。同じ世界の中の新しい出来事は、これまでどおり知らせます。

## 賞金の残高表示・行軍・領土の読み込みも、読んだ世界の中だけで反映する（2026-11-17、Lane C）

実際の導線：`controller.mjs` の `refreshPrize`・`refreshMarches`（`readMarches`）・`refreshConquest`（`refreshS1`・`refreshKeepEvents`・`wantKeepHistory` を含む）。

- どの読み込みも、始めたときの固定の世界（世代を含む `providerWorld()`）を覚え、待ったあとに書く前に、まだ同じかを確かめます。違えば何も書きません。A → B → A は三つの世代なので、最初の A で始めた読み込みの答えを、あとの A に書きません。
- 賞金の読み込み（`refreshPrize`）は、ウォレット・中継先（relay）・世界の三つが始めたときと同じときだけ、賞金の情報と成績表を書きます。この理由で捨てた読み込みは、間隔の制限を自分の分だけ解き、新しいウォレット・中継先・世界ですぐ読み直せるようにします。支払い・参加・テストトークンの受け取り・受け取りの権利の意味と実行は変えません（`paidJoin`・`faucet`・`payAndJoin` はそのまま。参加の経路が `FS.prize` で決まることもそのまま）。
- 行軍の読み込み（`readMarches`）の身元（ヘラルド・ローカルプレイ・村・帳簿の鍵）に世界を加えます。最後の書き込み（帳簿の保存・`FS.marches`・`FS.bellItems`・`FS.formingBells`）は同じ身元のときだけです。自分で鍵を出す送信（self-reveal）とその記録は変えません。
- 領土の読み込み（`refreshConquest`）は、要求の番号と世界をまとめた `current()` で、待ったあとのすべての確認をします。世界が変わったら、領土の状態（拠点・順位・最終結果・読んだ日の記録・拠点の履歴）を前の世界のものとして使わず、「読み込み中」から始め直します。S1 の隊商・構造物・国家も、読んだ世界の記録だけを持ちます（失敗や NotFound のときに前の世界の内容を残しません）。世界の印のない状態は「世界なし」として扱います。
- 同じ世界の中の順序・間隔・「まだわからない」の出し方は変えません。

## 地図の範囲・環の一覧・環の概要も、読んだ世界の中だけで反映する（2026-11-17、Lane C）

実際の導線：`app.mjs` の `loadSeason`（固定）→ `controller.adoptPinnedWorld`。`controller.mjs` の `refreshOverviews`。`app.mjs` の `loadOverviews`。どちらの読み込みも、共有の読み込み列 `map/overviews.mjs` の `readOverviews` を通ります。

- `refreshOverviews` の処理（相乗り・キャッシュ・完了の印）は、ヘラルドと固定の世界（世代を含む）の両方が同じときだけ有効です。シーズンの記録の答えは、待ったあとも同じ世界のときだけ反映します（記録・範囲・環の一覧・`FS.season`）。
- 共有の読み込み列は、呼び出し側から今の世界（`source`）を受け取ります。各読み込みには、作ったときの世界が付きます。世界が変わったら、読み込み側が替わったときと同じく、待っている読み込みは false で終わります。世界がもう固定されていない読み込みは、始めず、答えを保存せず、false で終わります。`source` を渡さない呼び出し方は、これまでと同じです。
- 同じ世界の中は変えません。同時に四つまでの読み込み、優先の順、範囲が変わったときの読み直し、一部だけ読めたときに次の機会に読み直すことは、そのままです。
- 別の世界を固定した直後、その世界の記録を反映する前に、前の世界の読み込みを忘れます：
  - 環の概要（地図が同じ入れ物を持っているので、中身だけを空にします）
  - 概要を取ったときの州の数（新しい世界のすべての環を読み直すため）
  - 一部だけ読んだ環の一覧
  - 完了の印
  - 領土と S1 の状態

  最初の固定と、同じ世界の固定では、何も忘れません。
- 領土が無効の世界に移っても、前の世界の領土と S1 の状態は見せません。出来事の一覧・地図の効果・報告・調べる画面・S1 の歩みは、領土が有効かを確かめずにこれらを読みます。そのため `refreshConquest` は、有効かを確かめる前に、別の世界の状態を捨てます。
