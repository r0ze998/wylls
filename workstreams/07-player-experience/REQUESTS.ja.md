# ④・⑤・① から受け取る必要があるもの（v5 で更新、2026-10-30 時点）

**確かめたこと。** `origin` の全ブランチを取り直して探しましたが、④・⑤・① の契約の実物（報告にある `bd415e7`、`ba3c180b` を含む）はありませんでした。新しく出ていた作業は ③ の `2f8ec700`（外部プログラムから CPI で SendCaravan）だけでした。

そのため、⑦ は次の2つに分けて進めました。
- **S1 のデータとプログラムのルールだけでつなげるところは、つないだ（v4 の 0006）。**
  - 到着は状態を分けて出す（予定超過・未決着／決着・実入荷未検証／入った量のみ確定（比較不可）／送付記録の数量に対して一部／送付記録の数量に対して全量／損失確定）。v5 で「入った量が分かるか」と「送付記録と比べられるか」を別の判定にし、全量・一部には比較の基準（送付記録の数量）を明記した。
  - 倉庫宛ては常に未検証（④-5）。
  - v3 の「`CARAVAN_SENT.cargo` と `CARAVAN_SETTLED.cargo` を比べて全部か一部かを決める」は、倉庫宛てで誤るので廃止した。
- **持ち主の実物が要るところは、受け口（`registerStatusSource`、`registerCoopEntry`）だけを置いた。** 登録が無ければ画面は今までと同じです。

以下は、受け口に何を渡してほしいかと、その出どころとして受け取りたいものです。

## ④（隊商の取消と到着）

### 調べた事実

- プログラム（`permutation-frontier/src`）に、隊商の取消（cancel）の命令はありません。
- クライアントにも、取消の操作や、署名済みで未確認の要求の一覧はありません。
  - `FS.inFlight` はありますが、通信中の要求の数で、署名済みの要求の数ではありません。
- したがって、取消の3段階は ④ が新しく作るものと考えられます。⑦ はそれを推測では作っていません。

### 受け口

`registerStatusSource('caravanCancel', (FS, c) => input | null)`、`registerStatusSource('caravanArrival', (FS, c) => input | null)`（v4 で追加。登録すると、道中の隊商の行の到着は ④ の状態に置き換わる）

- `c` は隊商 feed の1件です（`{ownerTag, seq, …}`）。
- `input` は `{stage: 'stopNew' | 'awaitSigned' | 'cancelled', signedPending?, settled?}` です。

### 受け取りたいもの

| # | 内容 | なぜ要るか |
|---|---|---|
| ④-1 | 取消の状態を定義しているファイル：状態名、遷移、どの操作で変わるか | `stage` の対応表を作るため |
| ④-2 | **`signedPending` の出どころ**：署名済みで未確認の要求を、どこで保持しているか（端末の保存領域のキー、relay のキュー、herald のファイルなど）と、何で「確認済み」と判定するか（署名の確認状態、記録の seq など） | 「署名済みの要求 N 件の確認を待っています」の N を出すため。出どころが無いと「件数は受け取っていません」と表示する |
| ④-3 | 取消の前に成立した効果の表し方：どの記録か、プレイヤーに見せる文 | `settled` を埋めるため。欄が無ければ「まだ受け取っていません」と表示する |
| ④-4 | **「到着」の状態の名前と定義**：⑦ の状態（予定超過・未決着／決着・実入荷未検証／入った量のみ確定（比較不可）／送付記録の数量に対して一部／送付記録の数量に対して全量／損失確定、`CONTRACTS.ja.md` §2）と ④ の状態がどう対応するか。とくに ④ の「全量」が何を基準にするか（送付記録の数量か、最初に積んだ量か） | 受け口 `caravanArrival` に登録したときに、どの状態をどの文で出すかを決めるため。⑦ の状態は ④ と照合していない |
| ④-4 の照合（v7） | `origin/preserve/ws04-a967f5f1` の `workstreams/04-execution/docs/HANDOFF.ja.md` §2 と、⑦ の文を突き合わせた（`INTEGRATION.ja.md` §0f.2）。下限「以上」、倉庫宛ての「最大」、0 の意味、別の行き先の説明を ④ に合わせた（0013）。④ の状態名（`DeliveredUnverified`、`DestinationMismatch` ほか）から ⑦ の状態への変換（アダプタ）と、その契約テストはまだ無い | 受け口 `caravanArrival` に ④ の実物を登録するため |
| ④-5 | **倉庫宛ての、その配送の実加算量**。次のどちらかが要る。(a) その配送で倉庫に実際に加わった量を載せた記録（たとえば `CARAVAN_SETTLED` に資源ごとの実加算量を足す。あるいは別の記録）。(b) 検証できる計算根拠：決着を処理したその命令の中での、資源ごとの加算前の残高と上限（`settle_caravan` の `have` と `cap`）を、その配送に結びつけて残すもの。**倉庫の現在の残高や、2つの時点の残高の差だけでは確定できない**ので要求しない（同じ倉庫には他の配送、取り出し、奪取が同じ間に重なりうる） | `settle_caravan` は資源ごとに `min(have + c, max(cap, have))` で切り捨てるのに、`CARAVAN_SETTLED.cargo` は元の積荷のまま。(a) か (b) が無いあいだ、⑦ は倉庫宛てを「決着・実入荷未検証」のままにする |
| ④-6 | 上の挙動を固定している ④ のテスト | 受け口のアダプタのテストに使うため |
| ④-7 | **村宛ての判定の前提が ⑦ と同じか**。⑦ は次の4つがそろうときだけ「入った量」を確定とする：(1) 決着の結果が「配送」（`outcome` 0）、(2) 宛先の種類が村（`dst` の種類 1）、(3) ルールの版が S1 のプログラム（`program_version` 4。`Holding::credit` が記録の積荷を上限なしで加える）、(4) 数量は記録の単位（`cargo_log` は内部の 1/1000 単位を整数に切り捨てる）。全量か一部かの比較は、さらに (5) 送付記録を読めていて、その行き先（種類・州・場所・世代・マス）が決着の行き先と完全に同じときだけ行う。④ が別の根拠（村の口座の前後の値など）で確かめるなら、その出どころ | ⑦ の導き方を ④ の契約で確かめるため |

## ⑤（費用の4区分と手動復帰）

### 受け口

- `registerStatusSource('villageCosts', (FS, holding) => {costs: [{phase, amounts?}], committedInHave} | null)`
- `registerStatusSource('manualPlay', FS => {signedPending?} | null)`

### 受け取りたいもの

| # | 内容 | なぜ要るか |
|---|---|---|
| ⑤-1 | 費用の4区分（予約・確定・未確定・解放）を定義しているファイルと遷移、どの注文や操作の費用か | `phase` の対応表を作るため |
| ⑤-2 | 予約がどこにあるか（チェーンのアカウントの欄か、端末の保存領域か、relay か） | 予約の額をどこから読むかを決めるため |
| ⑤-3 | **`committedInHave`**：確定した費用は、村の倉の値からすでに引かれているか | 使える量の計算で、確定分を二重に引かない、または引き忘れないため。答えが無ければ「使える量を出せません」と表示する |
| ⑤-4 | 未確定の費用に上限があるか | 「未確定：最大 …」と出すか、「額はまだ決まっていません」と出すかを決めるため |
| ⑤-5 | **手動復帰の操作と、署名済みで進行中の操作の件数の出どころ** | 「すでに署名した操作 N 件は止まらずに進みます」の N を出すため |
| ⑤-6 | 上の挙動を固定している ⑤ のテスト | 同上 |

**候補（未確認）。** `origin/agent-wallet/delegation-notice`（`553bfb99808adc760e4ccd2ad2993ed4ecc9a5e4`）の `permutation-server/web/frontier/fdelegation.mjs` は、エージェントから鍵を取り戻す操作を扱っています。冒頭の説明には、鍵を取り戻しても、エージェントはサーバー側で止めるまで自動のままだ、と書かれています。⑤ の「手動復帰」がこれを指すのかは確かめていません。⑦ は使っていません。

### 受け口

`registerCoopEntry({id, title(), state(FS) → {available, why?}, open(FS)})`

S1 の村カードの「国の議会」の下に枠があります。

### 受け取りたいもの

| # | 内容 |
|---|---|
| ①-1 | 入口を出す条件（`state` の規則）と、押せないときの理由の文（日本語と英語） |

## ⑦ の側で受け取ったあとにすること

1. 状態名の対応表を、各担当の側に小さなアダプタとして置きます。⑦ の `statusview.mjs` は変えずに済むようにしています。
2. アダプタのテストで、全状態が `ok: true`、`errors: []` になることを確かめます。
3. 画面テスト `ws07-s1-card.screen.mjs` と `ws07-s1-page.screen.mjs` の mock 登録を、実物の登録に置き換えます。
