# 世界を終わらせない達成評価への訂正（2026-10-31）

方針の訂正：シーズン制をやめ、世界は続く。戦期（戦争・競争の区切り）は世界の寿命と別。戦期の周期・集計・賞金は未決で、勝手に決めない。

この担当（⑮）への指示：世界を終わらせない達成評価にする。C 案を残すなら、「世界の終了」ではなく「戦期・評価期間だけを閉じる比較案」として分け、採用済みとしない。

この文書は、訂正にあたってこの担当で行ったことを、4つの点でまとめる。共有コアの変更はしていない（④の担当）。World／Period の正本も作っていない。評価期間は**入力として受け取る**だけ。

## 1. 残っていたシーズン依存

### この担当のコード（すべて直した。§2）

| 依存 | どこに | 何が起きていたか |
|---|---|---|
| 世界の模型が評価期間を持っていた | `world.mjs` の `closeAt`、遅着の印（`late`）、`keepsAtClose`、計画の期限を `closeAt` で切る処理 | 一つの評価期間の中でしか世界を作れなかった。次の期間を判定するには、荷を初期状態として渡し直す必要があった。模型の中で世界をリセットしていたのと同じこと |
| 入力が「一つの期間」だった | `state.period`（開始と終了）だけ | 複数の評価期間、期間をまたぐ隊商・計画を表せなかった |
| 期間が閉じると選択肢が「待つ」だけになった | `optionsOf` の `open = at < closeAt` | 期間の終わりを世界の終わりとして扱っていた |
| 賞金をすべての案で、期間の終わりの要塞数から読んでいた | `prizeOf` | B・C でも、未決の集計規則（シーズン終了→賞金）を前提にしていた |
| C が「戦期を区切る」案だった | `rulesets.mjs` の C、範囲の文言「共同目標は次の章へ」「要塞は中立に戻る」 | 世界の区切りと評価の区切りを分けていなかった。戦期の未決の細部を案の中で決めていた |
| 荷の経路が無限に伸び、空の荷・着いた隊商が残り続けた | `path`、`lots`、`ships` | 終わらない世界では、保存する状態が際限なく増える |

### 入力の側（⑮は変えていない。④・⑧の判断）

| 依存 | 根拠（基準 commit 4cd901de のコード） | 評価器への影響 |
|---|---|---|
| ゲームのすべての口座の住所が、Season の PDA を基点に作られる | `frontier-abi/src/addr.rs` の `AddrCtx { season, program }`、`with_seed(&self.season, …)` | Citizen の tag、隊商の住所、倉・建物の住所が、シーズンごとに別になる。同じ人・同じ場所を、期間をまたいでつなぐ写像が要る |
| 鐘の番号はシーズンの genesis から数える | `frontier-abi/src/prologue.rs` の `bell_at(genesis_ts, t) = ⌊(t−genesis)/600⌋`（u32） | 期間ごとに鐘が 0 に戻る。続く世界の時計への換算が要る。u32 の鐘は 600 秒ごとで約 8 万年分あり、一つの genesis のまま続けるなら上限の問題はない |
| 隊商の `seq` は Citizen ごとの連番 | CARAVAN_SENT の鍵（`owner_tag`, `seq`） | tag が変われば、同じ人の隊商の番号が重なる |
| 賞金の集計は Season が Ended になった後だけ | `permutation-prize/src/lib.rs`（`STATUS_ENDED` でなければ Tally を拒否） | 旧経路の確認にしか使えない。世界を終わらせる根拠にしない |
| 取り分の台帳は「終わりの状態」だけを数える | `achievements.mjs`、`prize-params.json`（`end state only`） | 同上 |
| ヘラルドの畳み込みはシーズンの口座を持つ | `frontier-node/crates/herald/src/fold.rs`（`season_id`、`Present program accounts of the season`） | `/h/events` の番号を記録の流れの位置に使うなら、番号がシーズンをまたいで続くかの確認が要る |

## 2. 変更した挙動

| 変更 | 中身 |
|---|---|
| 世界は一つの続く記録から作る | `buildWorld` は評価期間を知らない。期限・遅着・要塞の持ち主は、判定のときに評価期間の窓（`windowView`）を通して読む。計画の期限は計画自身のもの |
| 評価期間は入力 | `input.windows: [{id, opensAt, endsAt}]`。重なりは拒否する。長さも繰り返しも評価器は決めない。旧形式の `state.period` は、評価期間が一つの入力として読む |
| 期間をまたぐ達成は一度だけ | 達成はそれが成立した鐘の評価期間に入る。前の期間で達成した計画は `achieved_earlier` として、後の期間で再び報酬枠を作らない。材料の投入は前の期間のものも数える（`carryInputs`。材料は消えない） |
| 判定結果に世界の状態 | `world.ends: false`。期間の終わりの時点の、資源ごとの収支・移動中の隊商・未完成の計画・世界の digest を返す |
| 保存と再開 | `snapshotOf(W, at)`／`buildWorld({resume})`。保存した世界から再開した結果は、最初から再生した結果と一致する。適用済みの記録は流れごとの範囲で覚える。再開の後に同じ記録が来ても `replayed` として二度は適用しない |
| 一連の期間の判定 | `evaluateSeries`。境界ごとに、収支・移動中・未完成・再開の一致を返す。各期間は、直前の保存点から再開した世界で判定する（毎回最初から再生しない） |
| C は評価期間だけを閉じる比較案 | `C-joint-window`、`status: 'comparison-only'`。閉じた後の残りの期間は `unevaluated` として報告し、埋めない。世界の digest は B と同じ |
| 賞金 | A だけが旧経路（シーズン終了→要塞数）の互換確認として読む。B・C は `not_decided`。閉じた時点の要塞の先頭は `scores.leaderAtClose`（情報。賞金ではない） |
| 選択肢 | 期間が閉じても世界の中の選択肢は残る（目標の付け先が次の期間になるだけ） |
| 終わらない世界での状態の大きさ | 着いた・奪われた・失われた隊商と空の荷は、生きた状態から外す。id だけを残し、二重使用は拒否し続ける。同じ持ち主・資源・出どころ・確かさの荷は一つにまとめ、元の id は別名として残す。経路は最初の荷と最後の 16 手だけを保つ（手数は数える） |
| adapter | S1：`epoch`（シーズン id）で id と流れを分ける。`worldBell`（その期の鐘→世界の時計）、`actorOfTag(tag, epoch)`（期ごとの tag→同じ参加者）。④：受領書の slot はチェーンの時計なので続く。tag と番号は `epoch` で分ける |

## 3. 試験で確認したこと

固定した短い評価期間（W1 = [0, 240)、W2 = [240, 480)）で、境界をまたぐ記録を使った（`scenarios/boundary-crossing.json`、`test/continuity.test.mjs` 8件）。

| 確認 | 結果 |
|---|---|
| 境界で、移動中の隊商6つ・未完成の計画1つがそのまま次へ続く | 通過 |
| 境界で資源ごとの収支が合う（入った量 = 持っている + 移動中 + 計画の中 + 焼かれた + 失われた） | 通過 |
| W1 で始め W2 で完成・利用された共同の砦は W2 で達成。W1 の材料も数える。報酬枠は W2 だけに、一度 | 通過 |
| 後の期間（W3）で同じ達成を再び数えない。最後まで移動中の隊商は、期間が閉じても消えない | 通過 |
| 境界の位置を変えても、世界の最後の状態は同じ（世界は期間に依存しない） | 通過 |
| 期間を一つずつ判定しても、一連で判定しても、判定は同じ | 通過 |
| 境界で保存し再開した世界は、最初から再生した世界と同じ。再開の後に境界前の記録をもう一度流しても、状態は変わらない | 通過 |
| C は評価期間だけを閉じ（304）、残り（304〜480）を報告する。世界は B と同じ | 通過 |
| 境界の後の襲撃は、境界の前に出た隊商でも W2 に一度だけ入る | 通過 |
| 2つのシーズンの S1 記録を、epoch と世界の時計で一つの世界にできる（epoch なしでは重複に見える） | 通過（`adapter-s1.test.mjs`） |

**長期の確認（境界を通れることとは別に）**：`test/long-run.mjs`、`results/long-run.json`。生成した世界で、40 と 160 の評価期間、約 5,900 件の記録を使った。

| 項目 | 結果 |
|---|---|
| 159 の境界のすべてで収支が合う | 合った |
| 再開の一致（10 境界ごとに確認） | すべて一致 |
| 生きた荷の数 | 156 → 391（40 → 160 期間）。まとめる前は 4,569 まで増えていた |
| 1期間あたりの判定時間 | 22 ms → 約 63 ms（履歴 4 倍で 2.85 倍）。最初から再生しなくなったが、一定ではない |
| まだ増えるもの | 完成した計画とその材料の記録、荷の別名、決着した隊商の id。いずれも履歴で、保存した世界の大きさに比例して判定が重くなる（§4） |

チェーン・validator・④の実物の Run は使っていない。封印進軍・加工・預かりは、この評価器の対象外。隊商・計画・荷の持ち主・襲撃だけを扱った。

## 4. 移行や仕様の判断が残る点

| # | 点 | 誰が | この担当の観察・案 |
|---|---|---|---|
| M1 | 評価期間（戦期）の正本と、その境界の出どころ | ⑧→④ | 評価器は `windows` を入力として受け取るだけ。正本を一つにしてほしい。重なりは評価器が拒否する |
| M2 | 世界の時計 | ④ | 今の鐘はシーズンの genesis 基準。一つの genesis を続けるか、期ごとの鐘を世界の時計へ換算するか。評価器はどちらでも、`at` に世界の時計が入れば動く |
| M3 | 同じ参加者・同じ場所のつなぎ方 | ④（②・⑤と） | 口座の住所が Season 基点なので、期をまたいで tag→参加者、場所→場所を写す表が要る。それができるまでは、期をまたぐ寄与は adapter の写像頼みになる |
| M4 | 記録の流れの番号 | ④ | `/h/events` の番号（ヘラルドの畳み込みは期ごと）か、④の journal の番号か。欠落の判定はこの番号に頼る |
| M5 | 期間をまたいだ材料を、後の期間の達成に数えるか | 持ち主 | 今は数える（`carryInputs: true`）。数えないなら、前の期間の材料は「持ち越し」として別に扱う規則が要る |
| M6 | 戦期の集計・賞金 | 持ち主（⑰と） | B・C は決めていない。A の旧経路は互換確認としてだけ残す |
| M7 | 履歴の圧縮 | ④ | 完成し、それを数えた期間も閉じた計画の材料の記録、古い別名、決着した id を、どの時点で要約に移すか。移すときは、旧版の証拠を書き換えず、要約に元の digest を残す |
| M8 | C を続けて比べるか | 持ち主 | 区切りの早さが要塞の先頭を変える（早く閉じた 9 シナリオのうち 3）。妨害・早期終了の動機は、評価期間だけを閉じても残る |
