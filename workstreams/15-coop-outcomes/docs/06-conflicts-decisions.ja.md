# 既存の賞金・継続ルールとの衝突、採用に必要な判断、食い違い

**2026-10-31 の訂正の後：** シーズンに依存していた箇所と移行の判断は [07](07-continuity.ja.md) の §1・§4 にまとめた。下の K1〜K3 は、訂正の後は「C を採るなら」ではなく「世界が続くなら、どの案でも」の問題になった。

## 1. 既存の賞金・継続ルールとの衝突

| # | 衝突 | 案 | 中身 |
|---|---|---|---|
| K1 | 早期終了とプログラム | C | `permutation-prize` は Season が Ended になった後でだけ数え（Tally）、`end_bell` はシーズン作成時に決まる。共同達成で戦期を早く閉じるには、ゲームのプログラムと賞金のプログラムの両方に変更が要る |
| K2 | 戦期（23 の C 案）が未実装 | B・C | 「世界は続き、要塞と戦争の状態だけ戻す」は決定済みだが、コードはシーズンごとに終わる。B・C の「続くもの」は、今のコードでは成り立たない |
| K3 | 移動中の隊商 | B・C | ⑧の報告によると、EndSeason をまたぐ隊商は精算できず、lamports が残る（⑧ doc 11、修正案は未適用）。「移動中の隊商は次の戦期に着く」は、今のコードでは誤り |
| K4 | 国の中の取り分（28） | B・C | 28 は「国の戦いで消費されたもの」だけを数える。共同の砦への材料は、勝敗の砦の戦いでなければ数えられない。この担当は達成を賞金に入れないので矛盾はしない。ただし、入れるなら 28 を変える判断が要る |
| K5 | 取り分の台帳（今のコード） | 全案 | `prize-params.json` の capture・reinforcement は終わりの状態だけを数える。共同目標の材料とは別の物差しで、混ぜていない |
| K6 | AI と賞金の資格 | B・C | 今のコードでは、運営の AI 住民は賞金の資格がない（`prize-params.json` `decided.eligibility`）。この評価器の報酬枠（お金ではない）は、人と AI を区別しない。報酬枠を何かに結びつけるなら、区別の判断が要る |
| K7 | 区切りで閉じた後の判定 | C | 閉じた後の出来事（要塞の動き・投入・利用）は、その戦期に数えない。次の戦期の判定は、この担当の範囲外 |

## 2. 採用に必要な判断（持ち主の判断）

| # | 判断 | 選択肢 | この担当の観察 |
|---|---|---|---|
| Q1 | 共同達成で戦期を区切るか | B（区切らない）／C（区切る） | C では、終わりの時刻をめぐって早期終了と妨害の動機が生まれ、受取国が変わった（3/8）。区切るなら K1 のプログラム変更が前提 |
| Q2 | 達成を賞金に結びつけるか | 結びつけない（今の3案）／国の中の取り分に入れる（28 の変更）／別のもの（称号・建物の機能） | 結びつけないなら、達成で人が動くかは人で試すまで分からない |
| Q3 | 共同目標の「多様性」の条件 | 国の数・割合・数える単位（荷の出どころか、持ち主か） | 出どころで数えると、送った材料による洗浄を止める。代わりに、正当な売買の材料も売り手の国の寄与になる |
| Q4 | 別人であることの扱い | 模型のラベルのまま／参加費・投票権までの期間（14 の決定）などの費用で薄める／外部の本人確認 | どれでも、チェーンだけで別人を保証することはできない |
| Q5 | 余った材料の扱い | 先着（今）／国ごとの上限／比例 | 先着だと、固定連合が埋めた後の材料は余りになる |
| Q6 | 「実際の利用」の記録 | 砦の守備だけ／塔・柵の利用の記録を足す | 塔・柵の利用はチェーンの記録にない。足すならプログラムの変更 |
| Q7 | 村あての到着の量 | ①の下限／④の正確な量（RuleDerived）／④の P1（`credited` を記録に足す） | P1 が入れば、判定できない場合が減る |
| Q8 | 国の目標を選ぶ投票 | 今の投票の種類（構え・追放）に足す／置かない | 今の投票の種類には、国の目標を選ぶものがない |

## 3. 文書とコードの食い違い（見つけたものすべて）

コードの書き方に従い、評価器はコードの値を使いました。

1. **勝敗の数え方。** 23 §2 は「勝敗の砦をどれだけ長く持ったか」（提案）。コード（`permutation-prize/src/lib.rs`、`prize-params.json`）は「終わりの時点で最も多く持つ国」で、「Decided (owner)」と書いてある。この決定は決定ログ（99）に記録がない。評価器はコードに従った。
2. **資源の受け渡し。** `prize-params.json` と `achievements.mjs` の `resourceSupply` は「ゲームに資源を受け渡す命令がない」と書く。S1 には SendCaravan と CARAVAN_SENT/SETTLED がある（`frontier-abi/src/v2/log.rs`、PR #20 で他人あての隊商）。記述が古い。
3. **23 §4 の参照先。** `frontier/season-complete` と書いてあるが、remote にそのブランチはない（handoff は旧 core playtest の前提として触れるだけ）。
4. **戦期。** 決定ログは C 案（世界は続く）を決定とする。コード・README はシーズン制のまま（README も「戦期をまたぐ世界は計画」と書くので、README とコードは一致。決定ログとコードがずれている）。
5. **基準 commit。** 依頼文は 4cd901de を共通の基準とする。4cd901de は `integrate/claude-consolidation-20261029` の上にあり、この環境の checkout（`main` の 9214293）の祖先ではない（子孫）。作業は 4cd901de から始めた。
6. **AGENTS・skill。** 依頼文は AGENTS と関連スキルの確認を求めている。しかし、リポジトリのどの対象 commit にも `AGENTS.md` も `SKILL.md` もない。
7. **①の例の資源の合計（他の担当との食い違い）。** ①の共同成果の例「使われた交易 50」は、資源をまたいだ単純な合計。この担当の必須検証（資源を合計しない）と合わない。評価器は資源ごとの要求量で判定する。
8. **村あての到着（他の担当どうし）。** ①は積荷を下限、④は正確な量（RuleDerived）とする。評価器は選べるようにし、既定は①に合わせた。
9. **中央塔。** `DESIGN.md` は5段の Engine を書くが、プログラムにはない（⑭の報告。⑭が確認中）。評価器は塔を任意の入力として扱い、Engine の配当（`frontier-sim`）は使っていない。
10. **構造物の費用のコメント。** `structure.rs` の `cost_units` のコメントは「wood, stone, arms, gold」と書く。配列は8枠で、arms は Horses の枠（`arms.rs` `ARMS = Resource::Horses`）。コメントと値は一致する。誤読しやすいので記す（食い違いではない）。
11. **④の Receipt の body（2026-11-06）。** ④の型（`store.rs` の Receipt）は body を構造として持つが、保存と書き出しは JSON の文字列（`body_json`）。u64 の持ち主・襲撃者は JSON の数で、JavaScript では 2⁵³ を超えると丸まる。⑮は文字列から正確に読む（`parseExact`）。
12. **④の demo の積荷（2026-11-06）。** ④の `runexec demo` は Science（8 枠の 6 番）を送る。⑮の評価器の資源は 6 種（food・wood・stone・ore・arms・gold）で、Science・Influence を持たない。数えない資源として報告する。
13. **④の数量契約 §7 a と書き出し（2026-11-06）。** §7 a は「verification は Run の outcome にある」とする。⑫の書き出しは receipts と spec だけで、outcome を含まない。⑮は settle の記録から §3 の区分を決める。
