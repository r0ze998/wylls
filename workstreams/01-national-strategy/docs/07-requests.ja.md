# 7. 他の担当へ渡す要求（②④⑤⑦）

**この文書の役割：** ①（国の戦略）が、他の担当に求める「ゲーム上の条件」を並べる。実装のしかたは各担当が決める。①は他の担当の成果物を変更していない。

**担当の範囲（2026-10-30 に本人が訂正）：**
- ② 資源と施設の権限 ／ ④ 実行状態
- ⑤ **AI 参加と AI staking**：agent に予算と行動範囲を設定して委任する、利用費用を管理する、同じ村を手動と自動で切り替える。
- ⑦ **プレイヤー体験・UI/UX・表示の正確性**。
- ①自身のルールの検証と、国のチーム体験の試遊の設計は、①で続ける（最後の節）。

---

## ② 資源と施設の権限へ

| # | 要求（ゲーム上の条件） | なぜ①に要るか | 試作での扱い |
|---|---|---|---|
| 2-1 | 国の卓の範囲では、物の持ち主はいつも一人に決まる（目標・調整役・賛同は持ち主にならない）。国の共有資産・取り分を作るかは②と本人の別の判断（国の卓とは切り離す） | R1（範囲の限定） | `inventory` のテストで保存を確認 |
| 2-2 | 「持ち主のまま、他人が使う（預ける・使用権）」を作るなら、**使える人・量・期間・取り消し**を持ち主が決められること。持ち主の不在中も、決めた範囲だけが効くこと | 「預ける」の選択肢を開けるため（R4）。今は閉じている | 「預ける」「他人の工房を借りる」を閉じた選択肢として表示 |
| 2-3 | 使用権がない間は、他人の施設を動かす道がないことを、画面で理由つきで示せること | 選べない理由を出す（R12） | 理由の文言を試作で使用 |
| 2-4 | 他人の倉に「贈る」とき、上限（`VAULT_CAP`）を超えた分は**黙って失われる**（S1 の事実）。送る前に空きを見せる・断るなどの扱いを決めること | 拠点の倉に複数人が贈るため | 試作は S1 と同じく超えた分を失い、記録に出す |
| 2-5 | **倉：** S1 では中身は奪った人の物、向かっていた荷は失われる（1章 1-13、事実）。**村の占領：** 向かっていた荷と村の在庫がどうなるかを確定させること（この作業では未決定） | 失敗後の説明と、成立条件の崩れ方に要る | 倉は S1 のとおり実装・テスト済み。村の占領は試作で起こさない |
| 2-6 | 鍵の共有はしない。不在の人の物は、本人か、本人が決めた権限（代理の札など）以外は動かせない | R9 | 不在の人の操作はすべて断る |

## ④ 実行状態へ

| # | 要求 | なぜ①に要るか | 試作での扱い |
|---|---|---|---|
| 4-1 | 荷の状態を少なくとも **準備中／送信済み（未確定）／輸送中（確定）／到着済み（確定）／送信失敗／失った** に分けて返すこと | 進み具合を到着済みだけで数える（R5） | `shipment.state` |
| 4-2 | 到着の**見込みターン**と、遅れていればその**理由**（占領の決着待ち `CapturePending`、確定を誰も呼んでいない、道が柵でふさがれた など） | 遅延のとき、誰に何を選ばせるかを決める | `eta`・`delay`・`reason` |
| 4-3 | 送信が確定しなかったとき、荷が**送り主の手元に残っている**ことを確かめて示すこと | 「送信済み」を「消えた」とも「届いた」とも扱わない | 出来事「送信が確定しない」 |
| 4-4 | 卓の申し出と、実際の隊商を結びつける手段（隊商の id を卓が記録する、など） | 「この荷はこの申し出の発送」と示すため | 申し出 id を荷に持たせた |
| 4-5 | 輸送中の荷を呼び戻す・行き先を変える操作が S1 にないことの確認（あるなら規則）。**目標の方針変更・再確認・取り下げが、送信済みの荷を取り消したり転送したりしない**こと | 退出・方針変更のとき、荷がどうなるかを説明するため | 「そのまま届く」とし、テストで確認 |
| 4-6 | 砦の守備兵の「次のターンから数える」（`pend_bell`）のような遅れを、実行状態として返すこと | 成立の判定に「今いる兵」だけを使うため | 1ターン後に数える |
| 4-7 | **軍の出発は、持ち主の明示の操作でしか起きない**ことを、実行の側でも保つこと（補給の到着や目標の成立を合図に、軍の命令を出さない） | R6。依頼の境界 | テスト「ターンを何度進めても、軍は自動で出発しない」 |

## ⑤ AI 参加と委任へ

①は AI の代理を試作に入れていない（模擬もしていない）。②⑤の権限制御が整ってから、国の卓につなぐ。

| # | 要求（ゲーム上の条件） | なぜ①に要るか |
|---|---|---|
| 5-1 | **AI による申し出・発送の権限**：持ち主が明示的に許可した**操作**（申し出／発送／取り下げ）・**対象**（どの目標・どの必要）・**資源と量の上限**・**期限**の範囲でだけ、AI が持ち主の物を申し出・発送できること。範囲の外は断る | 国の目標に AI が手を貸す道を開けるため（R13） |
| 5-2 | **予算の上限**：AI の行動にかかる利用費用（隊商の手数料 `CARAVAN_FEE` など）に、持ち主が上限を決められること。上限に達したら止まること | 協力が持ち主の知らないうちに費用を生まないように |
| 5-3 | **停止と失効**：持ち主がいつでも委任を止められること。期限で失効すること。止めた後・失効した後に出た発送がないこと（止める前に送信済みのものの扱いは④と決める） | 持ち主の不在や方針変更のときに、委任が勝手に続かないように |
| 5-4 | **実行記録**：AI が何を、誰の委任で、いつ、どの範囲で行ったかを、持ち主と国の卓が読めること | 卓の記録で「誰が応じたか」を正しく出すため |
| 5-5 | **国への参加・目標への賛同・調整役になることは、AI に資源を動かす権限を与えない**こと。賛同は委任ではない | 賛同と権限を分けるため（3-4） |
| 5-6 | **手動と自動の切り替え**のとき、未発送の申し出と送信済みの荷がどちらの判断のものかが分かること | 卓の「申し出」と「発送」の持ち主表示が曖昧にならないように |
| 5-7 | AI に**投票**と**軍の出発**を任せないこと（決定 E2、決定 2026-10-23）。補給の成立を合図に軍を出さないこと | 依頼の境界 |
| 5-8 | 同じ人・同じ運営者が動かす複数の AI を、卓の賛同で「判断する人1」と数えられるよう、委任元（controller）を卓が読めること。読めないなら、そう分かること | 人間と AI の数を独立した意思と仮定しないため（3-4） |

## ⑦ プレイヤー体験・UI/UX・表示の正確性へ

| # | 要求 | 理由 |
|---|---|---|
| 7-1 | **国の卓の導線**：協力の入口を一か所にする（下のナビに「国の卓」：`proposals/0001-nav-nation-table.patch`、未適用）。村の画面の「足りない」から卓の目標・依頼へ行けること | 今は評議会のページで鍵を貼り、隊商の画面で贈る（Eternum UX 調査の「変更前」） |
| 7-2 | **所有者の表示**：荷・申し出ごとに、提供した人・今の持ち主・着いた後の持ち主・使う人を出す。着いた後に倉ごと奪われた物は奪った人の物と出す | R4 |
| 7-3 | **進行状態の表示**：準備中・送信済み（未確定）・輸送中・到着済み・失った を分ける。条件は「今ある・使える量」で出し、「到着の累計」と並べても混同させない。材料と条件を分けて出す | R5。送信を到着や達成と混同しない |
| 7-4 | **成立の判定時点**：「成立は期限のターンに判定」「今そろっている（期限まで保つ必要）」を出す | 早くそろった後に崩れる場合があるため |
| 7-5 | **賛同の表示**：「○村（人間○・台本○・AI○）・判断する人○」と出し、採択は試遊の仮説で正式な決定ではないと書く | 3-4 |
| 7-6 | 用語：送信済み・輸送中・到着済み・準備中・再確認待ち・供給元を失った・調整役・賛同・申し出・提供の上限・材料・判断する人 を用語集に | 状態の区別を言葉でも守る |
| 7-7 | 国の卓を国の仲間だけに見せ、隊商の動きはもともと公開だと明示する。護衛の中身は出さない | handoff 未検証事項5 |
| 7-8 | **操作と理解の検証**：試遊で、プレイヤーが「誰の物か」「着いたか・送っただけか」「次に何を決めるか」を正しく言えるかを確かめる（`docs/10-playtest-plan.ja.md` の理解の質問を共有）。①の試遊と同じ回で行うなら、記録を分ける | 表示の正確性を人で確かめるため |
