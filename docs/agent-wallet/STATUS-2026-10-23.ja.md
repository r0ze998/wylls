## 4. 停止・無料 autopilot・委任解除・鍵の取り戻しが保証すること

| 操作 | 何が起きるか | 強制する場所 | 今回実地で確かめたこと | 偽チェーンのテストのみ・未確認のこと |
|---|---|---|---|---|
| **停止**（mode を manual に。所有者の署名付きコマンド） | サーバーが agent の新しい要求を拒否する（`AgentStopped`）。runner は呼ばない。送信直前の再検査で、停止前に準備された要求も拒否。送信済みの取引は巻き戻さない。推論中の判断料は予約されたまま、結果が届いたら 1 回だけ課金し、その判断は実行しない | **運営の relay**（運営を信頼する必要がある） | E2E：capability での要求が `AgentStopped`（古い epoch でも同じ）。停止後 2.5 tick の間、モデル呼び出し・行動・課金がいずれも 0。予約 0。**chain 上の委任は残る**（`delegated: true`）。実ブラウザ：推論中の停止で予約 0.01 が残り、遅れた結果は 1 回だけ課金 | 停止と再開の競合（送信直前の拒否）は単体テストのみ |
| **無料 autopilot** | モデルを呼べないとき（失敗・不正な答え・残高や上限の不足）や、runner がモデルなしのときに、許可された行動の範囲で Harvest だけを行う。課金しない。**停止ではない**（自動のまま） | 運営の relay | 実ブラウザ：判断回数の上限で autopilot が代行し、画面に「停止ではありません」と出た。E2E：失敗後の代行は課金 0 | |
| **オンチェーン委任解除**（所有者の wallet が署名する SetSession で、セッション鍵を agent の鍵から別の鍵に替える） | chain が、agent の鍵をこの Citizen のセッション鍵として認めなくなる | **chain**（運営を信頼しなくてよい） | E2E と実ブラウザ：委任解除の後、chain の記録で `delegated: false` | **解除後に agent の鍵が直接 RPC へ送った取引を、プログラムが拒否すること**は今回は実地で試していない（プログラムの actor 検査による設計上の保証） |
| **鍵の取り戻し**（解除で、プレイ画面のセッション鍵に戻す） | 所有者がプレイ画面から同じ村を操作できる | chain | agent-manual-5：取り戻した後、プレイ画面からの手動の収穫が `finalized`。委任中は同じ画面の操作が 403 Auth で拒否された | |
| **旧 agent の資格情報** | capability トークンは agent の要求の入口。再発行すると古いトークンは即時無効。委任解除の後に自動へ戻しても、gateway は送信前に chain の委任を読み、`SessionNotDelegated` で拒否する | relay（トークン）、chain（委任） | E2E：不正なトークンが `BadCapability`。agent の鍵で `POST /f/relay` へ直接送ると `AgentKeyDirect`（偽の署名で試した） | **トークンの再発行後に古いトークンが拒否されること**と、**委任解除の後に自動へ戻した要求が `SessionNotDelegated` になること**は、偽チェーンの単体テスト・MCP 契約テストのみ。実チェーンでは未確認 |

## 6. 未確定のものを照合する規則：本番の前提条件

**原則**：時間が経っただけでは、「実行されなかった」「課金されなかった」ことの証明になりません。

**`--agent-unresolved-release-ms`（一定時間後の自動解放）は localnet の試行用です。既定は off で、本番の仕様として有効にしません。**

| 対象 | 今の判定 | 本番で塞ぐべき穴 | 必要な条件 |
|---|---|---|---|
| 推論の hold（再起動や TTL で結果が分からないもの） | `unresolved` として予約に残す。自動解放 off では運営の決定（`settle`）を待つ。解放後に遅れて届いた結果は課金しない（運営の記録に残す） | 外部のモデル提供者に原価を払う構成では、解放した後に提供者側の課金が確定すると、所有者が出金済みで運営だけが負担する。課金規則を変えて遅延分を所有者に請求すると、残高が負になるか二重課金になる | (1) 呼び出しごとに冪等なリクエスト ID を提供者へ渡す。(2) 解放の前に、提供者の利用記録をその ID で照会して「実行なし」を確かめる。照会できなければ解放しない。(3) 遅れて届いた結果は hold ID で 1 回だけ照合し、解放済みなら所有者には請求しない（今の動作）。(4) 解放と照合を同じ直列化された台帳更新の中で行い、出金と競合させない |
| ゲーム行動の hold（`sending`） | chain の答えで決める。署名の状態が見つからず、ブロック高が有効期限を超えたら「期限切れ」として戻す | 履歴を持たない RPC ノードや遅れているノードでは、着地した取引を「見つからない」と答える。価格表が空なので今は金額に影響しないが、価格を付けると二重支出になる | 期限切れの判定は finalized のブロック高で、余裕を持たせる。全履歴を持つノードで `getTransaction` も照会する。2 つの独立したノードの一致を求める。判定できないものは戻さず pending のままにする |
| 出金（`sending`） | 同じ規則。着地は confirmed で判定 | **上と同じ理由で、着地した出金を「期限切れ」と誤判定して残高に戻すと、二重出金になる**。confirmed は理論上ロールバックしうる | 出金の確定は finalized で判定する。戻す前に、カストディ（または vault）のトークン残高と台帳の負債（`liabilities()`）を照合する。合わなければ止めて運営に知らせる。出金済みの総額を chain の転送記録と照合する |
| 再起動 | `held` は戻す。`running` は `unresolved` に。`sending` は reconcile まで待つ | 複数のプロセスが同じ状態ファイルを使うと二重支出になる（非対応） | 単一の書き手を保証する（排他ロックか DB の行ロック）か、vault に移す。起動時に reconcile を終えるまで、新しい出金と送信を受け付けない |
| 残高の過大表示 | `available` は台帳の値 | 照合前の解放や誤った期限切れ判定で、引き出せない額を「使える」と表示しうる | 上の条件を満たすまで、その額は「確認待ち」として表示する（今の `unresolved` と同じ扱いを `sending` にも広げる） |
