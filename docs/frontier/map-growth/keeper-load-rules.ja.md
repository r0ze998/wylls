# ルール変更案 R1〜R4 の詳細設計：得点を毎ターン確定させたまま、静かな州に書き込まない

2026-10-28。[keeper-load.ja.md](keeper-load.ja.md) の §4 を詳しくしたものです。

前提はオーナーの回答「得点は毎ターン確定している必要がある」です。

**状態：設計だけです。コード・プログラム・ルールは変えていません。** 数字は見積もりで、計測はしていません。

## 0. 結論と、最初に確認したい1点

### 「毎ターン確定」の意味

この設計では、「確定」を次の意味で使います。

> ターン t の得点は、t の公開窓が閉じた時点で、**チェーン上のデータとルール（公開された計算式）だけから、誰が計算しても同じ値に決まる**。後から変わることはない。

今の S1 は「毎ターン、州ごとに数字を書き込む」ことで確定させています。この設計では次のように確定させます。

- 静かな州は書き込みません。
- 得点は「最後に書いた数字」＋「その後、何も起きていないことがチェーン上で証明できるターン数 × 1」です。
- 「何も起きていない」は、今もチェーンにある到着の記録（ArrivalDay）と公開窓の記録（アンカー）で証明します。

確定する時刻は今と同じ（そのターンの公開窓が閉じたとき）です。値も今と同じです（§8）。

**もし「チェーン上の数字そのものが毎ターン書き換わっていること」が要件なら、この設計は使えません。** その場合は、書き込みの数が州の数に比例することを避けられません。ここを最初に確認させてください。

### 設計の要点

1. **R1 領地ターン**：得点の「進め方」（各ターンの開始時に砦を持つ国に+1）は変えません。変えるのは「公式の値をどこから読むか」で、「記録＋証明済みの残り」になります。
2. **R2 賞金集計（Tally）**：最初は変えなくても動きます（シーズン後に全州を1回ずつ「早送り」する）。早送りをやめたい場合だけ変えます。
3. **R3 マーチ集計（fold）**：S1 の得点には使われていません（ヘラルドの順位は州の領地ターンの合計です）。それでも fold が全州を数時間ごとに進めさせているので、ここを変えないと書き込みは州の数に比例したまま残ります。
4. **R4 野営地**：ルールを変えずに、日ごとの判定を計算で再現できます。計算量が大きすぎた場合だけ、小さなルール変更を入れます。

全部入れると、静かな州への書き込みはシーズン中ほぼゼロになります。書き込みの数は「何かが起きている場所」の数に比例するようになります。

## 2. 共通の土台：休止証明と早送り

R1〜R4 は、次の3つの部品を共有します。どれも `frontier-abi` に置き、プログラム・ヘラルド・検証ツール・賞金プログラムが同じコードを使います。

### 2.1 休んでいる州（定義）

州が次をすべて満たすとき、「休んでいる」とします。条件はすべてチェーン上の州のデータから判定できます。

- `resolved_next` の時点で静かである（今の `trivially_quiet_v2` が真）
- 包囲・占領の記録がなく、砦の争奪も進んでいない（`active_count == 0`）
- 予定された変更が、確定させたいターンより後にある（`next_due > t`）

### 2.2 休止証明 `quiet_through(州, t, 証拠)`

ターン `resolved_next` から t まで何も起きていないことを、チェーン上の証拠で確かめる関数です。

1. 州が 2.1 を満たす。
2. その範囲のすべてのターンで、州の地域の公開窓が閉じている。証拠はアンカー、または保管庫のアカウント。
3. その範囲のすべての日で、到着の記録がない（アカウントがない）か、該当ターンのビットが0。
4. 野営地：範囲内に出現する日があれば、出現後も静かかを確かめる（R4）。静かでなくなるなら、その手前のターンまでしか証明しない。

戻り値は「証明できた最後のターン」です。途中で止まれば、そこまでが確定です。

### 2.3 計算で進める `project(州, t)`

休んでいる州の、ターン t 時点の状態を、1ターンずつ回さずに計算します。

| 項目 | t 時点の値 |
|---|---|
| 領地ターン（持ち主の国） | 記録 ＋（t − `SCORE_NEXT_BELL`）（シーズンの終わりで頭打ち） |
| `SCORE_NEXT_BELL`、`resolved_next` | t |
| 砦 | 変わらない（`advance_quiet` と同じ結果） |
| 1時間ごとの重みの記録 | 最後の6時間分を `control_weights(州, 6h)` で計算して書く（それより古い分は今も上書きされて消える） |
| 野営地 | R4 の方法で計算 |

**安全網**：「`project` の結果」と「1ターンずつ `cq::step` などを回した結果」が、州のバイト列としてまったく同じになることを、ランダムな州と長さで大量に試すテストを最初に作ります（§10）。これが通らない限り、先へ進みません。

### 2.4 新しい命令：早送り `FastForward(P, Q, t)`

- 誰でも送れます（今の SkipQuiet と同じ class D）。
- 2.2 で t まで証明できれば、2.3 の結果を州に書きます。証明が途中で止まれば、そこまで書きます。
- 1件で扱える範囲は、渡せるアカウント数で決まります。目安は7日分です（到着の記録7件＋保管庫14件程度）。§7 のデータ追加を入れれば、地域ごとに1件で済みます。
- 記録（イベント）は1件にまとめます（範囲、持ち主、加えた領地ターン、野営地の出現）。今は毎ターン・毎時間のイベントが出ているので、イベントの形式が変わります（検証ツールとヘラルドの対応が必要。§9）。
- 使う場面：州が起こされたとき（到着、予定、催促）の直前、シーズンの終わり、R3 を入れない場合の集計前。

## 3. R1 領地ターン：公式の値は「記録＋証明済みの残り」

### 変えること

- 公式の領地ターン：
  `territory(州, 国, t) = TERRITORY_BELLS[国] + （国 == 砦の持ち主 なら quiet_through(州, t) − SCORE_NEXT_BELL + 1、でなければ 0）`
- これを使うのは、ヘラルドの順位、賞金の同点処理、検証ツールの再計算（CQ3）です。

### 変えないこと

- 「各ターンの開始時に砦を持つ国に+1、占領の効果は次のターンから」という得点の進め方。
- 州のデータの配置（`TERRITORY_BELLS` と `SCORE_NEXT_BELL` はそのまま使います）。

### なぜ同じ値になるか

休んでいる州では、砦の持ち主は変わりません。持ち主が変わるには、ほかの国の兵が砦のマスにいて争奪を進める必要があり、その州は「休んでいる」の条件から外れます。だから1ターンずつ+1しても、まとめて足しても、同じ値です。

### 前に挙げた案との違い

前の文書では「持ち主が変わった時点の記録（`since_bell`）から計算する」と書きました。調べた結果、持ち主が何度も変わった州では履歴全体が必要になるので、やめました。今ある記録とカーソルをそのまま使い、残りだけを計算で足す方が、配置を変えずに済みます。

### ヘラルドでの毎ターンの計算

州ごとに毎ターン足し直すと、ヘラルドの計算量が州の数に比例します。そこで国ごとに「休んでいる州の数（＝1ターンあたりの増え方）」を持っておきます。

`国の合計(t) = 書かれた合計 ＋ 増え方 × t − 補正`

州が休み始める・起きるときだけ更新すれば、毎ターンの計算は国の数（6）に比例するだけになります。

## 4. R2 賞金集計（Tally）

今は「Tally はすべての州が `resolved_next ≥ end_bell` まで進んでいること」を求めています（`permutation-prize/src/lib.rs:621-624`）。

- **R2-0（ルール変更なし、おすすめ）**：シーズンの終わりに、休んでいる州を早送りで終わりまで進める。シーズンに1回だけで、1州あたり1〜4件です（7日分ずつ。§7 を入れれば1件）。817州なら最大でも約3,300件で、毎ターンの処理ではありません。
- **R2-1（ルール変更）**：Tally が `quiet_through` の証拠を受け取り、`resolved_next < end_bell` の州も数えられるようにする。シーズン後の早送りが不要になりますが、賞金プログラムが休止証明のコードと証拠のアカウントを持つことになり、監査の範囲が広がります。

**R2-0 で始め、シーズン後の件数が問題になったときだけ R2-1 を検討する**のがよいと考えます。

## 5. R3 マーチ集計（fold）

### 今の問題

マーチ集計は1時間ごとに、7州それぞれの重みの記録を読みます。記録は6時間分しか残らず、集計が遅れると、キーパーは3時間後に遅れている州を進めます。そのため R1 を入れても、**静かな州が6時間（36ターン）ごとに書かれ、集計自体も「マーチの数 × 1時間に1件」かかります**。817州なら1ターンあたり約23件＋約19件です。

### 案

- **R3-A：S1 ではマーチ集計をやめる（ルール変更）**。S1 の得点には使われていません。ただしヘラルドは、集計から「捕獲数」などの累計の表示も作っているので、それを州のイベントから作るよう直す必要があります。一番簡単で、効果も最大です。
- **R3-B：休んでいるマーチは、何時間分もまとめて集計する（ルール変更）**。7州すべてが休んでいれば重みは変わらないので、記録の代わりに `control_weights` で計算した値を使い、k 時間分を1件で足します。マーチの公式の値も R1 と同じく「記録＋証明済みの残り」にします。
  - 1件に7州分の証拠が要るので重くなります。
  - 今は「集計が遅れて記録が上書きされると Lost」ですが、この案では Lost が起きなくなります。**今の方式で Lost が出るような遅れがあった場合だけ、結果が今と変わります。**
- **R3-C：変えない**。R1 だけ入れて、6時間ごとの書き込みは残す。

マーチ集計を S1 で残す理由（得点以外の使い道）があるかどうかはオーナー判断です。なければ **R3-A** をおすすめします。

## 6. R4 野営地

### ルールを変えない方法（R4-0、おすすめ）

野営地が出るかどうかは、日ごとに独立して計算できます（§1）。早送りでは、休んでいた日を順に計算します。

- 1日1回の計算で、28日のシーズンでも最大28回です。
- 出現しても静かなまま（村のない州など）なら、そのまま進めます。
- 出現で静かでなくなる場合（村の近くに出るなど）は、その日の判定ターンの手前で止めます。そのターンは今の SkipQuiet か解決で処理します。キーパーは出現日を前もって計算できるので、その日に州を起こします。

### ルール変更が要る場合（R4-1）

1日分の計算（`place_v2`）が重く、28日分が1件に収まらない場合だけ検討します。

- 世代番号 `gen` を「出現回数」から「出現した日」に変えます。こうすると、t 時点の野営地は「t から遡って最初に出現する日」だけで決まり、遡る日数は出現確率の逆数程度で済みます。
- `gen` を野営地の識別に使っている箇所（イベント、襲撃の記録）への影響を調べる必要があります。

**まず R4-0 で計算量を測ります。**

## 7. データの追加（ルールではない）：地域ごとの「確定済みターン」

証拠のアカウント数を減らすための追加です。

- 地域ごとに「ここまでのすべてのターンの公開窓が閉じた」というターン番号を1つ持たせます。
- キーパー（誰でも可）が毎ターン地域ごとに1件で進めます。数は地域の数に比例し、州の数には比例しません。
- これがあれば、休止証明の公開窓の部分は地域ごとに1アカウントで済みます。到着の記録は日ごとに1アカウントのまま残ります。
- 入れなくても動きます（保管庫と最近のアンカーを渡す）。早送り1件の範囲が狭くなるだけです。

## 10. 確かめ方

1. **同一性テスト（最優先）**：ランダムな州（村・自由都市・野営地・格上げ予定などを含む）と長さで、`project` と「1ターンずつ回した結果」が同じバイト列になることを確かめます。野営地の出現をまたぐ場合も含めます。
2. **証明のテスト**：到着が1つでもある、窓が閉じていない、予定がある、争奪が始まった——どの場合も `quiet_through` がその手前で止まることを確かめます。
3. **svm テスト**：早送りの命令を、正しい証拠・欠けた証拠・偽の証拠で試します。
4. **ローカルの2世界比較**：同じ設定で今の方式と新方式を動かし、シーズン後の Tally の結果と各国の領地ターンが一致すること、検証ツールが両方で合格することを確かめます（乱数が世界ごとに違うので、プレイヤーの動きは録画した操作を再生して揃えます）。
5. **負荷**：`scripts/map-growth-measure.py` で、817州と、さらに大きい世界（リング24程度）で、1ターンの送信数、ターン処理の遅れ、ヘラルドの計算時間を測ります。

### 段階4（実装済み、ブランチ map/region-append）

- **進めてよいターン**：チェーンのデータだけで決まるターンだけです。

  - その州の到着の記録（ArrivalDay）に、そのターンのビットがない（記録がなければ、到着なし）。
- **進め方**：プログラムの早送りと同じ `rest_model::project` で、1ターンずつ州のデータを計算します。そのデータから、リングの地図（overview）、支配の地図（control）、順位、日ごとのファイルを、州が実際に処理されたときと同じように作ります。領地ターンは「書かれた値＋証明済みの残り」（R1）になります。

- **REST 記録**：早送りの記録の要約値（digest）を、取引後の州のデータから計算し直して比べます。違えば警報（`conquestMismatch`）です。早送りは1時間ごとの CONQUEST 記録を出さないので、その範囲のターンは「記録が足りない」の警報（`conquestMissing`）の対象から外しました。
- **再起動**：計算で進めた分は保存しません。再起動後は、チェーンに書かれた位置から計算し直します。すでにファイルを書いたターンは書き直しません。

### 2世界比較（§10-4、2026-10-28）

同じ設定の2つの世界を並べて、シーズンの終わりまで動かしました。違いはキーパーの `--keeper-rest` だけです。

プレイヤーがいないので、どちらの世界でも同じことしか起きません。乱数をそろえるための操作の録画は使っていません。

**結果**：
1. **州のデータ**：817州すべてで、イベントのつながり（先頭64バイト）より後のバイト列が、2つの世界で**完全に一致**しました。`resolved_next`（全州48）、開いたターン、領地ターン、スコアのカーソル、砦も一致しています。領地ターンの合計は、どちらもどの国も4,556です。
2. **ヘラルド**：最後の順位（ターン47）は、どちらの世界でも、どの国も4,556ターン・135州でした。チェーンとも一致しています。
3. **賞金の集計（Tally）**：どちらの世界でも、51回に分けた Tally がすべて届きました。砦のある810州をすべて数え、まだ終わりまで進んでいない州は0件でした。休みありの世界では、シーズン終了の早送りで全州が終わりまで進んだことになります。プールの面積（どの国も135）はチェーンからの数え直し（`--check`）とヘラルドの両方と一致し、2つの世界で同じでした。
4. **検証ツール**（`frontier-stack verify`）：どちらの世界も **PASS** でした。警告は同じ2件で、どちらも参考情報です。
   - CQ3 は命令の種類によらず、取引の前後で州の領地ターンを確かめます。なので早送りの取引の領地ターンも確かめています。REST 記録のつながりは CQ1 が確かめています。
   - ただし、早送りの「静かだった証明」（窓が閉じていたこと、到着がなかったこと）を検証ツールが計算し直す仕組みは、まだありません（SkipQuiet でいう V7）。これが「検証ツールの対応」の残りです。

**別に見つかった問題（休みの有無とは関係なし）**：Finalize（集計の確定）が、**どちらの世界でも** `WrongExpectedCount` で断られました。
- 原因：賞金プールは、作るときに「砦のある州の数」を決めます。このときは54（最初の地図）でした。ところが地図が広がって810州になりました。Finalize はゲームの開いた州の数とこの数が違うと断ります（`permutation-prize/src/lib.rs` の Finalize）。
- つまり**地図が広がるシーズンでは、今の賞金プログラムは確定できません**。シーズンの最初には最終的な州の数がわからないためです。賞金プログラムのルールを決め直す必要があります。たとえば、Finalize のときにゲームの開いた州の数を使い、作るときの数は使わない、などです。オーナーの判断が要ります。設計は [prize-finalize.ja.md](prize-finalize.ja.md) にまとめました。
- **その後**：オーナーが P1・P1'・B を了承し、賞金プログラムを直しました（[prize-finalize.ja.md](prize-finalize.ja.md) §7）。Finalize は、確定のときのゲームの州の数（6つの ProvinceFund の合計 − 7）と照らし合わせます。2世界比較をやり直し、どちらの世界でも 810/810 で確定し、結果も同じでした（6か国の同点）。
