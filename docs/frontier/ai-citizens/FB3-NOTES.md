# FB3: audit fixes (D1 to D3 of the wave-B fix plan, and the audit reviewer's issues)

Branch `frontier/ai-fb3`, worktree `.claude/worktrees/ai-fb3`, base `frontier/ai-integ` at `0cc0973`. Local commits only, nothing pushed. Files: `citizens/verify-minds.mjs`, `citizens/audit/{claims,episodes,replay,season_end}.mjs` (`claims.mjs` is new), the audit tests and the audit fixtures. No program, ABI, rules, wasm, sim, herald, agents, `session.mjs` or `advisor.mjs` file was touched, and no Rust. Nothing here was run live: no llama-server, no Gemma, no stack, no devnet, no paid API.

What this unit changes is how the audit judges a run. It does not change a run, and it makes no claim about how any run (smoke-b2, smoke-b3) would now come out: **not run** against any real run's published files. The only real run it was applied to is the recorded slice-4 fixture (result below).

## 1. What was fixed, and the test that fails on the old code

"Fails on old" was shown by checking out the pre-FB3 `verify-minds.mjs`, `audit/episodes.mjs`, `audit/replay.mjs` and `audit/season_end.mjs` from `HEAD` and running the four audit test files against them, with the new tests and the new fixtures in place: `node --test test/citizens-audit-fb3.test.mjs test/citizens-audit-fb3-m11.test.mjs test/citizens-audit-mini.test.mjs test/citizens-audit-slice4.test.mjs` gave **90 tests, 59 pass, 31 fail** on the old code. The new code passes all of them (section 3). The four new tests that pass on the old code are named in section 1.7.

### D1: a partial run was a full verdict (`--only M2` wrote `verdict: PASS` to the file the service publishes)

- `verifyMinds`: the verdict covers all seven checks. A check that was not run, or a `--through` that cut the range, turns PASS into INCOMPLETE; FAIL stays FAIL. The report carries `partial: true`, `not_run: [...]` (and `through_override`).
- `main`: a partial run never writes `PUB/verify-minds.json` (it says so on stderr); with `--out FILE` it writes the partial report there. Exit code 3 for INCOMPLETE as before. An unknown check id in `--only` is exit 2.
- The stdout summary now prints, per check, `unverified` fields and the counts `redacted_skipped`, `redacted_skipped_ai`, `m9_excluded_redacted`, `vacuous`, `skipped`; the stderr log line prints them too.
- Tests (all in `test/citizens-audit-fb3.test.mjs`): `D1: --only leaves checks out ...` (exit 3, INCOMPLETE, a sentinel `PUB/verify-minds.json` is untouched, `--out` writes `partial: true`), `D1: a failure in a partial run is still a FAIL ... --through is a partial run too`, `D1: a full run through the command line writes PUB/verify-minds.json (PASS, exit 0) ...` (a full CLI run through an HTTP front of the chain double and a fake llama: PASS, file written, no `partial`). `citizens-audit-mini.test.mjs` no longer pins `verdict === 'PASS'` after `--only M2`; it pins INCOMPLETE and exit 3.
- Correction to an earlier claim: the AC8 mini test asserted that a run of one check wrote `verdict: PASS`. That was a wrong pin, not a feature.

### D2: M3 trusted what the operator writes

M3 now compares the covered range with three sources: the herald (`hi < headBell - 1`, `tail_truncated` with `source: "herald log"`; `--through` overrides), the registrar's signed anchors index (`first_bell`, `last_bell`, `anchored`; its signature is checked, `anchors_index_signature`; a missing index is `unverified`), and **the anchor memos the registrar sent, read from the chain** (`getSignaturesForAddress` of the registrar, memo text `wylls-ai/1 <season> <bell> ...`; a bell outside the files is `tail_truncated` or `head_truncated`, two memos with different roots for one bell is `anchor_memo_conflict`). A registrar history that cannot be read is `unverified`, not a silent skip. Tests: `T1 tail truncation ...` (caught three ways; with the index also deleted, the herald and the chain still catch it), `T1: a head cut ...`, `T1: a chain history that cannot be read is "unverified"`.
- **T2, the label of a destination** moves the due bell, and "unrevealed", "not_sent" and "planned" skipped the REVEAL comparison. Now: "unrevealed" fails (`unrevealed_but_revealed`) when the herald logged a REVEAL of that march (looked up by the planned arrival and by the arrival of the public DEPART, never by the opening's own `arrive_bell`) at or before `release_bell + 6`; "not_sent" fails when the record's tx list (the minds file's list and every late update together) holds a sent march (`not_sent_but_sent`), when it lists no transaction at all (`not_sent_unsupported`), or when a listed transaction is a Depart (tag 0x50) on chain although its intent label says otherwise (`not_sent_but_depart_on_chain`); "planned" is compared with the public REVEAL when there is one (`destination_mismatch`); a record whose tx list sent a depart or march and whose opening names no destination fails (`march_without_destination`; a recall alone is not counted, because the plan's `intended` list may not name its host). Tests: `T2: a revealed march labelled "unrevealed" ...` (with the control that an honest "unrevealed", a host that never had a REVEAL, is not accused), `T2: ... "not_sent" ...`, `T2: an opening that names no destination ...`, `M3: a "planned" destination ...`.

Tests: `T3: a talk leaf flagged redacted ... fails M3 and M8`, `T3: a leaf with no bytes and no flag ...`, `T3: a record with its bytes present is checked ...`.
- **T4, a stored request body replaced by `{redacted:true}`** took a decision out of the M9 sample without a word. M9 now requires the stub's `request_hash` to be the record's (`redacted_request_hash`) and a tombstone behind it: the list must not be empty and the decision must have authored a tombstoned message (provenance table) or have had an inbox (`redacted_request_unjustified`); the excluded count stays `m9_excluded_redacted` and is printed. ### D3: M11 used a stored focus unchecked

A rejected stored focus is counted (`retrieval.focus_rejected`) and its retrieval is not recomputed from it.
- Part 2 that recomputed nothing is no longer a pass: no sampled decision (`vacuous: true`) or sampled decisions with no opened candidates are `unverified('retrieval')`.

## 2. What was rebutted or left, and why

- **The budget cut in M11 is still a plausibility reading** (`explainRetrieved` accepts any prefix cut of the oldest unprotected ids). The reviewer's fix, recomputing the block's token cost with the committed `block_tokens`, cannot be done from the published data: `mind/prompt.mjs` re-renders the memory block with a smaller budget (`memBudget` shrinks by 100 down to 120) when the whole prompt is too long, the budget used is not stored per decision, and the ledger and summary parts of the block are not published per decision. Not fixed; M11 now says so in a note whenever a cut was needed to match, and counts them (`with_budget_cut`). A service change that stores `memory_budget` with each decision would make it checkable.
- **The derived-focus variants (up to four) are unchanged.** They apply when the service stored no focus (older runs, the slice-4 fixture).
- **The inbox window and the threat window are the verifier's reading**, not stored values: any talk record addressed to the AI or its nation at or before the decision's bell justifies that sender's tag; a W-THREAT within 12 bells justifies a nation. If the real watcher delivers a threat to a decision more than 12 bells after it was logged, an honest stored focus would be rejected. Storing `inbox_tags` and `threat_nations` per decision would make it exact. **Not run on any real run.**
- **Seat-script mismatch stays `unverified`**: the seat script can be a file outside the committed tree (`--seat-script`), so a different in-tree file is not evidence of a mismatch. The injection corpus is hashed from one fixed path, so there a mismatch is a failure.
- **The sample seed is operator-influenced** (the last published `minds_root`; an operator can append a record to the last bell to change who is audited). Not changed: the seed rule is the contract's (7.3). For the architect: a seed the operator cannot grind (a later chain blockhash) would close it.
- **Published minds files still carry an unsealed decision's `public.say` as it was anchored**, so a redacted message's text can still be read there (the anchored record cannot be edited without breaking the root). Contract 6.3 says redaction blanks "bytes and text in files, season-end bundles and cards"; this part is a deviation the architect has to decide. FB3 blanks only what the season-end bundle publishes.
- **A non-redacted decision that happens to hold the same text as a redacted one** is blanked in `full/decisions` too (the match is by text), so M8 would report `text_differs_from_mind_output` for it. Rare; not fixed.
- **Season-end openings use the planned arrival to look up the REVEAL** (`destinationsOf` is handed `feed.revealOf` by `server.mjs`), so a march that arrived off plan is written as `unrevealed` there, and the new M3 then reports `unrevealed_but_revealed` next to `opened_late` for it. The fix is in `server.mjs` (a DEPART-aware reader), which is outside this unit.
- **`CLI season_end.mjs` passes no sanitiser** to the needle match; the live service does. Manual use only.
- M7 (session-key rotation hides earlier transactions), the M7 onboarding exemption and the `V5b` open points stay as the owner/architect list left them.
- **Not done, because the task did not ask for it**: any change to the release job, the registrar (A1, A2) or the run script (the last closed bell having talk, minds and anchor files is A2 of the fix plan, another unit). With FB3, M3 fails a run whose last closed bell has no files; that is the correct reading of "closed bell" and it will fail the smoke-b2 situation (86 closed bells, 85 anchored) until A2 lands.
